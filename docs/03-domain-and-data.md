# Доменная модель, данные и инварианты

Дата: 16 октября 2026 года. Статус: план реализации. Локально проверены P0 (identity и workspaces) и ограниченный P1a (проекты, секции, статусы, tags, задачи workspace, участники, общая оценка WorkPackage и added scope), доказательства — в [11](11-implementation-progress.md); остальная модель ниже, включая полный P1, — будущий план, а не существующая схема. PostgreSQL подтверждён Павлом; клиент и сервер используют TypeScript. Структура модулей описана в [архитектуре](02-architecture.md), команды — в [API](04-api-and-integrations.md), последовательность — в [плане реализации](06-implementation-plan.md).

## 1. Принципы модели

- Задача описывает выполнение работы. Пакет работы (`WorkPackage`) хранит происхождение и исходный бюджет; дробление задачи не создаёт бюджет повторно.
- План на неделю, полная исходная оценка и прогноз остатка — разные величины. В простом случае один ввод создаёт согласованные значения без дополнительных действий сотрудника.
- Факт принадлежит выполнившему работу человеку. Автор ввода, ответственный за задачу и участник встречи могут быть разными людьми.
- Общее время задачи является суммой персональных записей. Дополнительная «общая запись» поверх этих часов не создаётся.
- Изменяемое текущее состояние дополняется неизменяемыми ревизиями и снимками. Полный event sourcing не требуется.
- `null` означает «не известно/не заполнено»; `0` — явное нулевое значение. Пропуски не превращаются в нули при расчёте отчёта.
- Все бизнес-сущности содержат `workspace_id`. Связи внутри пространства проверяются базой, а не только фильтром интерфейса.
- Ранний режим без входа заменяет только получение личности. Доменные команды продолжают получать actor, workspace и capabilities.

## 2. Соглашения хранения и транзакций

Идентификаторы — UUID, создаваемые сервером; внешние Asana GID и идентификаторы Auth хранятся отдельно. У изменяемой сущности есть `revision`, у записи истории — собственный ID, версия схемы, `recorded_at`, `actor_id`, `source`, `request_id` и при необходимости причина. Время события назначает сервер. Клиентская дата выполнения работы — отдельное проверяемое поле.

Длительность хранится целым числом минут (`duration_minutes >= 0`); интерфейс принимает часы/минуты, явно показывает выбранное округление до минуты и передаёт целое число. Парсер десятичных часов избегает ошибок двоичного округления; сервер валидирует тот же диапазон. Для сумм PostgreSQL использует `bigint`; контракт проверяет безопасный диапазон перед выдачей JSON number. Календарные дни хранятся как `date`, моменты — `timestamptz`, зона — IANA-имя. Date-only дедлайн не преобразуется в полночь браузера.

Для команды 5–7 человек первоначальная стратегия — короткая транзакция записи с барьером пространства: `SELECT ... FROM workspaces WHERE id = :id FOR UPDATE`. Все доменные изменения, включая импорты и jobs, получают этот барьер до чтения изменяемого состояния. Это намеренная простая сериализация записей одного пространства; разные пространства независимы. Сеть, скачивание вложений и отправка webhook внутри транзакции запрещены.

Под барьером команда заново проверяет членство, ACL, expected revision и политики; читает `clock_timestamp()` после ожидания блокировки; при необходимости фиксирует наступившие периоды; выполняет изменения; увеличивает `workspace.change_seq`; добавляет audit, outbox и результат идемпотентности; коммитит. Неожиданная ошибка откатывает весь набор; ожидаемый отказ в правке после автоматической фиксации обрабатывается как отдельный результат, описанный ниже. Очерёдность `change_seq` соответствует коммитам этого пространства, потому что блокировка удерживается до завершения транзакции. Автоинкрементная sequence сама по себе такой гарантии не даёт. Несколько событий одной транзакции получают дополнительный `event_ordinal`; auto-freeze и следующая поправка могут попасть в один коммит, поэтому точные версии snapshot определяет manifest, а не один seq.

Большие импорты выполняются ограниченными пакетами, а не одной длительной транзакцией. Измеряются время ожидания барьера, p95 команды и длительность snapshot. После появления измеренной проблемы барьер можно разделить на период/граф/агрегат с фиксированным порядком блокировок; до этого изменения обязательны повторные конкурентные тесты из [проверок](07-verification-and-pilot.md). Модель не обещает неограниченную пропускную способность одного workspace.

Для обычной команды достаточно `READ COMMITTED` с указанным барьером. Согласованный сложный read/report использует `REPEATABLE READ`, а закрытие периода и запись воспроизводимого manifest проходят через тот же write barrier. Drizzle описывает таблицы и запросы; специальные constraints, индексы и триггеры оформляются проверяемыми SQL-миграциями. Автоматическое изменение production-схемы при запуске процесса не допускается.

## 3. Пространства, люди и доступ

| Сущность | Основные поля и назначение |
| --- | --- |
| `User` | Внутренний ID личности, отображаемое имя; не является ролью в пространстве |
| `ExternalIdentity` | `provider`, `issuer`, `subject`, `user_id`; уникальность `(provider, issuer, subject)` |
| `Workspace` | Название, timezone, week_start, `change_seq`, `permission_epoch` |
| `Membership` | Workspace, user, роль, состояние active/revoked, revision; запись сохраняется после ухода человека |
| `Invitation` | Workspace, hash токена, срок, роль, email target, consumed/revoked; появляется при подключении настоящего входа |
| `Project` / `Section` | Проект, архивность, порядок секций, закрепление; секция не является границей доступа |
| `TaskAccessGrant` | Task, membership, capability доступа; явный допуск к private-задаче |
| `ImportedPerson` | Идентификатор человека источника и статус mapping; не создаёт фиктивного исполнителя из импортирующего администратора |

Доменные ссылки на сотрудника используют стабильный `membership_id`. Отзыв membership прекращает вход, но не удаляет старые оценки и worklogs. Уникальность `(workspace_id, user_id)` позволяет восстановить членство с историей, а не создать второго «того же человека». Переназначение записи другому User запрещено.

В P0 сервер подставляет одного из seed-пользователей через development identity adapter. Такой actor выбирается только в разрешённом локальном окружении; нельзя доверять произвольному публичному заголовку `user_id`. Никаких production-приглашений или фиктивной проверки email этот адаптер не выполняет. При подключении Auth `issuer/subject` связываются с существующим User явно; совпадение email не является доказательством идентичности.

Начальные роли Owner/Admin/Member/Viewer преобразуются в capabilities. Проверки различают `task.read`, `task.edit`, `time.write_self`, `time.write_others`, `plan.freeze_self`, `plan.freeze_project`, `plan.adjust`, `fields.manage`, `reports.read` и `members.manage`. Таблица прав живёт в одном policy-модуле и применяется к API, MCP, jobs и импортам.

`Task.visibility = workspace | private`. Для private нужны активное membership и явный grant; владелец пространства не получает автоматический доступ к содержимому. Организатор получает grant при создании. Участие и доступ независимы: удаление отсутствовавшего из списка не отзывает доступ, а отзыв доступа не удаляет историческое присутствие. Для новой серии можно предложить grants участникам, но изменения будущей серии не открывают прошлые приватные экземпляры.

Вложения, комментарии, история полей, материалы, worklogs и снимки задачи наследуют её правила чтения. ACL проверяется до агрегации, поиска и экспорта. Видимость колонки в сохранённом виде не ограничивает доступ. Увеличение `permission_epoch` при отзыве прав инвалидирует кэши и подписки; выдача скачиваемого экспорта требует повторной проверки доступа.

## 4. Задача, пакет работы и индивидуальное участие

| Сущность | Ключевые поля |
| --- | --- |
| `Task` | Project, section, parent_task_id, work_package_id, title, description, status_id, responsible_member_id, dates, visibility, revision |
| `TaskParticipant` | Task, membership, роль assignee/attendee, active/removed, индивидуальные настройки; unique `(workspace, task, member)` |
| `TaskWatcher` | Task, membership; подписка на события, без плана и начисления часов |
| `TaskStatus` | Стабильный ID, имя, системная группа todo/in_progress/done/cancelled, порядок |
| `WorkPackage` | Единица исходного объёма, тип ordinary/meeting, состояние, origin, текущий прогноз остатка |
| `PackageEstimateRevision` | Package, полная оценка в минутах, причина, revision, change_seq |
| `PackageBaseline` | Первое согласованное обязательство пакета и состав его исходного объёма; immutable |
| `LineageEvent` | Split/replace/added_scope/reparent/transfer, исходные и новые IDs, причина, change_seq |

Простая новая задача получает один package автоматически. Создание подзадачи по умолчанию означает детализацию этого package; добавление действительно новой работы явно создаёт другой package и связь `added_scope`. Интерфейс не показывает технический package ID, но предлагает понятный выбор при дроблении уже оценённой работы.

Task может иметь нескольких участников и необязательного одного ответственного. Ответственный не получает чужие часы автоматически. Полная оценка ordinary-package — трудозатраты команды, а не календарная длительность. Добавление второго исполнителя не умножает её и не делит автоматически; нераспределённый бюджет показывается явно.

Иерархия задач, зависимости и lineage — разные отношения. Reparent меняет представление дерева, но не переносит часы между package. В MVP нельзя произвольно объединять несколько package или переносить учтённый worklog в чужое происхождение. При необходимости исправление источника оформляется отдельной проверяемой корректировкой.

Архивирование и отмена сохраняют данные. `done` не означает автоматически нулевой остаток или заполненный факт: команда завершения проверяет политику часов и требует факт либо явный ноль. Статус package «завершён» определяется завершением исполняемых частей исходного объёма и явным подтверждением; частичная отмена маркирует его несопоставимым для обычной метрики точности.

## 5. Кастомные поля, определения и политики

| Сущность | Назначение |
| --- | --- |
| `FieldDefinition` | Стабильный field ID, workspace/project scope, target task/commitment, semantic binding, текущая версия |
| `FieldDefinitionVersion` | Тип, имя, единица, настройки валидации, options, история/фиксация, версия |
| `FieldOption` | Стабильный option ID, архивность; label/color версионируются и не заменяют ID |
| `TaskFieldValue` / `CommitmentFieldValue` | Текущее типизированное значение, definition_version_id, revision |
| `FieldValueRevision` | Old/new, target ID, definition version, actor/source; создаётся по политике истории |
| `FieldPolicyVersion` | Когда обязательно/блокируется, scope, capabilities, действие correction; immutable версия |
| `FieldSemanticBinding` | Связь колонки с доменным значением estimate/weekly_plan/actual/remaining; ID, не название колонки |

Реестр типов P1: text, number, duration, date, single_select, multi_select, person, boolean, URL. Для каждого существуют schema значения, редактор, операторы фильтра и допустимые агрегаты. Значение хранится в JSONB с discriminator типа; duration/date/reference дополнительно индексируются по реальным запросам. Нельзя применять `SUM` к тексту или сравнивать часы с обычным числом без выбранной единицы.

Для каждого scope используется отдельная таблица значений с настоящим FK; универсальная пара `entity_type/entity_id` без ссылочной целостности не является основной моделью. Значения массивов содержат option/member IDs, а не отображаемые названия. Ссылки multi-select на допустимые options проверяет доменная команда в транзакции; при развитии горячих запросов их можно вынести в таблицу связей.

Переименование создаёт definition version и сохраняет field ID. Архивирование убирает поле из новых видов, сохраняя значения и snapshots. Смена типа с накопленными данными требует preview миграции; для MVP создаётся новое поле с явным mapping, а исходное архивируется. Нельзя объявить прежние строковые значения числовыми изменением discriminator.

История значений, включение в baseline и блокировка — три разные настройки. Включение истории не восстанавливает прошлое; отключение не удаляет уже собранные версии. Изменения определения и политики, бюджета, персонального плана, факта, ACL, lineage и dependency всегда аудируются независимо от настройки обычной колонки.

Колонки Hours Est/Hours Fact в шаблоне связываются с доменными величинами через binding. Их переименование не меняет поведение. Hours Fact вычисляется из worklogs и не имеет второго независимого writable field value. Обновление плана через редактор колонки вызывает ту же команду, что и экран планирования.

Политики не содержат пользовательского SQL/JavaScript. P2 поддерживает ограниченные условия AND, triggers manual/self-freeze/cutoff/status-change/period-close и подготовленные действия. Для правил хранится версия; зафиксированный baseline продолжает ссылаться на прежнюю версию после редактирования правила.

## 6. Периоды, бюджет и персональные обязательства

| Сущность | Основные поля |
| --- | --- |
| `PlanningPeriod` | Project, local_start/end_exclusive, timezone, cutoff_at, state planning/frozen/actual_closed, revision |
| `PeriodCommitment` | Неизменная тройка period/package/member, planned_minutes nullable, state, revision; один stable ID на тройку |
| `CommitmentTransfer` | From/to commitment IDs одного period/package, minutes, reason, before/after revisions обеих сторон, actor/change_seq; immutable |
| `CommitmentAllocation` | Commitment, task, allocated_minutes; распределение одного обязательства по исполняемым задачам |
| `PersonalFreeze` | Period, member, immutable snapshot, freeze instant/change_seq, policy versions |
| `PeriodBaseline` / `BaselineItem` | Исходный состав периода, обязательства, поля, структура, package baselines, источники личной фиксации |
| `BaselineAdjustment` | Ссылка на исходный snapshot/предыдущую поправку, причина, before/after, actor, change_seq |
| `PeriodClose` | Cutoff факта и manifest источников; первоначальное закрытие и последующие корректировки |

Уникальность PeriodCommitment: `(workspace, period, package, member)`. Уникальность allocation: `(workspace, commitment, task)`. Сумма allocations не превышает текущий персональный бюджет; остаток показывается как нераспределённый. Для задачи на одну неделю создаётся одна allocation на полный бюджет. Если родитель показывает rollup детей, он не включается в сумму как ещё одна allocation.

Полный известный план недели — сумма персональных commitments, только если оценки всего выбранного сопоставимого состава заполнены. При пропусках показывается knownPlannedMinutes и полнота baseline, а не якобы полный план; точное общее отклонение остаётся null. Общий план обычного package не обязан равняться полной оценке, если работа занимает несколько недель. Оценка 20 часов + полный план 6 часов этой недели + подтверждённый факт 5 часов дают недельное отклонение −1 час; полную точность ещё нельзя посчитать. Прогноз завершения = накопленный факт + текущий остаток, и он не заменяет исходные 20 часов.

Первый согласованный полный estimate фиксируется в PackageBaseline при первой фиксации связанного плана. Для поздно добавленной работы — при явном принятии первой оценки; она остаётся помеченной добавленным объёмом относительно исходной недели. Отсутствующая оценка не заполняется автоматически текущим фактом при закрытии.

Личная фиксация сохраняет commitments конкретного member и выбранные общие поля связанных задач. Его персональные поля блокируются; общие защищённые поля нельзя менять обычным способом, если их уже зафиксировал хотя бы один участник. У других людей остаётся возможность редактировать собственный ещё не зафиксированный план. Смена ответственного или removal участника не снимает существующий lock. Перед PersonalFreeze используется тот же шаг материализации ожидаемых встреч периода, что и перед общей фиксацией: задержка worker не должна пропустить запланированное участие человека.

При фиксации всего периода уже сохранённые PersonalFreeze включаются как источники исходного плана; остальные строки фиксируются на текущем cutoff. Новые commitments человека после его личной фиксации сохраняют метку добавления, даже если общий snapshot создан позже. Для одной общей задачи допускаются разные моменты персонального согласования; snapshot показывает provenance каждой строки.

`TransferAssignment` перемещает явное положительное целое число минут между разными людьми одного period/package. Команда принимает from/to, `minutes`, причину, expected revisions обоих commitments и изменения allocations. У получателя переиспользуется существующий stable commitment ID, в том числе при обратном переносе; новый создаётся только при отсутствии тройки `(period, package, member)`. `expectedTargetRevision = null` означает именно отсутствие записи, а не разрешение затереть существующую.

Для известного источника требуется `0 < minutes <= source.planned_minutes`; у существующего получателя с известной оценкой результат равен прежнему плану плюс minutes. При отсутствии целевого commitment он создаётся с планом ровно minutes. Если source или существующий target имеет `planned_minutes = null`, перенос возвращает `PLAN_VALUE_UNRESOLVED`: сначала нужно явно заполнить/скорректировать неизвестную оценку. Null никогда не подставляется как 0. При полном переносе исходный commitment сохраняется с известным нулём; снятие участия — отдельное явное изменение. Неактивный существующий target требует явного восстановления с expected revision и известным текущим бюджетом.

Обе стороны и allocations меняются атомарно, добавляется immutable CommitmentTransfer с суммой и before/after revisions. Так A=240/B=120, перенос 60 даёт A=180/B=180 без создания второго commitment B. Обратный перенос использует те же IDs; несколько входящих переносов представлены отдельными событиями, а не одним перезаписываемым transfer_origin_id. Исходный baseline остаётся у прежнего человека. Это перераспределение исходного объёма, а не новая работа; факт остаётся у того, кто его выполнил. Перенос после фиксации оформляется разрешённой поправкой с причиной.

Перенос задачи в следующую неделю создаёт commitment нового периода и событие carryover. Прежний baseline и факт не переезжают. В новом периоде показывается новый план остатка; отчёт отличает перенос от новой исходной работы. Удаление строки из недели является состоянием removed/cancelled с историей, не удалением обязательства.

## 7. Cutoff и создание неизменного снимка

Снимок содержит IDs и значения, а не только ссылки на изменяемые строки: task/package/commitment, участников и allocations, оценки, категории, даты, parent lineage, выбранные custom values, definition/option labels и policy versions. Сохраняются `null`, timezone, requested cutoff, actual barrier instant, actor/source и `change_seq`.

Последовательность внутреннего `FreezePeriod` (команда API `FreezePlan` с соответствующим scope) внутри одной транзакции:

1. Получить write barrier пространства и проверить права/идемпотентность.
2. Прочитать серверный clock и актуальную конфигурацию периода; повторная фиксация уже frozen периода возвращает существующий результат.
3. Материализовать ещё не созданные допустимые встречи периода из конфигурации серий, действовавшей до перехода через cutoff; источники создания уникальны, сеть не используется. Команда редактирования серии после cutoff обязана сначала выполнить этот переход со старой конфигурацией и только затем изменить будущий состав.
4. Собрать исходные commitments, личные snapshots и выбранные поля; проверить ограничения суммы и происхождения.
5. Сохранить immutable baseline и его строки, ссылки на исходные полные оценки, событие фиксации, новую версию периода и outbox.
6. Зафиксировать транзакцию; только после этого показывать успешную фиксацию пользователю.

Каждая команда, способная менять план, добавлять/убирать задачи из периода, менять его категории/структуру/участников или сгенерировать встречи, после получения барьера выполняет `ensureDuePeriodsFrozen`. Если cutoff наступил, сначала сохраняется snapshot прежнего состояния, затем команда либо отклоняется как locked, либо применяется как явная поправка/добавление. Ожидаемый доменный результат `plan_locked` (HTTP 409 `FIELD_LOCKED`) после этого перехода коммитит только служебную фиксацию и возвращает её ID, не применяя запрещённую правку; его нельзя реализовать exception с откатом и затем сообщить о несуществующем snapshot. При неожиданной ошибке вся транзакция откатывается, следующий writer повторит проверку. Прочие команды могут инициировать тот же переход; worker нужен для своевременного UI, а не для единственного обеспечения правила.

HTTP-запрос, пришедший в 09:59:59, но получивший барьер в 10:00:01, считается поступившим после cutoff 10:00. Команда, получившая барьер до cutoff, логически предшествует фиксации даже при коммите чуть позже; это выбранная сериализационная семантика, записанная в audit. Транзакции должны быть короткими и иметь timeout; нельзя использовать `now()` от начала долго ожидавшей транзакции как время допуска.

Если worker опоздал, а после cutoff ничего не менялось, snapshot всё равно фиксирует прежний состав. Если изменение пришло раньше worker, оно само сначала фиксирует план. Гонка двух jobs/вкладок разрешается барьером и уникальностью baseline; проигравшая сторона получает уже созданный ID.

Snapshot и подтверждённая история не обновляются и не удаляются runtime-ролью БД. Все строки snapshot вставляются в транзакции его создания; DB-проверка запрещает дописывать items к уже завершённому снимку в последующей транзакции. Администратор БД технически способен изменить данные: это прикладная неизменяемость с раздельной migration-ролью, а не криптографическое обещание.

Поправка создаёт новую запись с обязательной причиной, expected revision и ссылкой на исходный snapshot. Представления «Исходный» и «С поправками» явно различаются. Закрытие факта действует аналогично: поздний worklog становится поправкой, а не незаметным изменением прежнего отчёта.

## 8. Split, replace и защита от двойного счёта

`SplitTask` принимает исходную задачу, новых детей, их распределение существующего плана, expected revisions и классификацию нового объёма. В одной транзакции создаются дети, сохраняется общий package, текущие allocations переводятся с родителя на детей, добавляется LineageEvent. Split/replace наследуют ACL исходной задачи; расширять видимость требуется отдельным явным изменением. Старый snapshot не пересчитывается.

Пример: package оценён в 8 часов; до дробления на родителя записали 2 часа. Затем появились дети A/B, на них записали 3/5 часов. Полный факт package = 2 + 3 + 5 = 10 часов, отклонение от исходной работы = +2 часа / +25%. Строка родителя с rollup 10 часов не добавляет ещё 10 к детям.

Если при дроблении выяснились дополнительные требования на 4 часа, они оформляются новым package и task с `added_scope` относительно первого. Их факт входит в общие затраты периода и показатель добавленного объёма, но не выдаётся за перерасход исходных 8 часов. При смешанной работе человеку нужно разделить фактические записи между явно названными частями; система не угадывает пропорцию.

`ReplaceTask` создаёт новую исполняемую задачу того же package, помечает старую superseded и переносит только текущие allocations/ссылки выполнения. Старые worklogs продолжают ссылаться на прежнюю task; package ID в них не переписывается. Повтор команды с тем же idempotency key возвращает того же преемника.

Перемещение задачи в дереве не меняет `work_package_id`, `source_task_id` worklog и lineage. Наличие родителей не означает, что каждый узел — отдельный бюджет. Отчёт агрегирует worklogs по уникальным log IDs и revisions, commitments — по их IDs; join с участниками/тегами не должен размножать суммы.

Создание внешне новой, но семантически той же работы невозможно надёжно распознать автоматически. Система гарантирует видимость добавлений и происхождения известных split/replace, а не обнаружение намерений. Владелец подтверждает классификацию подозрительных добавлений через явную операцию с журналом.

## 9. Worklogs, простой ввод факта и исправления

| Сущность | Основные поля |
| --- | --- |
| `WorkLog` | Workspace, неизменные task/package/worker/source_kind/source_key, latest_revision_id; manual_period также закрепляет period_id источника |
| `WorkLogRevision` | Revision number, minutes, work_precision, work_date/period_id, category ID/version, state active/void, reason, actor/change_seq |
| `Attendance` | TaskParticipant, unknown/present/partial/absent, actual_minutes nullable, revision, confirmed_by/at |
| `TimeCorrection` | Причина, source/target logs, before/after revisions, затронутые периоды, preview/hash при merge; одна атомарная операция |

У WorkLog неизменные task, worker, source и происхождение package. Исправление длительности или категории добавляет ревизию; удаление — void revision. День/точность можно исправить ревизией только у источника, где они не входят в identity. Для manual_period тройка task/person/period неизменна: PATCH/revision не может заменить ни её часть, ни производный source key. Ошибочный исполнитель, задача или период такого источника исправляются атомарной TimeCorrection, а не переносом прежнего ID в другое место.

`work_precision = day | period`. В day обязательно есть work_date и timezone контекста; в period — точный PlanningPeriod, а work_date отсутствует. Недельные 5 часов включаются в полный отчёт недели, но не распределяются на пять дней. Фильтр на часть недели выводит такие часы отдельно как «без разбивки по дням» и не добавляет их молча к дневным значениям.

`SetManualPeriodWork(task, person, period, minutes)` обслуживает простую ячейку. Стабильный source key = `(task_id, person_id, period_id)` в namespace `manual_period`; изменение создаёт ревизию этой записи, а не прибавляет второй такой же worklog. Если уже есть meeting/daily/другие источники, ячейка открывает детализацию и не заменяет общий aggregate одним числом.

Перенос manual_period принимает `expectedSourceRevision`, `expectedTargetRevision` и другую целевую тройку; совпадающая тройка требует обычной правки, а не void/merge самого источника. В одной транзакции исходный источник получает void revision, а целевой — новую запись либо ревизию существующей. `expectedTargetRevision = null` допустим только при отсутствии target log; наличие даже void-источника требует его actual revision и переиспользования ID. Для существующего target обязателен explicit merge preview с обеими версиями, исходными минутами, предлагаемой итоговой суммой, причиной и hash входов; stale preview отклоняется без частичного void. Нельзя молча перезаписать или сложить два пользовательских итога. Принятый merge показывает, например, перенос 60 в существующие 120 → target 180/source void. Обе затронутые недели проверяются на close/права корректировки; correction link, audit, изменения и idempotency result коммитятся вместе. Повтор команды не начисляет минуты повторно.

Worklog по person A, введённый менеджером B, входит в часы A и audit B. Для групповой строки Hours Fact показывается сумма; её обычное редактирование требует выбора человека и источника. Прочие прямые внесения имеют свой уникальный source key; клиент передаёт idempotency key на создание.

Ключевые поля времени и категория сохраняются в самой ревизии. Последующее изменение категории задачи не переклассифицирует старый факт. Владелец может применить отдельную корректировку категории к выбранным записям с preview и причиной. Для закрытого периода создаётся новая версия отчёта, исходная остаётся доступной.

Confirmed zero хранится как активная нулевая ревизия и участвует в показателе заполненности. Отсутствие записи и Attendance.unknown остаются missing. Void не равен нулевому факту. При агрегировании выбирается ровно одна разрешённая revision каждого log на выбранную границу истории.

## 10. Встречи, участники и начисление часов

У экземпляра встречи есть `MeetingDetails`: planned_start, planned_duration_minutes, actual_duration_minutes nullable, organizer, join URL, recording URL, summary URL/text. Длительность — календарная характеристика одной встречи; сумма персональных часов — затраты команды. Материалы экземпляра не копируются в следующий экземпляр.

Плановая длительность по умолчанию предлагается каждому активному attendee как индивидуальный план; это явное правило meeting-шаблона. Организатор может задать персональную часть времени. Для ordinary-task такого умножения нет. WorkPackage встречи объединяет участников только этого экземпляра, а сама серия не получает часов.

`ConfirmAttendance` атомарно принимает список person/status/minutes с expected attendance и связанных worklog revisions, проверяет `time.write_others` для чужих записей, обновляет Attendance и создаёт/версионирует соответствующие WorkLogs. Уникальный источник `meeting_attendance:<attendance_id>` позволяет UI, MCP и повтору job сослаться на один факт.

Для present подставляется подтверждённая длительность встречи; partial требует явного положительного времени не больше её длительности; absent означает подтверждённый ноль. Unknown не создаёт факта. Подготовка и работа после встречи оформляются отдельными источниками, чтобы не делать присутствие длиннее самого созвона. Если реальная длительность неизвестна, массовое подтверждение сначала запрашивает её или явные персональные значения.

Пять участников по 1 часу дают 5 человеко-часов и одну часовую встречу. Три полных участника, один на полчаса и один absent дают 3,5 человеко-часа. Организатор не добавляется шестым источником, если он уже в списке участников. Watcher не получает часов.

Правка своего начисленного времени использует тот же attendance worklog, а не второй ручной period source. При изменении длительности встречи уже подтверждённые часы не переписываются автоматически: UI предлагает список затрагиваемых людей и отдельное подтверждение поправки. Batch должен отклонить конфликт ревизии, сохранив прежние данные целиком.

Удаление приглашённого до факта меняет участие/отсутствие текущего экземпляра. После начисления отмена участия требует явного void/correction; исходный baseline остаётся. Отмена всей встречи не удаляет существующий факт: команда требует подтвердить, был ли созвон фактически проведён и какие записи нужно исправить.

## 11. Повторения, timezone и исключения

| Сущность | Поля и ограничения |
| --- | --- |
| `RecurrenceSeries` | Project, шаблон, organizer, timezone, start_date, end_date/count, weekdays, local_time, duration, revision |
| `RecurrenceSeriesVersion` | Неизменяемая конфигурация и effective_from; история редактирования «эта и будущие» |
| `RecurrenceInstance` | Series, occurrence_key, task_id, original_local_date, generation_version, resolved_start; unique series/key |
| `RecurrenceException` | Instance, skip/move/override, исходное и новое расписание, reason, revision |
| `RecurrenceGeneration` | Series version, горизонт/период, результат, cursor; контроль воспроизводимости и retries |

В MVP поддерживается не больше одного номинального вхождения серии в локальный день: ежедневные/еженедельные повторы по выбранным дням. `occurrence_key` = первоначальная локальная дата в рамках stable series ID, независимо от UTC, времени начала и номера версии. Перенос сохраняет key и task ID. Два созвона одного дня задаются двумя сериями; более общий RRULE — следующий этап.

Materialize создаёт обычные Task/TaskParticipant/MeetingDetails и commitments перед фиксацией недели. Уникальность `(workspace, series_id, occurrence_key)` защищает от повторной job. Нельзя хранить только виртуальные события календаря: у каждого экземпляра нужны собственные права, материалы, факт и baseline.

«Только эта встреча» создаёт exception. «Эта и будущие» создаёт series version с явной датой вступления; не переписывает прошедшие, завершённые или зафиксированные исходные snapshots. Уже материализованные будущие экземпляры сохраняют IDs; допустимые текущие поля меняются командой с историей, а затронутый frozen план получает поправки. Изменение дней недели показывает preview отменяемых и добавляемых экземпляров.

Удалённый из расписания будущий экземпляр помечается cancelled, а не удаляется. Если та же nominal date возвращается, используется прежний instance ID через явное восстановление. Ручной перенос не должен быть отменён regeneration; exception имеет приоритет над новой базовой конфигурацией до его явного сброса.

`count` считает номинальные запланированные вхождения; skip не добавляет автоматически встречу в конце серии. Перенос понедельника на вторник сохраняет понедельничный key. Если вторник уже имеет другой созвон серии, preview показывает пересечение; система не объединяет факт и не удаляет один из экземпляров автоматически.

Расписание разрешается по IANA timezone, сохраняя intended local time, полученный UTC offset и UTC instant. Для несуществующего локального времени при весеннем DST выбранная политика MVP — сдвиг к первому допустимому времени с заметным предупреждением; для двусмысленного осеннего времени — более ранний instant. Политика версионируется, пользователь может перенести конкретный экземпляр. Реализация использует timezone-библиотеку и тестовые зоны/даты, а не арифметику `+24h`.

Плановая длительность означает реальное прошедшее время: конец = resolved start + duration. Если часы переводятся во время встречи, 60 минут остаются 60 минутами. Изменение timezone пространства не переинтерпретирует старые series/period/work dates. При переносе встречи через границу недели baseline остаётся в исходной, факт попадает в период фактической даты.

## 12. Зависимости, дерево и представления

`TaskDependency` хранит predecessor_task_id, successor_task_id, type finish_to_start, revision и состояние active/removed. Оба endpoint принадлежат одному workspace. Для MVP допускаются ссылки между проектами одного workspace, если actor видит и вправе менять обе задачи; внешние ссылки другого workspace запрещены.

Уникальность `(workspace, predecessor, successor, type)` и CHECK `predecessor <> successor` отсекают дубли/петлю. Команда AddDependency после получения workspace barrier проверяет рекурсивным запросом, существует ли путь successor → predecessor. При наличии пути операция отклоняется. Поэтому одновременные A→B и B→A не могут обе пройти на старом состоянии.

Task parent тоже проверяется на цикл под тем же барьером. Lineage replace/split не переиспользует таблицу dependency. Перетаскивание даты Gantt меняет обычные dates той же задачи; оценка часов не пересчитывается в календарную длительность автоматически. Автоматический каскадный reschedule не входит в первый этап.

SavedView хранит versioned JSON-конфигурацию колонок, фильтров, сортировки и группировки со стабильными field IDs. GraphLayout хранит координаты по `(view, task)`; они не создают вторую задачу. Закреплённая секция — настройка вида/проекта, а не дубликат сущностей. Сохранённые фильтры не обходят ACL.

Если dependency endpoint скрыт пользовательским фильтром, UI может предложить показать доступную задачу. Если он закрыт ACL, ответ не раскрывает ID, название, участников или число приватных препятствий; доступный узел получает только разрешённый нейтральный признак блокировки. Такая информация и режим обязательности блокировки задаются отдельной capability-политикой.

## 13. Отчёты, историческая граница и приватность

| Сущность | Содержание |
| --- | --- |
| `ReportDefinition` / `Version` | Источник, метрики, фильтры, группировка, график, выбранная семантика baseline/current |
| `ReportRun` | Definition/metric versions, период/timezone, baseline IDs, fact cutoff/change_seq, manifest и результаты с completeness/coverage |
| `ReportInputManifest` | Точные ID/revision источников, включая worklogs, commitments, lineage, definitions и close/adjustment |
| `ReportExport` | Run ID, audience/access epoch, срок, состояние; выдаётся через проверяемый endpoint |
| `ReportMeasureResult` | Known planned/actual minutes, missingEstimateCount, baselineCompleteness, factCoverage, nullable exact variance; value object run, не отдельный источник часов |

Первый отчёт строится как типизированный query plan с разрешёнными метриками/операторами. Пользователь выбирает field IDs и фильтры, но не SQL. Источник факта — WorkLogRevision, а не дата закрытия Task. Источник исходного плана — immutable baseline, текущего плана — текущие commitments с явной подписью режима.

Для закрытого периода manifest выбирает точную ревизию каждого источника в согласованной транзакции. Одного timestamp недостаточно: могут совпасть времена, а транзакции могут завершиться в другом порядке. `change_seq` и точный manifest разрешают неоднозначность. Реализатор может сначала хранить manifest в JSONB, но обязан сохранять ссылки на уникальные версии и их schema version.

Оригинальный ReportRun не меняется при коррекции факта; команда пересчёта создаёт новый run и ссылку `supersedes_run_id`. Версия метрики тоже фиксируется: изменение формулы не переименовывает прежние результаты. Для неподдерживаемой старой формулы показывается сохранённый результат с provenance, а не незаметно другой расчёт.

При чтении любого run заново применяются текущие membership/ACL. Историческая возможность видеть задачу не даёт права видеть её сегодня. Если состав доступных данных изменился, отображается разрешённая проекция с пометкой, что это часть исходного run; исходный общий aggregate и чужой cached export не выдаются. Полная воспроизводимость чисел возможна при том же доступе; права всегда имеют приоритет. Для package с недоступными источниками полный baseline-бюджет и метрика точности не выдаются через доступного потомка: разрешён только aggregate доступных worklogs, а полное сравнение обозначается неприменимым к выбранным данным. Rollup дерева также считается после ACL, без раскрытия количества скрытых частей.

Разрешённый самостоятельный доступ человека к собственным часам после отзыва Task ACL возвращает только его duration/date/precision в личной ведомости без названия, участников, URL, комментариев и раскрывающих категорий. Эта проекция не появляется в чужом командном отчёте. Отдельное право руководителя видеть агрегат личных встреч не включается по умолчанию.

Каждое сравнение возвращает `knownPlannedMinutes` — сумму только известных оценок, `missingEstimateCount` — число выбранных сопоставимых единиц с null-оценкой, `baselineCompleteness = { knownItemCount, totalItemCount, ratio, complete }` и `factCoverage = { recordedItemCount, totalItemCount, ratio, complete }`. Единица сопоставления определяется метрикой: commitment для недели, package для полной оценки. Ноль является известной оценкой/подтверждённым фактом; отсутствие и void не являются заполнением. При totalItemCount=0 ratio=null, complete=false, сравнение неприменимо. Счётчики относятся только к разрешённому выбранному составу и не раскрывают число скрытых объектов.

Fact coverage означает наличие внесённого активного факта по каждому ожидаемому элементу, включая явный 0; она не доказывает отсутствие другой незаписанной работы. `actualMinutes` показывает только внесённые минуты и сопровождается factCoverage; при пропусках это известная часть факта, а не доказанный полный факт. Exact total variance и её процент возвращаются лишь для полного сопоставимого состава с заполненными оценками и фактом, применимой временной точностью и доступом к необходимым источникам. При неполном baseline или факте `totalVarianceMinutes = null` и `totalVariancePercent = null`; нельзя вычесть известную часть плана из всего факта и назвать результат перерасходом. Добавленный объём отображается отдельно и не включается незаметно в исходную сравниваемую группу.

Контрольный пример: планы `[120, null]`, факты `[120, 60]` дают knownPlannedMinutes=120, actualMinutes=180, missingEstimateCount=1, baselineCompleteness `{knownItemCount:1,totalItemCount:2,ratio:0.5,complete:false}`, factCoverage `{recordedItemCount:2,totalItemCount:2,ratio:1,complete:true}` и totalVarianceMinutes=null. Отдельный явно названный cohort «Только элементы с известной оценкой» может показать 120/120 и отклонение 0, но обязан указать охват 1 из 2 разрешённых элементов и собственный фильтр. Такой subset не заменяет общую метрику и не называется точностью всего периода.

Базовые метрики:

- План/факт недели: baseline commitments против worklogs по work date/period, с completeness и coverage описанного выше сопоставимого состава. При пропусках точное общее отклонение null, а известные суммы показываются раздельно. Planned, added, transferred, carryover различаются; task count не используется как эквивалент часам.
- Отклонение исходного объёма: `actual_original_scope − baseline_package_estimate` только при полной известной оценке и факте завершённого сопоставимого объёма; иначе null. Процент дополнительно требует estimate > 0. Для нескольких packages применяется то же требование полноты всего выбранного состава. Новые package не приписываются старому перерасходу.
- Прогноз незавершённого: `actual_to_date + remaining_forecast`; неизвестный остаток остаётся неизвестным, а не нулём.
- Доли работы: факт одной основной категории / весь разрешённый факт, включая «Без категории». Multi-select tags дают пересекающиеся группы с соответствующей подписью.
- Качество данных: missing estimate/fact/category, unknown attendance, unresolved imports, нераспределённые commitments и неточный дневной факт.

При join с участниками, tags или allocations сначала выделяются уникальные worklog IDs/выбранные revisions, затем агрегируются часы. Проекция по исполнителям использует worker, сравнение исходных назначений — baseline member, а журнал ввода — actor. Эти измерения нельзя молча подменять друг другом.

## 14. Идемпотентность, jobs, audit и интеграции

`IdempotencyRecord` уникален по `(workspace, actor_or_service_id, command_name, key)` и содержит hash канонического запроса, состояние и result IDs. Повтор того же payload возвращает прежний результат; другой payload с тем же key — конфликт. Результат сохраняется в транзакции команды. Дополнительно действуют постоянные domain-source uniqueness для attendance, recurrence и import; истечение HTTP idempotency record не разрешает создать их дубль.

`AuditEvent` — immutable actor/source/request/change_seq/entity/revision/action с безопасным diff и причиной. Полные значения секретных credentials не пишутся. Доступ к event также фильтруется ACL сущности, включая историю приватности. Worker имеет service identity и сохранённого initiating actor при пользовательской операции; он не impersonates владельца.

`OutboxEvent` сохраняется вместе с доменным изменением: stable event ID, version, workspace, entity refs и минимальный payload. Relay после коммита передаёт job в PostgreSQL-backed очередь; кандидат — pg-boss. Полезная нагрузка приватных сущностей не рассылается всем подписчикам пространства. Перед внешней доставкой заново проверяется разрешение интеграции на данные.

Доставка имеет семантику at-least-once. Crash после enqueue, но до отметки outbox, приводит к повтору; consumer хранит dedup по event ID. Для recurring и cutoff jobs дополнительно используются уникальные domain keys. Очередь не заменяет transactional outbox. Подробности retries, HMAC и MCP — в [контрактах API](04-api-and-integrations.md), эксплуатация — в [Railway-плане](08-railway-and-operations.md).

`JobExecution` хранит kind, domain key, attempts, status, last safe error и correlation IDs; lease/claim берётся средствами выбранной очереди. Job читает актуальные policy/ACL и вызывает ту же команду. Просроченная job не получает право перезаписать locked поле. Внешний запрос выполняется вне write barrier, затем его результат записывается короткой идемпотентной командой.

## 15. Импорт и доказуемое происхождение

`ImportBatch` хранит source system/project, fingerprint исходного файла, actor, mapping version, preview/commit status и счётчики. `ExternalReference` уникален по `(workspace, source_connection, entity_type, external_id)`; связь с Asana сохраняется после переименования задачи. Разные connection не считаются одним источником только из-за похожего названия проекта.

Preview ничего не меняет в задачах. Mapping пользователей, полей, статусов и времени подтверждается явно. Повторный commit использует stable source key; он не создаёт вторую задачу/вторые часы. Если импортированную запись уже меняли в Workloom, reimport создаёт конфликт для выбора, а не молча заменяет локальную версию.

Импорт текущего Hours Est получает provenance `imported_current`, а не `original_baseline`. Исторический baseline разрешён только при достаточных исходных данных с явной отметкой происхождения. Недатированный факт не записывается в произвольно выбранную неделю: хранится в import staging как unresolved precision до подтверждения периода или остаётся вне точной недельной отчётности.

Неизвестный исполнитель остаётся `ImportedPerson/unmapped`. До mapping его часы не попадают на импортировавшего пользователя. Комментарии, файлы и private-флаги требуют отдельной сверки; если источник приватности неполон, preview не делает такие задачи общедоступными автоматически. Импорт проходит те же правила cutoff, ACL и correction, что и ручной ввод.

Каждый объект содержит внешнюю ссылку и batch ID, созданные записи — audit с source=import. Rollback партии не означает delete истории: возможен ограниченный revert только ещё не изменённых созданных объектов с отчётом исключений. Исходный экспорт сохраняется как контролируемый артефакт согласно правилам хранения, без включения секретов в репозиторий.

## 16. Ограничения и индексы PostgreSQL

Это требования к будущим миграциям, а не уже исполняемый SQL. Для tenant-таблиц создаётся `UNIQUE(workspace_id, id)`, а связи используют composite FK `(workspace_id, parent_id)`. Так task пространства A не сможет сослаться на project, member, field, package или baseline пространства B даже при ошибке приложения.

| Ограничение / индекс | Назначение |
| --- | --- |
| `memberships(workspace_id,user_id)` unique | Один стабильный участник на личность |
| `task_participants(workspace_id,task_id,member_id)` unique | Участник без дублей; removal — состояние |
| `period_commitments(workspace_id,period_id,package_id,member_id)` unique | Один stable commitment навсегда, включая снятые/нулевые; transfer переиспользует существующий ID |
| `commitment_transfers` same-period/package FK + CHECK from≠to, minutes>0 | Явный перенос с обеими ревизиями; проверка известного остатка под барьером |
| `commitment_allocations(workspace_id,commitment_id,task_id)` unique | Одно распределение на task; проверка общей суммы под барьером |
| `work_logs(workspace_id,source_kind,source_key)` unique | Постоянная защита от повторного начисления; manual_period task/person/period immutable, каждая revision совпадает с period источника; перенос через correction |
| `work_log_revisions(workspace_id,work_log_id,revision)` unique | Ровно одна версия с конкретным номером |
| `recurrence_instances(workspace_id,series_id,occurrence_key)` unique | Независимость от retry и смены UTC offset |
| `external_references(workspace_id,connection_id,entity_type,external_id)` unique | Повторный импорт без дублей |
| `personal_freezes(workspace_id,period_id,member_id)` unique | Исходная личная фиксация; поправки в отдельной таблице |
| `period_baselines(workspace_id,period_id)` unique для original | Единственный исходный baseline; поправки не заменяют его |
| `tasks(workspace_id,project_id,status_id,position)` | Таблица и активный проект; keyset pagination |
| `work_logs(workspace_id,worker_member_id)` + revision date/period indexes | Личные/периодные отчёты |
| `task_access_grants(workspace_id,member_id,task_id)` | Permission-filtered набор до агрегации |
| `dependencies(workspace_id,predecessor_id)` и `(workspace_id,successor_id)` | Обход графа и проверка цикла |
| `audit_events(workspace_id,entity_type,entity_id,change_seq)` | История и ревизии объекта |
| Outbox pending partial index | Небольшая выборка неотправленных событий без полного сканирования |

CHECK-ограничения проверяют nonnegative duration, совместимость precision/date/period, start/end и недопустимость self-dependency. FK не используют каскадное удаление исторических записей. Sum allocations, циклы, option membership и разрешения требуют транзакционной доменной проверки; один CHECK их не заменяет.

JSONB не получает универсальный GIN-индекс «на всё» по умолчанию. Индексы создаются под реальные фильтры/отчёты после EXPLAIN на seed-наборе. Политики Row Level Security можно добавить как второй слой, но tenant isolation не зависит от них: обязательны composite FK, workspace-scoped repositories и тесты отрицательного доступа. Runtime DB-роль не владеет схемой и не имеет DDL-прав.

## 17. Последовательность миграций и границы этапов

P0–P6 обозначают функциональные этапы, а не неизменный календарный порядок или номера SQL-миграций. Первый недельный пилот P6 может начаться после P3 и минимального импорта P5.4/P5.6; P4 и остальные возможности P5 развиваются параллельно или позже. Auth-миграции не зависят от graph/MCP. Каждая реальная миграция имеет собственный последовательный ID и явные зависимости; полный объём MVP из продуктового документа сохраняется.

- **P0:** users/dev identities, workspaces/memberships, migrations, command transaction/barrier, audit/outbox/idempotency основы; synthetic seed для двух пространств. Реальный provider подключается позднее.
- **P1:** projects/sections/tasks/statuses/packages, participants/basic ACL, typed fields/versions/current values, история, saved views. Создаются простые package автоматически; расширенный UI планирования ещё не нужен.
- **P2:** periods, commitments/allocations, package/period baselines, поправки, worklogs/revisions, close/manifest и три базовых отчёта. Здесь проверяются split/replace/transfer и cutoff, а не откладываются до миграции команды.
- **P3:** recurrence/version/exception/generation, meeting details, attendance, материализация до freeze и постоянный dedup источника. Общая модель multiple participants уже существует из P1.
- **P4:** dependencies, graph layouts, Gantt-конфликты. Исторические даты и shared command API уже готовы из P2.
- **P5:** расширение report definitions/runs, import batches/mapping/external refs и scoped MCP credentials. Базовые report manifests из P2 не заменяются другой моделью.
- **P6:** внешний Auth mapping, приглашения, служебные роли БД, Railway backups/restore и пилотные миграции. Development identity запрещён в публичном окружении.

Каждая миграция имеет проверку на пустой БД и на данных предыдущего этапа. Потенциально разрушающее изменение сначала добавляет новое поле/версию и backfill, затем переключает чтение; старый формат удаляется только отдельным решением после проверки восстановления. Seed и demo не подменяют production-данные.

До начала реализации по каждому этапу сверяются команды и DTO с [API](04-api-and-integrations.md), состояния редакторов с [UX](05-client-and-ux.md), а наблюдаемые сценарии — с [проверками пилота](07-verification-and-pilot.md). Таблицы этого документа не должны заставлять P0 реализовывать весь продукт сразу: ранние этапы создают только необходимую часть, сохраняя указанные границы и инварианты.
