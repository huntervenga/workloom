This slice covers independent copies, stable refresh feedback and clearer reports. The shared reusable summary templates and shared-activity/meeting integration described in [102](102-shared-activities-and-summary-templates.md) remain **PROPOSED, NOT IMPLEMENTED**. Duplicating a section creates independent settings; it does not create a linked template or synchronize later edits.

## Duplicate a task

Open the task row actions and choose **Duplicate task**, or open the task details and choose **More task actions → Duplicate task**. Give the new task a name, choose which description, assignee, start/due dates, tags, priority, participants and subtasks to retain, review the server preview, then create the copy.

**Custom field values** start unselected. Choose individual ordinary fields when their current values should be copied. This rule applies equally to fields named Plan, Fact, Hours Estimation, Actual, or anything else. There is no special field name or implicit time classification. Explicitly copying a value used as actual hours in a report can increase that report's totals; the dialog explains this. Legacy recorded work is never copied.

New tasks use the project's first **To do** status, ordered by position and ID. The duplicate is placed after the original sibling. Included descendants are copied in preorder, with new parent IDs. A detail child shares its copied parent's package; an added-scope child gets a new package. Duplicating a subtask as a sibling retains the existing parent and the existing detail-versus-added-scope rule. Current legacy package estimates are not copied into new packages. Meeting preparation cannot bypass the separate-package requirement.

Comments, prior activity, field history, dependencies, personal plans, manual/attendance worklogs, baselines, original estimates, report snapshots and meeting/recurrence identities are excluded. Normal create/value-write events on the new identities form their own new history.

## Duplicate a section

Hover a real section header, open **Section actions for <name>**, then choose **Duplicate section**. The dialog supports copying tasks and copying section summaries/planning checks independently. A section can be copied with settings and no tasks. The new section is inserted after its source; following active section positions are shifted transactionally.

Task selection comes from the full server source, not loaded/filter-visible rows. Only active tasks are included. Selecting subtasks includes their complete active subtree, even when a descendant belongs to another section; copied section tasks are placed in the new section. Disconnected cycles, over-limit selections and unsupported sources fail instead of silently omitting work. Turning subtasks off deliberately excludes descendants of selected roots.

**Copy section summaries and planning checks** needs the current `fields.manage` capability (owner/administrator today). Ordinary task copying still uses `task.edit`. The optional settings copy includes only the source section's header-widget rule and section-targeted balance checks. It assigns new section/widget/measure/check identities. Existing field IDs, people, date ranges, project-date references, capacity choices and manual overrides stay literal; review them before creating the copy. A copied section called Maya does not infer or change the selected person. Project-wide presence/overdue checks and unrelated section/assignee rules are not duplicated.

Aggregate-settings and planning-check revisions remain independent. Changing either after preview makes that preview stale. Existing limits (including four widgets/group, 100 widget groups, 50 planning rules and distinct-field limits) remain enforced. An oversized settings copy rolls back the new section, order changes and all new tasks rather than leaving a partial copy.

## Duplication boundaries and consistency

- Same project only. The task request includes the currently viewed project; linked rows cannot silently create work in another home project.
- Ordinary workspace tasks only. Meeting tasks and sections containing active linked rows are explicitly unsupported when copying those tasks; they are not converted or skipped.
- At most **100 new tasks** per operation; at most **5,000 source-project tasks** are inspected. Overflow is an error, never a truncated tree. At most 200 ordinary field IDs can be selected.
- The preview is an authorized consistent read with no writes, automatic freezes or generated task identities. It returns counts, available fields, carried settings and a semantic source digest.
- Execution reauthorizes under the workspace barrier before receipt replay, compares the digest, runs the typed planning guard and same-transaction recurrence census, then checks the source again before creating anything. New source work from prerequisite materialization requires another preview.
- Task, participant, field-definition/value and section/settings revisions remain separate. Zero, false, typed null and absent rows remain distinct. Manual locks, deadlines/change limits, current member/tag/option validity and shared task-status policy remain enforced.
- One idempotent command creates the whole copy. A confirmed receipt returns the same IDs after a lost response, even if the source later changes or is archived, subject to current authorization. Unexpected failures roll back all proposed rows, audit/outbox and receipts. Existing tagged guard-rejection semantics can commit only prerequisites and their rejection receipt.
- No migration is required for this slice. It reuses existing task, field, settings, audit and idempotency storage.

HTTP endpoints are `POST /api/v1/workspaces/:workspaceId/tasks/:sourceId/duplicate-preview` and `/duplicate`, with corresponding `/sections/:sourceId/…` routes. Preview needs no Idempotency-Key. Writes require one plus `expectedSourceVersion`; clients choose copy options/field IDs and cannot supply copied rows or task identities.

## Reports: availability and work types by person

The existing project Reports route remains `/app/w/:workspaceId/projects/:projectId/reports`.

**Available hours period** follows saved explicit capacity configuration when present, otherwise optional project dates. It does not force a week or invent dates. The choices include no period, project dates, task-filter dates and custom dates (at most 366 inclusive days). Availability scope and task-total/date scope are visibly separate: changing availability does not filter tasks, edit the saved report, change a person's schedule or modify leave settings. No period, unavailable schedule, no assignee and unselected people have distinct unavailable states.

A temporary availability override disables capturing a new initial snapshot with an explanation. Existing historical snapshots remain selectable and retain their saved query/source authority. Existing ratio guards require matching people, dates and known schedules; recorded task values are not proof of attendance.

**Work types by person** uses the existing ordinary single-select category chooser and saved option IDs/colors. Actual time comes from the configured ordinary comparison field, not a field name. Cards show six people per page, search, and Name/Actual time sort. Per-person category aggregates are authoritative server sums with coverage, not sums of loaded task rows. Only the visible page is queried, reads are cancellable, and those reads omit capacity. People with capacity but no tasks remain visible.

Unassigned, Uncategorized, unknown values, explicit zero, no tasks, negative values and inconsistent results stay distinct. Negative/inconsistent distributions do not show a misleading pie. Historical snapshot view omits live category cards. A failed person/card query hides its stale cached result rather than presenting it as current.

## Refresh behavior

A successful Planning Checks assessment now stays visible during a background read for the same actor/workspace/project/settings revision. Its confirmed colors, group counts and overdue indicators are replaced only when a new authoritative assessment arrives. A failed read, lost authority, changed revision or new project clears that result. This preserves useful feedback while an ordinary field edit triggers assessment refresh; it does not show old results for a different scope.

Column totals, group totals and section header widgets similarly retain a successful result only for the same exact query during refresh. First load keeps its placeholder. New filters, errors, stale access or a settings-revision mismatch cannot reuse that old result. These are display-stability changes, not optimistic invented sums.

The live-refresh catch-up also has a narrowly owned **read-presentation lease**. A previously confirmed analytical decoration can stay visible while that catch-up rechecks authority metadata only when an already applied head and the fresh validated target head agree on actor, workspace, membership ID/revision, role and permission epoch. The change sequence may advance; the authority tuple must not. Identity, workspace, memberships and participating project queries must all be clean at entry. The lease captures their exact Query objects, metadata fingerprints and the owned in-flight reads. It is limited to the same actor/workspace/project and unchanged settings/query scope.

This lease grants no editing or reading authority. The strict access helper is unchanged: editors, mutations, duplication previews/writes and review actions remain disabled while their authority reads are stale or in flight. Retained check indicators can stay visible, but their review buttons are disabled and their callbacks still check strict access. The lease never enables a new query or opens an editor. Catch-up still performs every required reader and advances the applied head only after the ordinary refresh succeeds.

There is no grace for an initial load, absent prior applied head, changed permissions, changed metadata, errors, lost/changed Query identity, aborted/unsafe refresh, explicit recovery or a non-owned external read/invalidation. An authority/head query with a nonzero fetch-failure count, a paused fetch, or an invalidated head also revokes the lease, even if its cached data and promise identity remain unchanged. A later successful retry or network resume cannot revive that revoked generation. Those conditions revoke retention and use the existing neutral/error/recovery behavior. This is not a general stale-data exception, a cached membership grant or a guarantee that every possible screen transition has no flicker.

When Planning Checks are disabled in the saved configuration, they no longer automatically query an assessment. Owners can still open the settings editor to configure or enable them. This avoids an unnecessary assessment read; settings and current authority remain required.

Duplication keeps its independent preview/command state. A confirmed stale-source rejection disables creating from the obsolete preview and offers **Refresh preview**; the refreshed digest is required before the next creation. Pending and unknown outcomes keep the form locked, block cancellation and offer only an explicit retry of the identical request and Idempotency-Key. A 503 response does not permit a changed request or a new copy.
