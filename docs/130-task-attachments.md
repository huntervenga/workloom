# Вложения задач: настройка и реализация

27 октября 2026 года. Реализация согласованного дизайна из [129](129-task-attachments-design.md). Изменения находятся в исходниках; рабочая база, запущенное приложение и production в ходе реализации не изменялись.

## Что доступно

В панели сохранённой задачи появился блок **Attachments**: выбор одного или нескольких файлов, прогресс, отмена, повтор, скачивание и удаление. Максимум **5 файлов на каноническую задачу**, каждый до **50 000 000 байт**. Подзадачи имеют собственный лимит. Резервируемые и загружаемые файлы уже занимают место; конкурентные запросы проверяются внутри барьера записи workspace и ограничены уникальным индексом PostgreSQL.

Байты идут только **браузер → API Workloom → приватный S3**. Используются AWS SDK v3 `@aws-sdk/client-s3` и `@aws-sdk/s3-request-presigner`, без отдельного Google SDK. Поддерживается настройка S3 endpoint, региона и path-style addressing. Браузер не получает upload URL или ключи хранилища.

Без настроек S3 сервер запускается, остальные возможности продолжают работать, а кнопка прикрепления заблокирована с пояснением. `GET /api/v1/features` после авторизации сообщает `features.taskAttachments`: `enabled`, безопасную причину отключения, лимиты и TTL. Это проверка конфигурации, а не доступности облака. Неверные действующие ключи или сбой провайдера проявляются при операции с файлом, а не при входе в приложение. Частичные или некорректные параметры отключают функцию без падения сервера.

## Счётчик в списках задач

Справа от названия задачи в таблице проекта (включая подзадачи и связанные строки) и в My Tasks показываются скрепка и число готовых вложений. При нуле значок скрыт. Pending/uploading/failed/expired/deleted не учитываются. После загрузки или удаления обновляется семейство запросов задач текущего пользователя/workspace, без перезагрузки страницы.

`attachmentCount` приходит вместе с Task DTO: один группирующий запрос PostgreSQL на пакет задач, с ограничением workspace и выбранных task ID, без запроса списка файлов для каждой строки и без обращения к S3. Поле необязательное без значения по умолчанию для совместимости с прежними сохранёнными ответами. Используется существующая таблица 0035; новая миграция не нужна.

Проверки этого дополнения: полная приватная сборка и root TypeScript прошли, UI **26/4**, PostgreSQL **8/1**, Chromium **3 сценария** (светлая/тёмная тема на 1440×900 и мобильная ширина 390×844). Проверены ненулевой/нулевой счётчик, расположение после названия на той же строке, сохранение редактирования названия, обновление после загрузки/удаления, готовность файлов, My Tasks и изоляция workspace. Линтер изменённых файлов, границы модулей и локализация прошли. Просмотрен десктопный тёмный скриншот; данные браузера синтетические, PostgreSQL отдельный временный, реальная база и S3 не изменялись. Приватные серверы остановлены. Логи: `/tmp/workloom-attachment-count-*.log`. Полный набор тестов и production не проверялись.

## Просмотр изображений и видео

В готовом вложении нажмите имя файла или кнопку с глазом: откроется модальное окно поверх панели задачи. Изображение вписывается в окно, видео использует встроенные элементы управления браузера без автозапуска. Escape, крестик и клик по затемнённой области закрывают просмотр; сама задача остаётся открытой. При закрытии видео останавливается, его источник освобождается. Скачивание доступно отдельно и внутри окна.

Поддерживаются JPG/JPEG/JFIF, PNG/APNG, GIF, WebP, AVIF, BMP, ICO; видео MP4/M4V, WebM, OGV, MOV. Возможность декодирования зависит от браузера и кодеков: при ошибке окно предлагает повторить запрос или скачать файл. Расширение задаёт только подсказку декодеру, не является проверкой содержимого. HTML, SVG, PDF и другие форматы доступны для скачивания; iframe/object и выполнение содержимого не используются.

`POST …/attachments/:id/preview-url` сначала выполняет ту же проверку текущего доступа и состояния `ready`, что и скачивание. Сервер сам определяет разрешённый тип, клиент не передаёт MIME. Затем AWS SDK подписывает GET с `response-content-type`, `response-content-disposition=inline` и `response-cache-control=private,no-store`. Это [переопределение заголовков ответа S3 GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html), а не изменение объекта: **уже загруженные файлы работают без перезаливки и новой миграции**. При обновлении только этой возможности достаточно обычного перезапуска `npm run dev`; миграция 0035 нужна для исходной функции вложений.

Preview и download используют раздельные ключи общего ограниченного кеша; TTL и проверка доступа перед кешем одинаковы. Ответ просмотра привязан к ID вложения и допустимой паре kind/MIME. Ссылка остаётся только в состоянии открытого окна, запрос отменяется при закрытии; поздние ответы игнорируются. Отзыв доступа при обновлении списка также убирает открытый просмотр. Уже выданные bearer-ссылки сохраняют обычное ограничение отзыва до истечения TTL.

Для страниц API добавлена директива [CSP `media-src`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/media-src): HTTPS-медиа разрешены аналогично существующим HTTPS-изображениям. В локальном режиме дополнительно разрешены HTTP `127.0.0.1` и `localhost` для S3-эмуляторов; для браузерного просмотра локального хранилища используйте эти адреса. Ограничения scripts/connect/object не ослаблены. Без настроек хранилища кнопки просмотра и скачивания остаются отключены.

## Локальный запуск и включение

Нужен Node.js 24. После получения изменений:

```bash
npm install
npm run db:migrate
npm run dev
```

Миграция **0035_task_attachments** добавляет `task_attachments` и `attachment_storage_objects`. Она нужна и при выключенном S3: приложение читает метаданные вложений независимо от доступности хранилища. Команды здесь выполняются пользователем против его выбранного `DATABASE_URL`; реализация не запускала миграцию на рабочей базе.

Для включения добавьте в серверное окружение или локальный `.env`:

```dotenv
ATTACHMENTS_S3_BUCKET=workloom-private
ATTACHMENTS_S3_REGION=us-east-1
AWS_ACCESS_KEY_ID=<access-key>
AWS_SECRET_ACCESS_KEY=<secret-key>

# Для S3-совместимого провайдера; для AWS этот параметр обычно не нужен.
ATTACHMENTS_S3_ENDPOINT=https://storage.example.com
ATTACHMENTS_S3_FORCE_PATH_STYLE=true
ATTACHMENTS_SIGNED_URL_TTL_SECONDS=3600
# AWS_SESSION_TOKEN=<optional-session-token>
```

Указывайте регион, который требует выбранный провайдер. Endpoint — origin без пути bucket, query, логина или пароля. В hosted-режиме разрешён HTTPS; для локального тестового хранилища также разрешён HTTP на `localhost`, `127.0.0.1` или `::1`. После изменения окружения перезапустите API. Значения по умолчанию: стандартный AWS endpoint, `forcePathStyle=false`, TTL 3600 секунд. Оба ключа задаются явно; автоматического обращения к instance metadata/цепочке credentials нет.

Bucket необходимо создать приватным; Workloom не создаёт bucket, не меняет его policy и не проверяет публичность при старте. Серверному principal нужны PutObject, GetObject/HeadObject и DeleteObject в префиксе `attachments/`; при versioning также права чтения/удаления конкретных версий. Публичный доступ не требуется. У GCS можно использовать S3-совместимый XML endpoint и HMAC credentials; service-account JSON сюда не подставляется. Конкретный провайдер должен поддерживать используемые операции и Signature V4.

Загрузка через наш API не требует CORS для bucket или расширения браузерного `connect-src`. У reverse proxy должны быть допустимы PUT и тело 50 МБ, а тайм-ауты должны позволять загрузить файл. Обычные JSON-маршруты сохраняют лимит 16 KiB; только бинарный маршрут работает с большим потоком. Смена bucket/endpoint/region не переносит старые объекты: их storage ID сохраняется, операция против другого хранилища отклоняется. Для переноса существующих файлов нужен отдельный операторский процесс.

## Авторизация и подписанные ссылки

Список и получение ссылки требуют действующей сессии и текущего `task.read`. Прикрепление/удаление требуют `task.edit`; архив задачи или основного проекта блокирует изменение, но сохраняет чтение файлов. Поддерживается текущая модель задач `visibility=workspace`. Изменения не открывают private-задачи и не добавляют файловые операции в public API/MCP.

Перед загрузкой и после завершения потока проверяются actor и права. Привязка к ожидаемому actor защищает от сохранения после переключения аккаунта. Загрузка становится `ready` только после успешной записи объекта и повторной авторизации. После отмены, удаления, истечения попытки или отзыва прав позднее завершение не публикует файл.

Signed GET действует **1 час по умолчанию**, настраивается от 60 до 7200 секунд. Уже выданную ссылку можно передать другому человеку; до истечения срока он сможет скачать файл без сессии Workloom. Отзыв доступа запрещает получение новых ссылок, но не отзывает уже выданную. У временных credentials ссылка может перестать работать раньше TTL.

Подписание выполняется локально AWS SDK, без отдельного сетевого запроса к S3. Дополнительно есть **ограниченный кеш в памяти каждого API-процесса: 256 записей, до 5 минут повторного использования**, и не позднее чем за 30 секунд до истечения URL. Ключ учитывает объект, версию, имя и режим ответа (скачивание или MIME предпросмотра). **Текущая авторизация выполняется перед каждым обращением к кешу.** Удаление инвалидирует кеш. В localStorage, БД и Redis ссылки не записываются; ответы API помечены `private, no-store`.

Объекты получают `Content-Type: application/octet-stream`, безопасный `Content-Disposition: attachment` и `Cache-Control: private, no-store`. Обычная кнопка скачивания сохраняет эти заголовки; отдельный предпросмотр изображений и видео использует подписанные переопределения, описанные выше. Встроенного исполнения HTML нет. Антивирусное сканирование и общая квота workspace пока отсутствуют.

### Будущая доработка: общий кеш подписанных ссылок

При работе нескольких экземпляров API нужно обеспечить совместное использование кеша или согласованную инвалидацию между ними. Сейчас кеш локален для каждого процесса; распределённая схема **ещё не реализована**. Предусмотреть один из вариантов:

- Хранить подписанные ссылки непосредственно в общем Redis с ограниченным TTL и едиными ключами кеша.
- Сохранить локальные кеши и рассылать события инвалидации через Redis или другой брокер сообщений. Событие должно доходить до каждого экземпляра API; отдельно предусмотреть восстановление после пропущенных событий и переподключения.

В обоих вариантах сохранить проверку текущих прав перед выдачей ссылки, разделение просмотра и скачивания и запас до истечения URL. Очистка распределённого кеша не отзывает уже выданные S3-ссылки. Недоступность Redis/брокера не должна приводить к падению API; поведение при сбое нужно определить при реализации с учётом опциональности функции вложений.

## Протокол и восстановление

Префикс `T = /api/v1/workspaces/:workspaceId/tasks/:taskId`:

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `T/attachments` | Активные вложения, свободные места, разрешённые действия |
| POST | `T/attachments` | Резервирование: `fileName`, `sizeBytes`, `expectedActorId`; `Idempotency-Key` обязателен |
| GET | `T/attachments/:id` | Текущее состояние попытки после неоднозначного ответа |
| PUT | `T/attachments/:id/content` | Бинарный поток `application/octet-stream`; заголовок `X-Workloom-Expected-Actor` |
| POST | `T/attachments/:id/download-url` | Проверка текущего доступа и выдача временной ссылки |
| POST | `T/attachments/:id/preview-url` | Та же проверка доступа, подписанная inline-ссылка для разрешённых изображений и видео; 415 для других типов |
| DELETE | `T/attachments/:id` | `expectedRevision`, `expectedActorId`, `Idempotency-Key`; освобождает слот и планирует очистку |

Для каждого файла создаётся новая попытка с новым непредсказуемым ключом объекта. PUT в готовый объект не повторяется. Single PUT работает с backpressure и подсчётом реальных байтов, проверяет совпадение с зарезервированным размером, вычисляет SHA-256. Автоматические повторы AWS SDK для невоспроизводимого входящего потока отключены. Multipart upload и `@aws-sdk/lib-storage` не используются.

Попытка действует 15 минут. На один процесс допускаются 8 одновременных загрузок, не более двух на actor; резервирования ограничены 30 запросами в минуту на actor. Эти транспортные лимиты действуют на процесс, лимит пяти файлов обеспечивается общей БД. Файл при перезагрузке страницы не сохраняется и автоматически не возобновляется с прерванного байта. Повтор резервирования с тем же ключом возвращает актуальное состояние, включая `ready`, если успешный ответ потерялся. Неуспешная или истёкшая попытка повторяется с новым ключом объекта.

`attachment_storage_objects` создаётся **до** сетевого PUT. Эта таблица намеренно не имеет FK на задачу, проект или workspace: задание удаления переживает окончательное удаление задачи/проекта. Готовый объект не имеет даты очистки. Удаление готового файла назначает очистку сразу; незавершённого — после upload deadline и пяти минут запаса. Архивирование файлы не удаляет. Независимые копии задач не копируют вложения.

При настроенном S3 API автоматически обрабатывает очистку при старте и раз в минуту, до 10 объектов за проход. Lease и `SKIP LOCKED` разделяют работу реплик. Неуспешное удаление откладывается на 5 минут; после успешного удаления ключ перепроверяется каждый час в течение 24 часов после write deadline, чтобы подобрать позднюю запись. Затем запись остаётся как неактивный tombstone. После перезапуска задания восстанавливаются из БД; отдельный worker или cron для этого выпуска не нужен. При выключенном S3 очистка ожидает повторного включения соответствующего хранилища.

При известном version ID удаляется конкретная версия. Если результат PUT был неоднозначным, HEAD помогает найти её по уникальному ключу. Очистка не обходит bucket целиком. Политики retention, object lock, soft delete и резервные копии провайдера могут сохранять данные после удаления в Workloom. Гарантия очистки ограничена доступностью соответствующего хранилища и указанным окном поздней записи; при изменении конфигурации старое хранилище требует отдельного обслуживания.

## Проверки исходной реализации вложений

Проверки выполнялись на Node.js 24.19.0 в отдельной копии `/tmp/workloom-attachments-check.mvdle_dp` и в собственном временном PostgreSQL 17. Рабочий `DATABASE_URL` и реальные ключи S3 не использовались.

- Полная сборка прошла. После последних точечных правок отдельно пересобраны domain и web; компиляция остальных workspace ранее прошла на том же исходном коде этих workspace.
- Проверка типов всех workspace прошла. Ошибку слишком узкого типа actor ID в новой тестовой обвязке исправили; финальная проверка root TypeScript прошла отдельно.
- Unit/HTTP/config: **92 теста в 4 файлах** прошли. В том числе проверены отсутствие ключей, безопасная конфигурация, повторная авторизация перед кешем, смена сессии после PUT, точный потоковый предел 50 000 000 байт и отказ на 50 000 001 байте.
- PostgreSQL: **7 тестов в 1 файле** прошли, включая свежую миграцию, конкурентные 8 запросов/5 слотов, текущие права при повторе, отмену/истечение, lease реплик, сохранение очистки после purge и настоящий AWS SDK PUT через HTTP в локальный тестовый объектный сервер. Это проверка реального транспорта SDK, но не облачного провайдера.
- Новая UI-функция: **6 тестов в 1 файле** прошли, включая отключённый S3, загрузку, ограничения выбора, повтор после потерянного ответа, отмену при закрытии и скрытие данных после отзыва доступа.
- Расширенный набор панели задач: **50 из 52 тестов прошли**. Два старых теста `TaskDrawerAutosave` находят одновременно поле и заголовок колонки с подписью `Due date`. Оба сбоя повторены с исходным `TaskDrawer.tsx` до этой реализации; тесты не ослаблялись. Эти шесть новых UI-тестов входят в указанные 52, количества не суммируются.
- Линтер всех изменённых исходников, проверка границ модулей и общий аудит локализации прошли. Полный `npm run check` не объявляется зелёным: общий ESLint также проверяет уже существующие скомпилированные JS в `apps/web/public/assets` и `public/theme-init.js`, где есть прежние нарушения.

Ранние неуспешные запуски сохранены в `/tmp/workloom-attachments-*.log` там, где не заменены результатом повторной проверки; отдельный baseline UI — `workloom-attachments-web-baseline.log`. Первоначальные проблемы тестовой обвязки (пустая seed-база без задачи и обязательный `revoked_at`) исправлены; итоговые PostgreSQL-проверки не пропущены. Также исправлены найденные проверками подстановки имени в UI и истечение резервирования до фоновой очистки.

Проверка реального облачного bucket, его IAM, production reverse proxy, визуальная проверка в нативном браузере и работа в авторизованном production-браузере не выполнялись. Полный набор тестов репозитория не запускался. Вложение не требует доступа к Railway для работы локально, но настройку bucket и окружения hosted API выполняет владелец соответствующей инфраструктуры.

- **32 unit/HTTP-теста в 3 файлах** прошли: повторная авторизация перед выдачей preview URL, выключенное хранилище, привязка к вложению, настоящая локальная подпись AWS SDK с response overrides и version ID, раздельный кеш скачивания/просмотра, отказ для HTML/SVG/PDF и политика CSP. Сетевые обращения к облачному S3 в этих проверках не выполнялись.
- **24 UI/client-теста в 3 файлах** прошли: открытие по имени/кнопке, read-only доступ, отключённый S3, ошибка декодирования и повтор, отозванный доступ, отмена/игнорирование позднего ответа, остановка видео, повторный запуск эффекта React StrictMode, безопасная схема ответа и возврат фокуса.
- Нативный Chromium: **3 сценария** (1440×900 light/dark, 390×844 dark) прошли на собранном приложении с синтетическими API-ответами и отдельным локальным media-сервером с Range/206. Проверены реальные PNG и WebM, декодирование, проигрывание и перемотка видео, геометрия окна, Escape/крестик/фон, сохранение открытой задачи и освобождение video src. Ошибок JavaScript/CSP в финальном прогоне нет. Проверка физического телефона, других браузеров и реальной облачной ссылки сюда не входит. Просмотрены скриншоты мобильного изображения и десктопного видео.
- Линтер изменённых исходников, проверка границ и аудит локализации прошли. Полный набор тестов и глобальный `npm run check` повторно не запускались; ограничения исходного глобального lint выше остаются отдельными.

При браузерной проверке обнаружен и исправлен расчёт CSP-хеша inline-скриптов для CRLF: браузер нормализует переводы строк перед вычислением хеша, сервер теперь делает то же. Добавлен отдельный тест CRLF/lone CR. Первые прогоны также выявили ошибки новых тестовых селекторов/типов, исправленные до финального запуска; исходный 5-секундный HTTP timeout повторно проверен последовательно с бюджетом 15 секунд. Первый мобильный сценарий не закрыл только что смонтированное окно немедленным кликом; финальная проверка ожидает декодированное изображение перед кликом по фону. Логи начальных и итоговых прогонов сохранены как `/tmp/workloom-preview-*.log`, финальный браузерный — `workloom-preview-native-backdrop.log`.

Для этой доработки не изменялись `.env`, рабочие данные, объекты реального S3 или запущенные основные сервисы; приватные браузерные серверы остановлены. Production и браузер с настоящей пользовательской сессией не проверялись.
