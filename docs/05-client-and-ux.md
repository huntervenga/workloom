# Клиент и пользовательские сценарии

Статус: план реализации от 16 октября 2026 года. Локально проверены P0 (shell, workspace и участники) и ограниченный P1a (таблица задач проекта, карточка, дочерняя задача, фильтры по участнику и поиску, просмотр на mobile), доказательства — в [11](11-implementation-progress.md); остальные сценарии ниже, включая полный P1, — будущий план. Основа — [продуктовая спецификация](01-product-spec.md); архитектурные границы — [02](02-architecture.md), значения и инварианты — [03](03-domain-and-data.md), контракты команд — [04](04-api-and-integrations.md).

## 1. Что пользователь должен получить

Первый локальный каркас P0 открывает shell и пространство из базы. Начиная с P1 рабочий экран — таблица задач, а с P2 — таблица выбранной недели. Сотрудник добавляет задачи, оценивает работу, участвует в общих встречах, вносит факт и видит отчёт без настройки сложной системы. Владелец получает отдельные экраны полей, периодов, правил и доступа. Пустое пространство предлагает шаблон «Недельное планирование по часам», а не обязательный многошаговый onboarding.

Основная проверка: за одну неделю команда из 5–7 человек выполняет привычную работу без параллельного списка в Asana. Таблица, карточка, граф и отчёт показывают одни сущности. Повторное отображение общей задачи в нескольких группах не создаёт копию задачи или времени.

Первые локальные сборки используют вымышленных сотрудников и переключатель действующего пользователя. Он выбирает actor для серверной проверки прав; скрытие кнопок не является контролем доступа. Переключатель отсутствует в production-сборке и защищённой сборке пилота. Допуск реальных людей и данных определяется [архитектурой](02-architecture.md) и [эксплуатацией](08-railway-and-operations.md).

## 2. Стек и визуальная система

- React + TypeScript, сборка Vite, React Router для навигации; npm workspaces монорепы. API отдаёт production SPA и API с одного origin. Точные совместимые версии фиксируются lockfile при создании приложения.
- Tailwind и небольшая собственная библиотека компонентов `packages/ui`: кнопки, формы, меню, tooltip, popover, dialog, drawer, badges, таблица и пустые состояния.
- Визуальный язык Thermis: Inter, фон `#f8fafc`, текст `#0f172a`, borders `#e2e8f0`, белые поверхности, indigo `#6366f1` для главных действий, умеренная плотность, компактная навигация. Токены выделяются в CSS variables; тёмная тема не блокирует первую рабочую версию.
- Серверные данные — TanStack Query; модель колонок и строк — TanStack Table; виртуализация подключается отдельно через TanStack Virtual. Табличная библиотека сама не реализует сценарий редактирования или доменные правила.
- Диаграммы отчётов — Recharts с обязательной табличной альтернативой; граф зависимостей — React Flow с отдельным адаптером и небольшим layout-движком после технической проверки.
- Gantt начинается с ограниченной шкалы дней/недель и полос задач. До выбора библиотеки провести короткую проверку лицензии, accessibility, контролируемого drag и возможности показать baseline; платные функции не становятся скрытым требованием сборки.
- Radix primitives для доступных popover/dialog, Lucide для иконок, dnd-kit для таблицы; совместимость с виртуализацией проверяется отдельным прототипом. Zustand допустим для сложного временного selection/focus state, но не дублирует Query cache. Не переносить весь dependency tree Thermis и не ссылаться на его исходники во время сборки.

Локальные исходники Thermis подтверждают React 19, Vite, Tailwind 4, React Router 7, TanStack Query 5, Zustand 5, Radix Dialog, dnd-kit, Recharts 3 и Lucide на момент исследования. Это ориентир совместимости и поведения, а не требование слепо закрепить все те же версии.

Официальные ориентиры, проверенные 16 октября 2026: [виртуализация TanStack Table](https://tanstack.com/table/latest/docs/framework/react/guide/virtualization), [React Flow API](https://reactflow.dev/api-reference), [Recharts API](https://recharts.github.io/en-US/api/). При установке проверяются конкретные версии и лицензии; приведённые названия — выбор семейства инструментов.

## 3. Структура клиентского кода

```text
apps/web/src/
  app/                  # providers, router, bootstrap, error boundaries
  routes/               # route loaders/pages, без доменных вычислений
  features/
    workspace/          # выбор пространства, участники, capabilities
    tasks/              # создание, карточка, связи, комментарии, материалы
    task-table/         # row model, focus, selection, clipboard, editing
    fields/             # редакторы значений, определения и политики
    views/              # фильтры, сортировка, группировка, сохранённые виды
    planning/           # неделя, личная фиксация, baseline, корректировки
    worklogs/           # мои часы, точность периода, версии записей
    meetings/           # серии, исключения, присутствие, начисление
    reports/            # конфигурация, run, графики, drilldown
    dependencies/       # граф, список связей, Gantt adapter
    imports/            # preview, mapping, ошибки, результаты импорта
  lib/                  # api transport, query keys, locale/date adapters
  dev/                  # fixture identity и экран данных; только local-dev
packages/ui/src/        # визуальные primitives, tokens; без API/workspace logic
packages/contracts/    # DTO/schema/enums/errors; без React и persistence
```

`packages/ui` не импортирует features приложения. Feature импортирует публичный API соседней feature, а не её внутренние файлы. UI не импортирует `packages/db`, ORM, серверные переменные окружения или код привилегированных доменных команд. Общие контракты используют стабильные ID, discriminated unions типов полей и машинные коды ошибок.

## 4. Навигация и состояние

| Экран | Содержание и сохраняемое состояние |
| --- | --- |
| Мои задачи | Доступные задачи с участием текущего человека, личные часы, неделя |
| Проект / неделя | Table, Gantt, Dependencies, Reports; выбранный период и вид |
| Карточка задачи | Открывается drawer поверх списка; URL позволяет открыть напрямую |
| История недели | Исходный план, изменения, закрытые версии отчётов |
| Настройки | Поля, статусы, категории, участники, правила; только доступные действия |

Маршруты содержат workspace/project ID; query string содержит период, view ID и открытую task ID. Черновики фильтров не превращаются в сохранённое общее представление без явного действия. Название задачи, записи времени и приватные данные не помещаются в URL или диагностическую телеметрию.

Разделение состояния:

1. Серверное: задачи, периоды, права, definitions, baseline, worklogs, report runs — Query cache.
2. Навигационное: workspace, период, view, открытая карточка — URL.
3. Временное: фокус, выделение, открытый редактор, несохранённый ввод — local reducer/context.
4. Предпочтения: плотность и ширина боковой панели — локально; общие виды — сервер; личные виды принадлежат пользователю.

Query keys включают workspace, actor/access context, период и нормализованную конфигурацию выборки. При смене actor/workspace, logout или отзыве membership незавершённые запросы отменяются, данные прошлого контекста удаляются, открытые карточки закрываются. Не показывать stale приватную карточку в качестве placeholder для другого пользователя.

API возвращает актуальные версии сущностей и разрешённые действия с причинами ограничения. Клиент использует их для UX и всегда готов к отказу команды: между загрузкой и записью может наступить cutoff или измениться доступ. Серверные часы и состояние периода имеют приоритет перед часами устройства.

## 5. Таблица: контракт взаимодействия

Колонки первой недели: задача, исполнители, срок, теги, Hours Est, Hours Fact, приоритет. Пользователь может переставлять, скрывать и менять ширину колонок; имя остаётся закреплённым. Owner может добавлять definitions полей; Member настраивает собственный вид в пределах прав.

Обязательные состояния строки: обычная задача, подзадача, заголовок секции, групповая сумма, закреплённая встреча, строка создания. У каждой визуальной строки свой row ID; ссылки на задачу и запись периода сохраняются отдельно. Для группы «по человеку» одна общая задача имеет несколько visual rows, но mutation адресует исходную задачу либо конкретное участие.

| Действие | Поведение |
| --- | --- |
| Enter в ячейке | Начать редактирование; в редакторе подтвердить, если тип не многострочный |
| Tab / Shift+Tab | Завершить допустимый ввод и перейти к следующей/предыдущей доступной ячейке |
| Escape | Отменить локальный ввод или закрыть верхний popover; не отправлять mutation |
| Стрелки вне редактора | Навигация по ячейкам; дерево раскрывается отдельным доступным control |
| Enter в строке создания | Создать задачу и оставить следующую строку готовой к вводу |
| Несколько выбранных строк | Toolbar допустимых массовых действий с числом выбранных задач |
| Paste | Сначала разобрать TSV, проверить типы и показать preview для массового изменения |
| Drag | Меняет ручной порядок/секцию; в сортированном виде предлагает переключиться на ручной порядок |

Фокус хранится как `{rowId, fieldId}`, не как индекс DOM. При виртуализации переход сначала прокручивает нужную строку, затем переводит фокус; активный редактор закрепляется на время ввода. Не перемонтировать input из-за background refetch. Сворачивание родителя возвращает фокус в его строку.

Для вставки названий достаточно одного столбца текста. Вставка прямоугольного диапазона сопоставляется с видимыми колонками, перечисляет неподдерживаемые/locked cells и не превращает незнакомый select label в новый option без разрешённого действия. Значение пустой ячейки и явный ноль различаются. Пользователь подтверждает пакет; API возвращает результат по строкам и состояние атомарности согласно контракту, UI не предполагает успех всего пакета.

Для больших выборок сервер выполняет фильтрацию, сортировку и агрегации; интерфейс не вычисляет общий итог по случайно загруженной странице. Запросы раскрытого дерева/групп сохраняют устойчивый cursor и tie-breaker. Если сервер ограничил выборку, это явно указано. Начальный performance dataset и критерии описываются в [проверке](07-verification-and-pilot.md).

Групповая сумма по человеку содержит его индивидуальные часы. Общий итог считает каждую запись времени один раз, включая встречи, закреплённые и одновременно видимые ниже. Rollup родителя отображается как вычисляемый: сумма родителя и детей не складывается второй раз. Суммы задаёт серверная проекция.

## 6. Редакторы и дополнительные поля

Реестр UI типов сопоставляет `field.type` с render, editor, parse, format, фильтрами и допустимыми aggregate controls. Метаданные definition включают ID, тип, scope (`task` или период), единицы, options, ограничения, history/baseline flags, revision. Метаданные доступа значения приходят отдельно и зависят от задачи, периода и actor.

| Тип | Редактор и существенное правило |
| --- | --- |
| Текст / URL | Inline input; ссылки проверяются, открываются безопасно, произвольный HTML не исполняется |
| Число / длительность | Понятная ошибка единиц; часы вводятся десятичным числом или `1:30`, на API — целые единицы времени |
| Дата | Date picker; date-only не конвертируется в UTC midnight со сдвигом дня |
| Single / multi select | Поиск вариантов по label, сохранение option ID; архивные варианты видны в истории |
| Пользователь | Только допустимые members; task participants — специализированный редактор, не произвольное поле |
| Checkbox | Есть явное пустое значение, если definition допускает его; `false` не трактуется как отсутствие |

Локализованный parser принимает `1,5` и `1.5` как полтора часа при документированных правилах. В неоднозначном формате показывает пример; не делает тихого округления или превращения пустого в 0. Изменение definition type с существующими значениями требует серверной миграции/нового поля, а не простой смены иконки.

Настройка поля открывает имя, тип, options, обязательность, историю, включение в baseline и блокировки. Для каждой опции даётся короткое объяснение области действия. При выключении истории показывается дата, с которой новые события не собираются; сохранённая история остаётся. Системные инварианты оценок/времени не отключаются универсальным checkbox.

Locked cell показывает замок и причину: «План зафиксирован 19 октября, 10:00» либо «Нет права изменять». По клику доступны история и, если разрешено, «Оформить корректировку». Скрытая колонка не обозначается как защищённая от чтения.

## 7. Карточка задачи, участники и структура работы

Drawer содержит название и статус; проект/секцию; исполнителей и ответственного; даты; описание; оценки и факт; зависимости; подзадачи; custom fields; материалы; комментарии; историю. Редко используемые поля свернуты. Можно открыть карточку полноценной страницей, сохранив ту же feature.

Ответственный за результат, участник работы и наблюдатель показаны раздельно. Добавление участника обычной задачи не умножает общий бюджет: drawer предлагает распределить имеющийся план либо оставить часть «не распределено». Нераспределённые часы остаются в командном плане и видны в качестве данных, но не приписываются случайному человеку. План встречи устроен иначе: длительность предлагается каждому участнику.

Операции «Разбить работу», «Заменить задачу», «Перенести остаток» используют отдельные формы с preview исходного обязательства, новой структуры и распределения бюджета. Обычный drag подзадачи не переопределяет происхождение пакета работ. «Архивировать» поясняет, что задача остаётся в зафиксированной истории; скрытой очистки baseline нет.

При закрытии задачи с требованием учёта времени появляется компактный ввод факта или действие «0 часов, работа не требовалась». Для общей задачи пользователю не предлагается тихо подтвердить чужие часы; показываются собственные и ещё не подтверждённые записи. Сервер определяет, какие условия действительно блокируют завершение.

Комментарии поддерживают текст, ссылки и упоминания доступных участников. Возможности файловых вложений согласуются с [объёмом реализации](06-implementation-plan.md); ссылки на запись и summary обязательны независимо от файлового хранилища. Контент выводится после очистки, без выполнения встроенных script/HTML.

## 8. Недельный план и история

Header недели показывает диапазон дат, timezone, состояние «Планирование / План зафиксирован / Факт закрыт», срок фиксации, личный статус и доступные действия. Неделя задаётся ID и датами периода, а не только номером ISO-недели.

Фиксация личного плана открывает preview: выбранные задачи и индивидуальные часы, незаполненные оценки, участники встреч, добавленная работа. Фиксация всего периода использует серверный preview/revision; изменение данных во время подтверждения требует актуализации. UI не формирует authoritative snapshot из собственной загруженной страницы.

После фиксации остаются обычные текущие колонки. Переключатель «Сравнить с исходным планом» добавляет исходное значение и разницу. Добавления, отмены, переносы и изменённые назначения видны отдельными метками. Персональная фиксация не снимается сменой исполнителя.

Корректировка показывает исходное значение, новое, причину и влияние на отчёт. Успех возвращает revision, после чего обновляются таблица, drawer и затронутые report runs. Закрытый исходный отчёт продолжает открываться по прежнему run ID; пересчитанный создаёт новую версию.

Обычная задача на неделю требует один Hours Est. При переносе или длительной задаче drawer раскрывает «Вся работа», «На эту неделю» и «Остаток»: 20 часов всей задачи и 6 часов недели не сравниваются с одним и тем же фактом. На этапе выбора пользователь видит, какой scope он меняет.

## 9. Факт и общие повторяющиеся встречи

Hours Fact в одиночной задаче открывает текущий личный итог периода и список составляющих. В общей задаче ячейка команды открывает breakdown по людям; редактирование доступно отдельной записи, а не замене суммы коллег. Автор внесения отличен от человека, которому начислены часы.

Форма ввода поддерживает день или целую неделю. При вводе «итого за неделю» сервер учитывает уже внесённые записи согласно контракту [учёта времени](03-domain-and-data.md), а UI показывает имеющуюся сумму и результат до подтверждения. Записи встречи и ручная подготовка к ней различаются источником; новое значение не добавляется поверх той же встречи по умолчанию.

Недельная точность показывается значком «За неделю». Отчёт за вторник не распределяет эти часы на дни: выводит отдельный нераспределённый итог и объяснение. Поправка закрытого факта требует причину и создаёт revision. Отсутствие записи отображается «Не внесено», явный 0 — «0».

Форма серии «Ежедневный созвон»: название, дни недели, локальное время и timezone, длительность, участники, срок окончания/число повторов, visibility и постоянная ссылка подключения. Preview показывает даты ближайшей недели, индивидуальный план и сумму человеко-часов. Ошибки неоднозначного локального времени показываются до сохранения по ответу сервера.

Каждый экземпляр — самостоятельная Task. В закреплённой секции «Созвоны» показываются ближайшие доступные экземпляры, не template серии. Переход «Только эта встреча / Эта и будущие» описывает влияние на дату, состав и фиксированные планы. Перенос сохраняет identity встречи, отмена — её историю.

После встречи организатор открывает список участников: «Присутствовал», «Частично», «Отсутствовал», «Не подтверждено». Можно установить общую длительность всем отмеченным присутствующим и исправить исключения. Перед «Учесть время» показан итог и число затрагиваемых людей; внесение за других требует capability. Новые участники и изменения существующих записей различаются.

Повторный клик заблокирован на время запроса; идемпотентность обеспечивает API, поэтому retry после обрыва безопасен. Успех содержит per-person result/revision. Уже подтверждённое присутствие не получает вторую запись от ручного редактирования той же Hours Fact; добавочная подготовка создаётся отдельным действием.

Пример приёмки: часовая встреча, трое были час, один полчаса, один отсутствовал. Полоса Gantt длится 1 час; личный факт — 1/1/1/0,5/0; командный — 3,5 человеко-часа. Template, закрепление и группировка по людям не добавляют ни одной единицы факта.

Ссылка на запись и summary принадлежат экземпляру. Постоянная ссылка подключения может наследоваться из серии. Новая встреча не копирует вчерашнее видео. Снятие участия не равно отзыву доступа; интерфейс даёт разные действия.

Для внешней записи Workloom ограничивает видимость URL и метаданных внутри приложения, но не управляет доступом у провайдера и не отзывает уже увиденный URL. В приватной встрече возле поля записи показывается короткая заметка: «Ограничьте доступ к записи в сервисе, где она хранится». Это контекстное пояснение без отдельного обязательного подтверждения; ACL Workloom не обещает приватность самого внешнего файла.

## 10. Приватность и доступ

В карточке доступны «Вся команда» и «Только выбранные люди». Для приватной встречи отдельно видны список допущенных людей и список участников. Owner пространства не получает неоговорённого права просмотра содержимого. Новые участники серии не получают автоматически её прошлые приватные экземпляры.

Недоступные задачи не приходят в клиентский список, search suggestions, граф, отчёт, уведомления или экспорт. UI не вычисляет скрытые значения из разницы totals. Для разрешённого собственного worklog с отозванным доступом к задаче используется серверная обезличенная проекция без названия/URL; клиент не достраивает её из cache.

Скрытая фильтром зависимость, на которую есть право, может показываться как «Вне текущего фильтра» с действием раскрытия. Недоступная зависимость получает только нейтральный индикатор, если такой индикатор разрешён сервером; ни названия, ни количества приватных задач, ни ID в tooltip нет.

При ошибке отзыва доступа убрать содержимое текущей карточки и связанных cache entries. Toast и error logging не содержат предыдущих чувствительных значений. Download/export остаётся серверным действием с теми же правами, что report query.

## 11. Отчёты и раскрытие расчёта

В P2 экран начинает с трёх шаблонов: план/факт, добавленный объём и тип работы. В P5 набор расширяется до шести шаблонов из спецификации вместе с настраиваемым builder. Builder предлагает разрешённый источник, метрику, период, группировку, фильтры, исходные/текущие значения и тип графика. Список агрегатов зависит от типа поля. Произвольные SQL/JS или вычисления по загруженной странице отсутствуют.

Report definition и report run — разные сущности: изменение фильтра создаёт новую конфигурацию/запуск, но не перерисовывает прошлый закрытый run под тем же ID. Header показывает область доступных данных, период, baseline, revision данных и дату расчёта. «Полный отчёт команды» не обещается при частичной видимости.

Bar/stacked bar/line сопровождаются таблицей. Клик по сегменту открывает drilldown с тем же run ID, метрикой, dimension values и source revisions. Сумма drilldown должна совпадать с выбранным числом; если строк много, итог вычислен сервером и не зависит от pagination. Переход к текущей карточке отдельно помечает её актуальное состояние.

В отчётах показываются отсутствие категории, нераспределённые часы, неполный факт, coverage завершённых пакетов и недоступный процент при нулевом baseline. Несколько Tags — пересекающиеся группы; UI предупреждает, что их доли не составляют круговую диаграмму 100%. Основная категория работы используется для непересекающихся долей.

## 12. Gantt и граф зависимостей

Оба вида получают даты/связи из API и вызывают те же команды, что карточка. Перетаскивание полосы меняет предложенные даты только выбранной задачи; подтверждение показывает конфликт и причину, если дата или поле locked. Автоматического пересчёта всей цепочки в MVP нет.

Gantt показывает текущие и baseline-даты, дату-only задачи на дневной шкале и временные встречи с явным timezone. Оценка 8 часов не превращается сама в календарный день. Задачи без дат находятся в списке «Не запланировано». Изменение даты не меняет worklog date автоматически.

Граф поддерживает автоматическую раскладку, ручные позиции, фокус на соседях, фильтр и drag связи «блокирует». Позиции — настройка вида, а не даты задачи. Циклы отклоняются сервером, UI отменяет временное ребро и объясняет проблему. Подзадача и замена показываются отдельными типами линий.

Список зависимостей в drawer позволяет выполнять те же операции клавиатурой и без графического canvas. Для большого графа сервер возвращает ограниченную окрестность/область, UI показывает границы загрузки и не изображает её как полный проект.

## 13. Ошибки, конкурентное редактирование и связь

Обычная безопасная правка текста может быть optimistic с rollback. Фиксация, корректировка, массовое начисление, change access и импорт ждут подтверждённого серверного результата. Каждая mutation несёт expected version и, где требуется, idempotency key согласно [API](04-api-and-integrations.md).

| Ошибка / ситуация | Реакция интерфейса |
| --- | --- |
| Конфликт версии | Показать введённое и актуальное значение; предложить повторить после ознакомления, без silent last-write-wins |
| Поле зафиксировано | Сохранить локальный ввод в редакторе, объяснить cutoff; предложить разрешённую корректировку |
| Нет доступа | Убрать защищённые данные, обновить capabilities; не повторять mutation бесконечно |
| Валидация | Ошибка у конкретного поля/строки; черновик сохраняется в памяти |
| Сеть пропала | Баннер; ввод остаётся черновиком в памяти; commit недоступен/явно не сохранён |
| Ответ mutation потерян | Retry с прежним ключом/проверка результата, без создания второй операции |
| Просроченный report run | Показать прошлый результат и время, предложить новый расчёт; не выдавать stale за актуальный |

Offline editing и фоновая очередь записей вне сети не входят в MVP. Не сохранять приватные данные в localStorage для «удобного offline». Перед уходом с несохранённым вводом есть предупреждение; после reload ввод может быть потерян и это явно обозначено. Первая синхронизация — refetch при focus и после mutation плюс ограниченный polling; transport событий можно заменить позднее без смены feature API. Сигнал отзыва доступа или новый запрет сервера немедленно очищает затронутый cache; периодический refetch не является гарантией мгновенного стирания уже загруженных данных на чужом устройстве.

## 14. Доступность, тесты и этапы UI

Все действия доступны клавиатурой, поля имеют labels, focus виден, dialogs возвращают его на trigger. Замок/статус/изменение не обозначаются только цветом. Для виртуальной таблицы проверяются grid semantics, row/column counts и screen-reader навигация; для сложных форм существует обычная карточка. Drag имеет меню-альтернативу. Интерфейс не теряет рабочие действия при увеличении масштаба до 200%.

| Этап | Конкретная поставка UI | Проверка готовности |
| --- | --- | --- |
| P0 | Shell, routing, tokens, local actor; workspace и участники из PostgreSQL; 6 fixture users и второй workspace | Сквозной запрос UI → API → БД; actor switch очищает cache; чужой workspace недоступен; задач и недельных fixtures ещё нет |
| P1 | Сохраняемая таблица задач, inline edit, keyboard/paste, drawer, поля/виды, ACL, hierarchy/history; fixtures общих и приватных задач | Рабочий сценарий из скриншота без мыши; конфликт двух вкладок не теряет ввод; приватная задача недоступна чужому fixture actor в таблице/поиске |
| P2 | План/факт, личная/общая фиксация, история/корректировки, первые три отчёта | Cutoff во время редактирования; 20/6 часов; пусто и 0; split без двойного бюджета |
| P3 | Общие встречи, recurrence preview, присутствие, ссылки, privacy | 3,5 человеко-часа; retry; перенос; удаление участника; URL/метаданные записи скрыты от постороннего в Workloom |
| P4 | Граф и Gantt, filter boundaries, альтернативные списки | Один набор зависимостей; cycle error; отсутствие дат; drag locked задачи |
| P5 | Настраиваемые reports, drilldown/versions, импорт, готовность общего API к stdio MCP | Суммы совпадают; недельные часы не выданы за дневные; закрытый run воспроизводим; импорт сверен |
| P6 | Выпуск пилота после P3 и минимального импорта: Auth, участники/приглашения, защищённая сборка | Убрана dev identity; реальные права работают; перенос выбранных данных сверен; выполнен недельный rehearsal |

Идентификаторы P0–P6 совпадают с [общим планом реализации](06-implementation-plan.md) и обозначают модули поставки, а не строгую хронологию. Выпуск пилота P6 начинается после P3 и минимального импорта P5.4/P5.6; обогащение через Asana API P5.5 требуется только при необходимости для выбранных данных. P4 и остальные части P5 идут параллельно или после пилота: они остаются в полном MVP, но не задерживают первую рабочую неделю команды.

До подключения P6 используется только локальный `AUTH_MODE=dev` с synthetic actors и тестовыми данными. После подключения P6 защищённые сборки и следующие функции используют общий Auth; локальный dev adapter остаётся только инструментом разработки. Приватность встреч до настоящей аутентификации проверяется на fixtures как доменная политика, а не обещается реальным людям.

Тесты: unit для parser/formatter и row identity; component tests для focus/edit/clipboard/lock; integration с контрактными ответами API для cache и ошибок; браузерные сценарии через настоящий backend для concurrency, privacy, baseline и meeting retry. Accessibility automation дополняется ручной проверкой клавиатуры и screen reader. Screenshot checks применяются к ключевым состояниям таблицы/drawer/reports, а не ко всем возможным комбинациям полей.

Клиент не тестирует заново SQL/доменную арифметику снимками JSX. Он проверяет, что отправляет правильный scope/person/version, корректно объясняет серверный результат и не утрачивает пользовательский ввод. Производительность измеряется на фиксированном fixture, включая длинные названия, дерево, 20+ колонок, активный редактор и общие встречи; критерии и результаты ведутся в [проверке пилота](07-verification-and-pilot.md).
