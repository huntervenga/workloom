# Shared activities and reusable summary templates

## Что работает сейчас и чего не хватает

Существующие section/assignee summaries хранят до четырёх показателей для конкретной группы: операции над обычными numeric/duration-полями и доступное время явно выбранного человека. Период может следовать датам проекта, текущей неделе либо заданному диапазону. Есть локальное ручное переопределение displayed Available. Общего именованного шаблона со связанными применениями пока нет.

Generic project/workspace Reports считают canonical task values и относят их одному основному исполнителю. Полная duration задачи не копируется участникам. Их источник не объединён с meeting attendance. Итоги выбранного поля в таблице и трудозатраты людей — пока разные будущие семантики, а не два взаимозаменяемых названия одного SUM.

Native meeting engine уже хранит одну задачу созвона, roster, записи/summary, recurrence, отдельные персональные plan proposals и attendance worklogs. Present получает полную actual duration, partial — явно указанную часть, absent — ноль, unconfirmed остаётся неизвестным. История, revisions и проверки прав сохраняются. Однако создание требует `plannedPeriodId`, posting attendance — `periodId`; эта модель не интегрирована с обычными пользовательскими Plan/Fact-полями. Она не становится period-free от одного скрытия week selector.

## Шаблон сводки и его применения

В проекте появляется именованный **Summary template**. Он содержит стабильные widget keys, выбранные field IDs, поддержанные операции, область задач и правило периода. Выражения остаются типизированным ограниченным каталогом; произвольный SQL, код и неограниченные связи с другими таблицами не добавляются.

Пример обычной конфигурации пользователя: `SUM(поле A)`, `SUM(поле B)`, `Available(Person, Project dates)`. Система не ищет поля по названиям Hours Estimation/Fact и не сопоставляет людей по заголовкам секций.

Применение шаблона хранит ссылку на template ID, параметры и явные локальные исключения. Основные параметры:

- **Person:** в группировке Assignee можно выбрать «человек этой группы»; у произвольной секции человек выбирается явно. Секция не обязана означать человека.
- **Task scope:** задачи этой секции/группы либо задачи выбранного человека в проекте. Это разные понятные варианты; scope не меняется незаметно при выборе Person.
- **Period:** даты проекта, текущая неделя или конкретный диапазон. Неделя — удобный preset, а не системное условие. Ненастроенные Project dates дают понятный unavailable state.
- **Local overrides:** например ручной target для конкретной секции. Значение маркируется как Manual и не переписывает расписание человека, отпуска или report Available.

### Пользовательский путь

1. Пользователь настраивает сводку секции и выбирает **Save as template**. Текущая форма включается в сохранение; дополнительное Add/Apply перед Save не требуется.
2. В другой секции выбирает **Use template → название шаблона → Person**. Если шаблону не нужен Person, этот параметр не показывается.
3. В summary settings видно **Uses: Personal delivery**. **Edit template** редактирует общую настройку и перед сохранением показывает число затронутых применений.
4. **Customize this section** создаёт явные локальные исключения. **Reset to template** убирает их. **Detach** сохраняет разрешённую текущую конфигурацию как независимую.

Правка общего шаблона применяется ко всем связанным секциям. Локальные исключения сохраняются и остаются заметными. Ошибка в недоступном поле/человеке не превращается в успешный частичный итог. Открытие и закрытие чистого редактора не создаёт false dirty state; настоящие несохранённые изменения объясняются рядом с доступными кнопками подтверждения.

### Дублирование и связь — разные действия

Обычное дублирование создаёт самостоятельную секцию/проект и самостоятельные настройки. Последующая правка оригинала не меняет копию. Копирование значений само по себе не создаёт linked template.

Если исходная секция использует общий шаблон, интерфейс должен явно предложить **Keep template link** либо **Create independent settings**. Для желаемого сценария «изменить сразу всем» нужна сохранённая ссылка; при независимой копии это поведение не обещается. Имя скопированной секции не меняет Person binding автоматически: человек выбирается/подтверждается пользователем.

Между проектами нельзя переносить field/section IDs как будто они принадлежат новому проекту. Независимый project clone требует явной карты новых field/option/section/template IDs. Workspace membership binding сохраняется только при том же workspace и текущем доступе. Библиотека общих workspace templates с переносимыми field slots — возможное расширение, не обязательная часть первого этапа.

### Версии и совместимость

Новые template definitions и bindings должны иметь собственные revisions; проверка доступа, expected revisions, idempotency и audit выполняются в существующей workspace transaction. Изменение шаблона инвалидирует связанные query results. Исторические checkpoints/initial snapshots сохраняют фактически разрешённую версию шаблона и параметры, а не пересчитываются по его текущему head.

Существующие concrete header widgets остаются самостоятельными. Их можно явно сохранить как шаблон, но автоматическое создание ссылок или переосмысление сохранённых настроек не выполняется. Старые JSON payloads и receipts не получают новых default-полей при replay. Точный additive storage/API контракт выбирается до реализации; этот документ не вводит таблицы или миграции.

## Одна общая активность и персональное время

В списке остаётся одна canonical task, например ежедневный созвон, с общими названием, описанием, статусом, датами, ссылкой на запись и roster. В ней различаются **ответственный/организатор** и **участники**, чьё время нужно учитывать.

Обычные duration-поля остаются обычными полями. В настройке shared activity/report владелец явно выбирает field IDs и способ attribution. Значение на задаче описывает длительность события; персональный effort выводится из выбранных источников участия. Автоматически делить час на число людей или приписывать каждому participant часы всех обычных задач нельзя.

Для первого поддержанного shared режима достаточно **Full duration per participant**, с персональными исключениями. Split-проценты и любые другие не реализованные способы распределения не должны появляться как якобы работающие опции.

### Понятный UX созвона

1. **Add task → Shared activity**: имя, дата/время, duration, organizer и participants через поиск/chips. Можно использовать явно настроенный шаблон активности с выбранными обычными полями.
2. Добавление участников создаёт будущие персональные плановые вклады/предложения. Оно не подтверждает присутствие и не создаёт фактическое время.
3. После созвона пользователь указывает actual duration и выбирает **Confirm attendance**. Одна операция может подтвердить выбранных участников сразу, показывая перед действием личные минуты. Для исключений доступны **Partial**, **Absent**, **Not confirmed**.
4. В задаче видно, например: **Duration 1h · 5 participants · Team effort 5h**, а не двусмысленное одно число. Запись и summary — обычные доступные ссылки.
5. В представлении по людям общая активность может показываться reference-row с отметкой Shared и личным вкладом. Все такие строки открывают одну и ту же задачу. В других произвольных секциях активность не дублируется автоматически.

Для роли без права записи чужого времени подтверждение доступно только за себя. Организатор сам по себе не получает права менять факты остальных; массовое подтверждение требует соответствующей capability. Простое перемещение задачи между секциями не меняет attendance или владельца уже записанного времени.

### Источник персональных вкладов

Нужен серверный read/calculation contract, различающий хотя бы:

- Значение ordinary task field, относящееся основному исполнителю.
- Плановый вклад участника общей активности, с конкретной версией roster/duration и состоянием original/current.
- Подтверждённый фактический вклад участника: occurrence identity, membership ID, выбранная метрика/field binding, источник, revision и состояние active/void/unknown.

Это одна логическая модель персональных вкладов для расчёта; она не требует копий задач. Стабильная source identity исключает повторную запись при replay, нескольких placements и нескольких экранных reference-rows. Где можно, переиспользуются правила существующего attendance engine. Добавляется period-free путь, а не скрытая автоматическая неделя.

Старые native meetings/worklogs/baselines остаются неизменными. Для них возможен отдельный read adapter в новую модель. Если generic activity и legacy meeting ссылаются на одну задачу, источник метрики выбирается явно и однозначно; оба источника одновременно не складываются. Автоматическая миграция прежних значений в новые записи не подразумевается.

Confirmed contributions сохраняют подтверждённую версию duration/roster. Поздняя правка метаданных или удаление человека из будущего roster не стирает его прошлое время. Исправление ранее подтверждённого участия проводится ревизией с причиной и текущими правами. Планы и actuals не становятся друг другом; unconfirmed не подменяется нулём.

## Расчёт и совместное отображение

| Ситуация | Длительность события | Персональный факт | Итог трудозатрат команды |
| --- | --- | --- | --- |
| Созвон, 5 present | 60 минут | каждому 60 | 300 минут |
| 3 present, 1 partial 30, 1 absent | 60 минут | 60, 60, 60, 30, 0 | 210 минут |
| Один участник не подтвердил участие | 60 минут | unknown у этого человека | известный subtotal с явным coverage; не полный итог |
| Обычная личная задача | значение выбранного поля | одному основному исполнителю | один источник, один раз |

Для одной общей встречи task count равен 1, participation count может быть 5, effort — 300 минут. Эти показатели нельзя называть одним общим Count. Если дополнительно есть личная задача на 120 минут, суммарный effort при пяти present равен 420 минутам; к нему не прибавляется ещё 60 минут исходной общей task value.

Обычный `SUM(field)` по canonical tasks остаётся суммой task values. **Personal effort** — явный режим/источник метрики, который считает персональные вклады. Потребитель видит выбранную семантику. Сервер никогда не меняет старый SUM незаметно после добавления участников.

Для персонального summary пользователь может выбрать **This person across project → Include shared participation**. Тогда созвон из общей секции входит в его итог рядом с личной работой. Для **Tasks in this section** остаётся section scope; выбор человека только для capacity не должен внезапно добавлять чужие задачи или созвоны из других секций.

Один server calculator обслуживает summaries, project Reports, workspace Reports и planning checks. Он считает полный разрешённый scope, учитывая source revisions и coverage, независимо от pagination/collapse. Расписание и отпуска дают отдельный Available; участие в созвоне расходует время, но не переписывает capacity. Отношение effort/Available использует человеко-минуты с обеих сторон.

Рабочие категории используют выбранные field/option IDs и сохраняют цвета. Один вклад учитывается один раз в эксклюзивной category; пересекающиеся tags не превращаются в повторный team total. Shared task в нескольких проектах также не даёт несколько одинаковых источников во workspace report.

Даты ordinary task duration остаются выбранным task-cohort фильтром. У occurrence attendance есть реальная дата события. В отчёте смешанные источники получают явно описанное правило дат; task-level duration нельзя выдуманно раскладывать по рабочим дням. Initial snapshots должны фиксировать персональные source identities, roster attribution и unknown states, чтобы изменения исполнителя/roster позднее не меняли исходное обещание.

## Права и ограничения

Template management использует существующие права на проектные настройки/поля; просмотр не даёт право редактирования. Сохранённый template/binding не предоставляет вечный доступ к человеку или полю. Недоступные источники не должны утекать через totals, labels и counters.

Attendance сохраняет разделение self/others; immutable history и exact retry остаются обязательными. Отчёты получают neutral availability, без причин отпусков, медицинских заметок и иных скрытых данных. Полная private-task ACL не считается решённой этой моделью и требует отдельного контракта.

Пределы числа шаблонов, применений, участников и source rows определяются до реализации с явным overflow, без обрезания итогов. Существующие ограничения generic widgets/fields/capacity продолжают действовать, пока новая версия не принята отдельно. Программируемые произвольные выражения, внешние календари и миграция legacy sources не входят в первый bounded этап.

## Этапы реализации и условия приёмки

1. **Linked summary templates.** Definition + binding + Person/period parameters + visible overrides/detach. Проверить изменение всех связанных секций, независимую копию, field ID remapping в clone, чужие/архивные источники, concurrency, exact replay и сохранность старых concrete widgets/snapshots.
2. **Personal contribution contract/calculator.** Явные источники/attribution и versioned output, без нового UI создания. Независимые оракулы из таблицы выше, zero/null/missing/void, несколько placements/tags/subtasks, roster edits, full scope при одной загруженной странице, правильные category denominators.
3. **Period-free shared task UI и atomic commands.** Одна активность, поиск участников, plan proposals, подтверждение actual/attendance, recording/summary links, self/others permissions. Старые native paths остаются рабочими и не переименовываются в новые. Проверить late SQL rollback и lost-response exact retry.
4. **Unified summaries/Reports/checks.** Подключить один калькулятор ко всем экранам; сохранённый отчёт явно показывает семантику и date rule. Неизвестный факт не считается нулём, shared event duration не добавляется поверх effort, capacity не переписывается, original snapshots не изменяются. Проверить оба theme, автосохранение/Undo, reload и актуальные permissions.
5. **Recurrence нового пути.** Удобная ежедневная серия без скрытых недель; occurrence identity, исключения и история. Внешний calendar ingestion — следующий отдельный этап. Существующая native recurrence остаётся самостоятельным поддержанным сценарием.

Для каждого этапа отдельно фиксируются изменения контракта, meaningful unit/PG/browser evidence и ограничения. Этот proposed-документ сам по себе не является разрешением на production deployment, изменение существующих данных или обход обязательных guards.
