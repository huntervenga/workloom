# Подготовка размещённого Workloom

Подготовлен исходный путь для staging/production; публичное развёртывание пока не выполнено. Текущий локальный код306ed35 активирован; scope и local proofs — в [84](84-team-pilot-plan.md), предыдущая версия — в [82](82-reports-and-five-person-demo.md). Новые настройки не доказывают работоспособность Railway, внешнего Google-входа, реальной команды или восстановления резервной копии. План допуска небольшой команды — [84](84-team-pilot-plan.md).

## Настройки сервиса

Задайте `APP_ENV=staging` либо `production`, `NODE_ENV=production`, `AUTH_MODE=shared`, `HOST=0.0.0.0`. Railway передаёт `PORT`; вне Railway задайте положительный порт явно. Запускайте `node apps/api/dist/main.js`, а не корневой local-start с загрузкой `.env`. Hosted entrypoint не читает файл `.env`.

Обязательны явные `AUTH_APP_ORIGIN=https://workloom.pavelignatov.com`, `AUTH_BASE_URL=https://auth.pavelignatov.com`, соответствующий точный `AUTH_ISSUER`, `AUTH_AUDIENCE=pet-projects` и приватный `AUTH_SESSION_KEY`. Сохраните один и тот же ключ сессий между выпусками и всеми replicas; новый/разный ключ делает прежние токены нечитаемыми. Не публикуйте ключ и не используйте вместо него analytics secret или Auth client secret. Hosted cookies имеют Secure; браузерный callback остаётся `/app/auth/callback`. Существующий ранее принятый upstream allowlist эта работа не меняет. Provider origin-matching semantics этим audit не проверены; реальный HTTPS callback/вход проверяются отдельно, без требования менять уже принятую конфигурацию. При заданном `APP_ORIGIN` допустим только тот же canonical origin. JWKS вычисляется как `AUTH_BASE_URL` + `/.well-known/jwks.json`; старый `AUTH_JWKS_URL` не является читаемой настройкой текущего сервера.

`DATABASE_URL` должен указывать на отдельную целевую hosted-базу. Публичный адрес требует `sslmode=verify-full`; URL с `require`, `prefer`, `disable` и переопределениями host/SSL/credentials отклоняется. Только точный DNS-поддомен `*.railway.internal` может не задавать sslmode для приватной сети. Не используйте `PG*` overrides, `DEV_ACTOR_ID` или `NODE_TLS_REJECT_UNAUTHORIZED=0`. Локальные инструменты и worker сохраняют прежние ограничения; запуск worker не входит в этот контейнер.

## Сборка и миграция

`Dockerfile` собирает библиотеки, API и frontend в Node24, запускает процесс от пользователя node. Старт не мигрирует базу, не создаёт демо и не запускает worker. `.dockerignore` исключает локальные секреты, состояние и старые dist. Сборка/запуск контейнера должны получить отдельный фактический результат; наличие файлов не является проверкой образа.

Оператор проверяет резервную копию и возможность восстановления, затем сверяет с одобренным выпуском число и SHA списка миграций. SHA вычисляется как SHA-256 UTF-8 `JSON.stringify(readExpectedMigrations())` из собранного `@workloom/db`; включает упорядоченные tag/createdAt/hash. Только после проверки целевой базы и релиза допустима явная команда:

```sh
node scripts/hosted-migrate.mjs --apply --expect-count 20 --expect-manifest-sha 341070a96a60586f00061833741f585bacec0c13c0f55548bd8802b9af5cea80
```

Для текущего одобренного source manifest это20 entries и указанный SHA; при новом выпуске сначала заново сверяют конкретный manifest, не используют старую команду вслепую. Она требует hosted shared config, запрещает loopback, проверяет ожидаемый manifest до подключения и использует существующую блокировку/проверку ledger. Она не заменяет backup/restore или план выпуска и не откатывает миграции автоматически. В Railway автоматический predeploy migration не настроен. Миграцию проводят явной операторской командой до старта совместимого сервера; startup DDL нет. После0018/0019 прежний18-ledger image увидит schema ahead и readiness503. Обычный возврат к старому backend image недостаточен: нужен совместимый с20-entry schema образ либо отдельно проверенный recovery/restore план. Автоматический schema rollback не реализован. Не исполняйте эту команду для локальной основной базы или без отдельного разрешения оператора.

## Допуск выпуска

Проверьте `/healthz/ready` и реальные HTML/JS/CSS, затем HTTPS callback/сессии двух пользователей, изоляцию workspace и права/revoke. Проверьте reload/старую вкладку и восстановление backup в отдельной базе. Подтвердите сохранность данных, ledger и ключа, а также выключенный worker. До этого размещение остаётся подготовкой. Текущий worker config по-прежнему local/dev-only и отвергает Railway: hosted pilot оставляет workerOFF и использует ручные freezes/materialization/подготовку встреч. Deadline/quota custom fields проверяются синхронно при записи и worker не требуют. Docker image не сохраняет прошлые hashed chunks так, как local promotion; production old-tab upgrade требует отдельной проверки, его PASS не следует из локального retention старых assets.

Host приложения ограничен canonical origin. Для readiness разрешён отдельный `healthcheck.railway.app` только на точном GET/HEAD `/healthz/ready`; это не разрешение на API или Origin writes. Такой hostname указан в [официальной документации Railway](https://docs.railway.com/deployments/healthchecks); readiness Railway проверяет запуск, а не непрерывный мониторинг. `trustProxy` не включён. TLS-режим проверен по установленному исходнику postgres.js; параметры TLS описаны в [первичном репозитории драйвера](https://github.com/porsager/postgres). Источники проверены 18 октября 2026.
