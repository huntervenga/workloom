## Visible states and controls

Weekly shows a compact Plan freeze status region beside the selected period. The status comes from the authorized readiness GET and its server timestamp, rather than the browser clock. Planning, deadline passed without a baseline, calendar preparation, blocked and persisted frozen are distinct. Frozen requires an actual persisted baseline; requested cutoff and actual freeze time are shown separately. Refreshing disables new mutations until a fresh readiness result arrives. A denied read hides cached controls and status. A missing API or invalid response is an error, never a successful fallback state.

Automatic freeze settings remain collapsed initially. Existing periods are explicitly unconfigured until an owner/admin enables this period. Enable automatic freeze, Turn off automatic freeze and Renew authorization are explicit actions using the current server-supplied permission and optimistic period/authorization revisions. Renewing uses the current administrator's authorization. Request processing again creates only a processing request; it never claims that processing has started or that a baseline/report has been saved. The existing explicit Save project baseline dialog is reused, gated by the fresh `canFreezeProject` action. Personal baseline controls remain separate. Turning automatic freeze off does not remove ordinary deadline protection when plans are edited.

Reported blockers use stable localized explanations. The meeting-preparation count and issue count remain distinct because issues also include automatic-freeze authorization. A truncated blocker response remains explicit; the client does not invent full calendar totals. Every returned blocker is reachable in the disclosure. Recurring-meeting blockers open the existing recurring-meeting area explicitly. Pausing advance creation does not cancel registered occurrences; only missing meeting creation needs the current calendar generation authorization. Complete persisted census may freeze without borrowing future generation authority.

## Commands and recovery

One page-owned idempotent command ledger covers configuration and processing retry across period/view changes. A pending command blocks replacement actions. Unknown commands retain their exact original period, payload and key. Recovery opens the original period and requires its current configuration capability before replay; a new-processing `canRetry=false` does not prevent replay of an already-sent public command under that current authority. Readiness reads never create jobs, meetings, baselines or reports.

An exact public replay may return an older authorization receipt after another administrator replaces or revokes authorization. The client never installs that receipt as the current head: success invalidates live readiness/period collections and reads the authorized current projection. A late response never changes the selected period or report view. Existing manual freeze success explicitly refreshes readiness. A fresh readiness response that observes a newer period revision or project baseline also invalidates the real period, project period list and baseline queries. It never manufactures a period/baseline DTO, selects another period or clears report drafts; repeated observation of the same read is deduplicated.
