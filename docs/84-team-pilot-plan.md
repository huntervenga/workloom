## Как работает локальный срез

**Team access.** Owner выдаёт ручную bearer invite-ссылку на Admin/Member/Viewer; Admin — только Member/Viewer. Owner не передаётся и не отзывается этим UI. Ссылку пользователь передаёт самостоятельно: сервис не отправляет email и не связывает приглашение с адресом почты. Получатель сначала входит через Auth, затем вновь открывает/вставляет исходную ссылку с fragment и подтверждает join; бесшовный перенос секрета через login не обещается. Первый личный workspace и profile сохраняются. Роли/revoke проверяет сервер; отзыв membership не восстанавливается старым receipt, нужен свежий invite. Pending invite прекращает выдавать новый доступ при expiry/revoke/утрате прав issuer. Уже consumed same-actor receipt при всё ещё активном членстве — replay результата, не новая выдача; он не обязан исчезнуть с expiry исходной ссылки.

**Field rules.** Project→Columns→Team columns→Edit field→**Rules** в текущем UI; Record history и Lock values остаются отдельными настройками. Owner настраивает UTC deadline и лимит изменений. Admin не получает это право через существующий fields.manage. В карточке показаны локальный timezone и точный scope: **на каждого участника, для каждой canonical task+field, за всё время после первого включения**. Browser clock — подсказка; сервер проверяет DB barrier time≥deadline.

Первый changed set (включая отсутствовавшее typed null) и changed clear расходуют1; equality/no-op, exact replay и rollback —0. История значений выключена или policy отключена — usage всё равно сохраняется после первой activation. Rename, лимит/policy revision, disable/re-enable, reassignment и второе placement не сбрасывают счётчик. Ноль допустим как запрет новых changed writes; это не «без лимита». До activation не выдумывается прошлый usage.

**Owner exception** — отдельное явное изменение с reason, текущими policy/value/definition revisions и аудитом. Обычный owner подчиняется правилам. Исключение обходит только deadline/quota и расходует собственное изменение owner; **manual lock и frozen baseline абсолютны**, исходный snapshot не меняется. Для never-activated policy исключение не применяется. Причина появляется в whitelisted Activity; raw value при выключенной history и reason в outbox не публикуются. Одна запрещённая строка не должна давать partial bulk/import/composer.

**Keyboard selection.** В сфокусированном gutter ArrowUp/Down перемещают selection, Shift+Arrow расширяет/сокращает диапазон, Enter открывает детали. Не перехватывать курсор в text editor, IME или модифицированные Ctrl/Meta/Alt chords. Существующие pointer/manual reorder и41px rows должны сохраняться. Unknown command остаётся привязан к первоначальным actor/body/key/target; Close/reload/403/409 не должны терять draft и создавать повторный write.

**Hosted prep.** В source добавлен явный staging/production shared-only режим: HTTPS canonical origin/Auth, Secure session cookies, строгий Host/Origin, remote DB TLS. Local defaults и worker guards сохраняются. Подробнее [85](85-hosted-runtime-preparation.md). Это проверенная локальная подготовка, не public deployment и не успешный внешний Google-вход. Первая Docker-сборка завершилась npm ci EUSAGE; lockfile исправлен, повторная сборка в уже работающем colima-librechat context прошла npm ci/libs/API, но завершилась web-build RED из-за отсутствующего oxide native binding. Успешный image build пока не заявлен. Engine не запускался, global context/другие контейнеры не менялись.

## Ручной перенос и короткая UX-приёмка

После P0 gates выбрать один небольшой общий проект. До задач настроить sections/statuses,цветные tags, custom-column types+options и один single-select Work type для долей. Перенести вручную10–20 актуальных задач: понятное название, короткий outcome, ответственный, due/+start, зависимости, значения. Parent/detail делят package estimate; independent work получает собственный scope. Одна canonical Task с общим статусом может иметь placements; факты и original accounting остаются home-scoped, без копирования и удвоения часов.

Asana оставить read-only reference. Не создавать выдуманные historical originals/часы/комментарии: сначала текущие personal plans, затем настоящий explicit freeze, затем facts. Общие tags могут пересекаться, Work type+Uncategorized дают100% по fact minutes без двойного счёта.

20–30мин приёмки Павлом и вторым участником: join/role/revoke; Enter-create и keyboard gutter; переименование/назначение/комментарий через compact autosave pane; custom field denial/recovery; собственные plan/fact0 и missing; Reports team/person и Work type100%; один manual freeze. Продолжать после первой недели, если люди выполняют этот цикл без разработчика, ACK/unknown не потеряны, отчёт сходится с контрольными source minutes и restore проверен. При потере доступа/данных/обходе locks остановить real writes и сохранить evidence; не reseed/rewrite историю.

## Что взять из Asana, чего не обещать


Asana разделяет управление **определением поля**, ограничения **значений в проекте** и **видимость** поля; это полезное разделение для Workloom, а не повод строить enterprise permission matrix. [Официальный overview](https://help.asana.com/s/article/asana-custom-field-permissions), проверено18Oct2026.

Пользователь достигает настройки через column menu→Edit field, а project value restrictions — через Project menu→Manage project permissions→Fields. Настройки определения и право менять значение не следует смешивать. Asana описывает ограничения значений, включая Assignee/Due Date, как Enterprise-функцию; документ не подтверждает наш quota/deadline механизм. [Custom fields](https://help.asana.com/s/article/custom-fields), [Value restrictions](https://help.asana.com/s/article/edit-restriction-on-custom-field-values?language=en_US), [Access levels](https://help.asana.com/s/article/custom-field-access-levels?language=en_US).

Из повседневного UX нужны узнаваемые list entry points: Enter для добавления задачи, явная ручка reorder, видимый multi-select toolbar и контекстное редактирование. Наши own semantics —41px rows, personal weekly accounting и ограничения linked rows — остаются отдельным контрактом, без parity claim. [Asana List view](https://help.asana.com/s/article/list-view), [Task actions](https://help.asana.com/s/article/task-actions?language=en_US).

Для переноса важнее заранее договориться о названиях, ответственном, due dates и порядке работы, чем копировать весь старый backlog. Это согласуется с [Asana team conventions](https://help.asana.com/s/article/establish-conventions-for-your-team?language=en_US); интеграции/email automation не входят в этот пилот.
