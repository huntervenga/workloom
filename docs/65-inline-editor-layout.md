# Inline editor layout budget

This bounded client change fixes the desktop layout defect recorded in [62](62-inline-task-priority.md) at compiled `0fc9feb`: the 96px Priority column left the inline editor about 72px, uncertain save feedback wrapped one word per line, and the Save/More details/Collapse row overflowed under the adjacent last sticky Team estimate cell. That cell (`lg:sticky right-0 z-[1]`) intercepted pointer events on the enabled Collapse control after a committed Urgent change lost its acknowledgement. Mobile, without the sticky estimate column, passed.

## Presentation contract

`TaskTable` accepts one explicit presentation-only prop, `activeFieldEditor: { taskId, field }`, which `ProjectPage` derives from its existing active inline state. The editor itself still comes from `renderTaskFieldEditor`; the table does not call that function to discover the active column. When the task is loaded and the edited field's column (mapped by the shared `taskInlineColumn`) is visible, that `<col>` widens to at least `INLINE_EDITOR_COLUMN_WIDTH` (288px) and the table minimum width grows by the same amount. The rule applies to every field sharing the inline editor: Status, Assignee, Due date, Priority and Team estimate. Title editing uses the existing flexible title column and changes no width. No active editor, an unloaded task or a hidden column leaves every width unchanged.

The flexible title column keeps its existing minimum, so the wider editor causes local horizontal scrolling rather than squeezing titles. Column order and visibility, row cells, hierarchy, the sticky title and the sticky last estimate column stay unchanged. The editor gets real width; nothing is painted over, hidden or raised above unrelated values.

Inside that budget, `InlineTaskEdit` is `min-w-0` with `overflow-wrap: anywhere`, so recovery copy and request IDs wrap within the cell. The Save/Retry, More details and Collapse row and the existing-draft and not-editable fallback actions use `flex-wrap`, so they wrap instead of overflowing. Width changes do not remount the keyed editor, so focus claims, retained sessions and held commands are unaffected. No mutation, authorization, command, filter, query or message catalog changes were made, and no English copy was added.

## Explicit reveal in the table scrollport — `5267fbd`, accepted

A wider column can leave the opened editor outside the visible table area. Root's stronger read-only geometry gate takes no scroll, focus or click. On old compiled `54005e1` it failed natively at 1440 and 390, before any further click or save. On desktop a sticky cell occluded Priority, More details and Collapse. On mobile the select reached x=425, past the 390px viewport.

`revealInlineEditor` in [`TaskTable`](../apps/web/src/features/task-table/TaskTable.tsx) adjusts only the editor's own `[data-task-table-scroll]` container horizontally. The clear area runs between the real bounds of the sticky cells before and after the edited cell, within the window. An editor wider than that area is aligned to its start, keeping the input and Save in view. [`InlineTaskEdit`](../apps/web/src/features/tasks/InlineTaskEdit.tsx) calls it once, from the same explicit focus claim that opens the editor. It never scrolls the page or moves focus. A lost ACK, refresh or remount does not repeat it, and it does nothing in a sticky cell or outside a task table.

The source author reported 55 affected tests passing. On compiled `5267fbd`, root's normal gates passed, including the full web suite. The same stronger spec that failed on `54005e1` then passed all six cases at 1440/390. Root inspected the Priority screenshots and confirmed that the select and the Save, More details and Collapse buttons are visible without help. Test-only `4e63b57` adds a 1024×900 Priority case with a read-only check that a sticky cell is present; it passed on its own, with no product change. This is accepted RED→GREEN for these three widths. Physical touch, other widths and column configurations, and old-tab behavior are not claimed. The independent source review has since completed; it found no inline-editor issue ([25](25-ux-verification.md)). Exact results are in [25](25-ux-verification.md).
