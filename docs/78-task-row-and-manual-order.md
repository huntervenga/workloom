## Поведение таблицы

Ограниченный новый UX сохраняет **41px** строки и полную область ячейки. Видимый текст названия редактируется явно; свободная область справа открывает детали (**Open task …**), отдельный **Task actions** заменяет набор мелких action icons. Новая строка остаётся на выбранном месте, а следующий ввод получает отдельный буфер и ключ. Ввод между строками/Enter связан с соседней задачей и её subtree, а не с номером видимой строки после фильтрации.

Отправленные pending/uncertain строки показывают сохранённый readonly preview. Очередь ждёт настоящий ACK предыдущего create, чтобы следующий anchor указывал на подтверждённую задачу. При неизвестном исходе повторяется исходная команда с тем же содержимым и ключом; последующие строки не перепривязываются к неподтверждённому UUID. Неотправленные изменения, значения полей и явный plan/fact должны сохраняться в собственном draft. Явный Escape отбрасывает **все** ещё не отправленные quick rows, включая прежнюю нижнюю пустую строку (решение пользователя/root); отправленные и unknown записи очереди сохраняются.

В новом UI, если в новой строке есть custom values или plan/fact, task, builtin-поля и эти дополнения уходят одним all-or-nothing запросом rows route (ниже). Строка только с названием/builtin-полями без дополнений по-прежнему создаётся прежним task create endpoint. При первой отправке anchor разрешается и фиксируется в теле; unknown retry повторяет точно то же тело и тот же ключ. Шесть принятых compiled Chrome flows перечислены ниже; исчерпывающая приёмка всех колонок/drawer/keyboard и полный Asana parity не заявлены.

Ручное pointer drag в UI доступно **только** при группировке по Section и manual sort. Ручная группировка по Assignee поддерживает вставку через Enter, но **не** drag. Сортировка по due date не предлагает mid-row insertion или reorder; обычный create в конце section остаётся доступным. Это ограничение UI: серверная возможность ниже (root move между sections по anchor и splice полного глобального порядка) остаётся как описано и не сужается. Drag меняет порядок в разрешённой группе siblings, не родителей, даты или effort. Корневую задачу можно поставить в section корневого anchor; подзадачи остаются у того же parent и в том же section. Выборка на экране может быть частичной: сервер определяет порядок по полному проекту, включая скрытые, archived и ещё не загруженные строки. Сохранённые относительные позиции остальных задач не должны перемешиваться.

Drawer использует отдельный блок подзадач вне родительской формы, чтобы inline subtask create не был вложенным HTML form. Конкретные user-facing selectors, keyboard actions и bounds фиксируются по final frontend packet и native gates; текущий документ не превращает source intent в browser PASS. Details receiver и assignee follow-ups включены в source freeze: immutable transfer сохраняет staged extras и insertion, а общий guard не передаёт pending/unknown/queued session в новый create. Это source contract и focused-test evidence; отдельная native-приёмка именно этого переноса не заявлена.

## Создание и перемещение на сервере

Обычный create получает необязательный `insertion: {anchorTaskId, placement: 'before' | 'after'}`; одновременно передавать numeric `position` нельзя. Отсутствие insertion сохраняет прежний parsed payload и прежний hash — без нового default-поля в старых командах. Контракт: [tasks.ts](../packages/contracts/src/tasks.ts).

`POST /api/v1/workspaces/:workspaceId/tasks/:taskId/move` принимает `{expectedRevision, anchorTaskId, placement}`, возвращает **200 TaskResponse** и использует обычный `Idempotency-Key`. Действуют текущий `task.edit`, workspace barrier, planning guard/census и атомарность обычных task commands. Anchor активен, принадлежит тому же проекту и parent; для roots section выводится из anchor и проверяется. Move не reparent. Сервер выполняет splice полного порядка `(position, id)` и нормализует позиции полного проекта. Реальные изменения metadata получают revisions/audit; true adjacent no-op ничего не меняет. Migration для task order не нужна.

Для одной законченной строки добавлен `POST /api/v1/workspaces/:workspaceId/tasks/rows` → **201 TaskRowResponse**. Строгое тело содержит `task` и необязательные `fields`, `plan`, `actual` ([task-row.ts](../packages/contracts/src/task-row.ts)). Одна транзакция и один `task.row.create` receipt объединяют task, первые custom values и явно выбранные plan/fact. Ошибка не оставляет часть задачи, work package, renumbering, value или часы.

Plan и actual несут явные period/membership IDs: «сейчас», человек или неделя не подразумеваются. Ноль, null и отсутствие значения различаются. Plan относится ко всему work package; detail subtask разделяет пакет родителя, поэтому это не дополнительная per-task allocation. При существующем commitment требуется его revision и сохраняются allocations/state; removed commitment не восстанавливается автоматически. Существующие роли, field locks, cutoff/period policies и права на часы продолжают действовать.

Только для rows route transport cap — **1 MiB**; общий **16 KiB** остальных endpoints не увеличен. Некоторые формально schema-valid большие наборы значений могут не поместиться. **413 PAYLOAD_TOO_LARGE** отклоняется до domain call, без записи; клиент должен оставить неотправленный draft для сокращения ([route](../apps/api/src/http/task-row-routes.ts)).
