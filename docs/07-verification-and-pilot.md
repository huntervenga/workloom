# Проверки и недельный пилот Workloom

План проверки от 16 октября 2026 года. Локальные проверки P0 и ограниченного P1a выполнены и записаны в [11](11-implementation-progress.md); ранние частичные checkpoints там сохранены как исторические. Остальные проверки приложения ниже, включая полный P1, запланированы и ещё не выполнены. Документационные проверки не являются подтверждением работоспособности продукта.

## Уровни проверки

| Уровень | Что доказывает | Чем проверять |
| --- | --- | --- |
| Domain unit | Формулы, policy decisions, state transitions | Vitest и fixed clock |
| PostgreSQL integration | Реальные constraints, transactions, revision conflicts, migrations | Изолированная тестовая БД выбранного major |
| HTTP contracts | DTO, ошибки, identity/workspace boundaries, повтор команд | Fastify inject + PostgreSQL для mutation scenarios |
| Component tests | Ввод, focus, parsing, конфликты, доступность редактора | Testing Library |
| Browser | Пользователь действительно проходит сквозной сценарий | Playwright, собранное приложение |
| Operations | Deployment, worker recovery, restore и старые вкладки | Staging rehearsal и release manifest |

Не перепроверять формулу тысячей JSX snapshots. Контроль исторических чисел выполняется на уровне domain/query/DB, браузер проверяет их корректное представление и взаимодействие.

## Гонки и повторные запросы

Проверять конкуренцию отдельными PostgreSQL connections, с управляемым порядком lock/commit; однопоточный unit test не доказывает отсутствие гонки.

- C01: update оценки одновременно с freeze; допускается ровно один последовательный исход, snapshot не содержит смешанной версии.
- C02: worker не работал во время cutoff; следующая mutation материализует план до изменения. Проверить существовавшие schedule instances.
- C03: две противоположные dependency edges одновременно; только одна проходит, цикл невозможен.
- C04: двойной attendance submit, в том числе с разными HTTP idempotency keys; одна запись источника на участника.
- C05: участник исправил время, затем организатор отправил старую attendance revision; конфликт вместо потери коррекции.
- C06: worker умер после domain commit до queue ack; повтор job не начисляет время и не создаёт встречу заново.
- C07: импорт оборвался после нескольких batches; restart продолжает без дублей и показывает completed/failed части.
- C08: mutation ответ потерян после commit; retry возвращает прежний результат после повторной проверки текущих прав.
- C09: тот же Idempotency-Key с другим payload даёт conflict, а не результат другой операции.
- C10: долгий import не удерживает workspace barrier на сетевых запросах; другие mutations получают bounded latency.
- C11: первая mutation после cutoff коммитит auto-freeze и возвращает domain outcome plan_locked (HTTP 409 FIELD_LOCKED), не применяя запрещённую правку; исключение handler не откатывает уже необходимый freeze.
- C12: personal freeze и project freeze сначала материализуют повторения в нужном горизонте; позднее пробуждение worker не добавляет дубли.
- C13: auto-freeze и допустимое последующее изменение в одной транзакции различаются event ordinal; snapshot соответствует состоянию до изменения.
- C14: correction переноса manual_period при параллельном изменении целевого значения отклоняется по revision без частичного void/записи.

## Повторения и календарь

Серия daily/weekly материализуется заранее на ограниченный горизонт, включая неделю фиксации. Проверки: count/until boundary, selected weekdays, skip, cancel, move внутри/между неделями, this-and-future, изменение участников и длительности.

DST fixtures должны проверять gap и overlap. Принятая политика: несуществующее локальное время переносится на ближайшее допустимое после разрыва; для неоднозначного берётся раннее вхождение. Смещение сохраняется в occurrence. Не превращать один календарный экземпляр в два при осеннем переходе. Изменение timezone будущей серии не переписывает UTC/date уже проведённых встреч.

Ссылки recording/summary существуют на occurrence, постоянный join URL — на серии. Изменение будущего расписания не переносит прошлую запись видео в новый день. Завершение понедельника не является условием появления пятницы.

## Доступ и приватность

Проверять как минимум: workspace owner, обычный участник, участник private meeting, пользователь без grant, revoked member и пользователь другого tenant. До P6 это fixture actors; в P6 повторить с реальными сессиями.

Для F12 проверить response bodies и DB query scope, а не только HTTP status. Каналы: task list/detail, search, counts, autocomplete, graph/Gantt, timeline/history, report/drilldown/export, attachment link/download, inbox/notifications, MCP, outbox delivery. Для внешних recording/summary URL проверка доказывает сокрытие метаданных в Workloom, а не отзыв доступа у провайдера. До реальных личных встреч проверить настройку доступа к записи в выбранном сервисе; Workloom не обещает сделать публичный URL приватным. Cached report не должен отдавать private totals после отзыва ACL. Запрос старого export повторно проверяет доступ.

Workspace owner управляет пространством, но не получает неявное чтение private meeting. Shared totals рассчитываются после фильтрации и обозначаются как доступные данные; не добавлять счётчик скрытых встреч. Отдельный агрегат private time не включать без явной политики. Участник сохраняет доступ к собственному времени как к личной записи, но при отзыве task grant запись не раскрывает название/ссылку задачи.

Проверки auth на P6: JWT signature/issuer/audience, callback/Origin/CSRF, session rotation/logout, revoked membership, несколько вкладок одновременно refresh. Попытка подменить actor/body/header в production игнорируется или отклоняется. Dev identity/switch routes не регистрируются в публичной APP_ENV=staging/production, а попытка запуска dev adapter в Railway отклоняется. Локальный dist smoke с NODE_ENV=production, APP_ENV=local, loopback и fixture БД проходит отдельно и не считается проверкой защищённого входа.

## UI и производительность

Browser acceptance: Enter создаёт строку; Tab сохраняет и переводит фокус; ошибки остаются у ячейки; переключение фильтра не теряет ввод; split/attendance/freeze показывают серверный результат; private row исчезает после смены actor и не остаётся в query cache.

Фиксированный performance fixture: 1 workspace, 6 человек, 1000 активных задач, до 3 уровней подзадач, 25 колонок, 10000 worklog revisions и 500 dependency edges. Это тестовый профиль пилота, не обещание предела продукта. Дополнительно smoke на 10000 задачах проверяет, что серверная pagination не заменена полной выгрузкой.

Начальные цели на указанной в отчёте машине/staging: p95 ordinary reads и cell writes до 500 мс без учёта внешней сети, первая интерактивная таблица до 2 секунд, локальный keyboard input до 100 мс. Измерять отдельно cold/warm и PostgreSQL lock wait. После первого замера скорректировать цели с объяснением; не объявлять их достигнутыми по unit tests.

Отдельно проверять клавиатурный путь создания dependency, видимость focus, contrast, editor labels и альтернативу графику в виде таблицы. Offline edits не обещаются: при потере соединения UI хранит видимый черновик и предлагает повтор, не ставит бесконечную скрытую очередь.

## Перенос команды

Минимальный пилот требует P0–P3, ограниченный импорт P5.4/P5.6 и P6. P4 и полный P5 могут ещё отсутствовать: их проверки маркируются not in pilot scope, а не pass. Перед общим выпуском полного MVP эти проверки обязательны. Если пилотный объём требует зависимостей или вложений, включить соответствующий модуль до переноса либо согласовать конкретное ограничение данных; ничего не удалять молча.

1. Выбрать одну рабочую неделю, незавершённые задачи и необходимые зависимости. Зафиксировать список source projects и mapping.
2. Dry run в staging: task/subtask counts, users, statuses, dates, custom values, hours, links и samples comments/attachments.
3. Утвердить конкретные исключения: неизвестный исполнитель, неоднозначный multi-home, отсутствующая история/дата факта, недоступное вложение. Не подставлять нули или администратора.
4. Сохранить import input hash, mapping version, Asana GIDs, Workloom IDs, reconciliation report и rollback/export plan.
5. После разрешения переключить только пилотный объём на Workloom. Asana остаётся архивом; новых записей пилота в двух системах одновременно не вести.
6. В середине недели проверить, что никто не заблокирован вводом/правами, и что все встречи правильно начисляются.
7. В конце недели закрыть факт и сравнить с ручным контролем 10–15 задач и всех созвонов. Собрать проблемы UX по частоте/влиянию.

Критерии принятия: нет необъяснённой потери/дублирования; исходный план восстанавливается; сумма часов совпадает с контрольной выборкой; участники выполняют ежедневную работу без второго списка; private leakage и ошибочное начисление устранены. Неясность данных может быть помечена и принята владельцем, но не превращается в pass.

При блокирующей проблеме остановить новые записи в затронутом сценарии, сохранить Workloom изменения, выгрузить их для контролируемого возврата. Нельзя просто загрузить старую БД поверх новых часов. Технический rollback описан в [08](08-railway-and-operations.md).

## Формат результата проверки

Для каждого этапа сохранить checked commit, environment, schema version, fixture version, commands и статусы pass/fail/blocked/skipped. Отдельными строками: HTTP/API bodies, JS/CSS assets, browser UI, authenticated flows, private access, old-tab upgrade, worker recovery, backup restore. Фактические результаты по этому формату ведутся в [журнале доказательств](11-implementation-progress.md).
