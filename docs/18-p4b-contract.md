# P4b: календарные даты, простой Gantt и baseline overlay — accepted bounded slice

Статус: **bounded P4b принят координатором 16 октября 2026 года после functional/visual gate**. P4a source `12f5dbd8c9d5af8c01070e0278ec1ec8fe499fe2`; новый P4b checkpoint фиксируется отдельно. Автор source — Codex gpt-6.1-sol high; текущая инструкция пользователя — только Codex, без Claude calls/probes. Принят manual-date срез, без pointer drag/resize/auto scheduling/full MVP. Источники: [P4a](17-p4-contract.md), [domain](03-domain-and-data.md), [implementation](06-implementation-plan.md), [immutable baseline](13-p2a-contract.md), [meeting](15-p3a-contract.md), [recurrence](16-p3b-contract.md).

## 1. Минимальный полезный результат

У обычной задачи есть nullable **date-only startDate** и существующий nullable dueDate. Пользователь видит простой календарный диапазон, может явно изменить даты одной/нескольких задач через общий read-only preview и atomic apply и сравнить текущие даты с **выбранным** immutable baseline. Одна дата не превращается в выдуманную длительность. Оценка WorkPackage, личный план и факт не меняются при сдвиге полосы.

Только ручные даты. Нет auto cascade, lag, critical path, resource levelling, пересчёта hours в рабочие дни, календарей отпусков/смен, historical dependency topology или отдельного scheduling engine. Текущие P4a edges используются для предупреждений, не выдаются за связи прошлого baseline. Gantt не расширяет права/источники встреч и не перемещает worklogs между периодами.

## 2. Additive Task совместимость

Миграция `0008_task_calendar_dates` добавляет `tasks.start_date` nullable SQL DATE. Существующие rows получают SQL NULL; старая колонковая проекция/IDs/revisions/история/JSON не переписываются. Fresh current Task reads всегда содержат startDate:null|date. Shared `taskSchema` добавляет **optional без default** startDate, чтобы прежний cached TaskDto и `snapshot.tasks` без поля оставались валидны и байтово прежними.

CreateTaskInput и UpdateTaskInput добавляют только optional nullable startDate **без default**; старые payloads после parsing сохраняют прежнюю форму/hash. Omitted означает «не менять», explicit null — очистить. Добавить startDate в task mutation keys; old dueDate parsing/defaults не меняются. Старый key повторяет исходный stored outcome без дорисованного startDate. UI не трактует отсутствие startDate в старом replay DTO как доказательство текущего NULL: инвалидирует current read, не затирает новые данные старым outcome.

Для новых SQL DATE writes нужен общий SQL-compatible validator: **реальные YYYY-MM-DD в0001..9999**, с точной leap-year проверкой и без Date.UTC remap годов0..99. Сам z.iso.date() недостаточен: потенциальный0000 PostgreSQL DATE не представляет. Helper возвращает исходную строку без coercion/нормализации/default, поэтому формы и hash ранее допустимых SQL-date payloads не меняются.0000 явно rejects, не превращается в0001. Не ужесточать задним числом historical JSON/custom-date readers, не связанные с SQL DATE; старый pinned JSON/replay остаётся нетронутым. Браузерная/серверная timezone не меняет date-only значение; не сериализовать его как локальный midnight/UTC instant. Если обе даты заданы, final effective startDate<=dueDate. При частичном UpdateTask проверка использует вторую текущую дату под barrier, а не только присланные поля. Domain и SQL CHECK защищают порядок; nullable стороны не создают ложного диапазона. Due inclusive: одинаковые даты — один календарный день.

## 3. Meeting boundary и snapshot locks

`meetingId` — canonical server locator до первого attendance. Любой generic startDate/dueDate write к meeting task отклоняется существующим meeting guard; добавить startDate в exhaustive protected-field list, включая task.create/update/import/internal helpers. Batch schedule также rejects meeting row до proposed writes. UI открывает MeetingDrawer/исходный period, не пытается изменить встречу обычной полосой.

В первом P4b meeting rows имеют отдельную подпись/ссылку «Встреча — открыть календарь», без редактируемой date-only полосы. UTC plannedStart, IANA zone, duration, roster, frozen calendar остаются единственной истиной P3. Не выводить meeting startDate из current dueDate/nominal date и не растягивать hours на календарную ось как task duration.

Наличие task в baseline — **snapshot**, не автоматический новый lock на все core date fields. P2a защищает явно выбранные custom values/estimate/commitments и meeting schedule; P4b не придумывает blanket date lock задним числом. Current ordinary dates могут изменяться по существующим правам, а overlay показывает разницу. Любая уже существующая применимая field/meeting/recurrence policy остаётся обязательной; будущая core-date lock policy требует отдельного freeze.

## 4. Preview/apply командный протокол

`TaskScheduleRowInput={taskId,expectedRevision,startDate:null|date,dueDate:null|date}`. Batch содержит1..100 уникальных задач **одного path project**, обе desired даты явные. Schema нормализует порядок rows по taskId перед новым command hash. Cross-workspace/неизвестный task404, доступная задача другого project422. Current task.read/task.edit проверяются для каждого target до stored replay. Archived task требует explicit restore; meeting task rejects422 с предложением guarded editor.

Read-only preview ничего не фиксирует/не materialize/не создаёт IDs. Под consistent read сервер проверяет desired final ranges и sources, возвращает source/desired rows, dependency comparisons, protected/recovery impacts и previewHash. Hash включает actor/current permission epoch, проект/target task revisions/dates/meeting marker, релевантные active dependency IDs/revisions и endpoint dates/status/context, successor policy revision, применимые baseline/meeting/field locks и recurrence readiness источники. asOfChangeSeq — read-version marker, не замена full manifest и не основание включать каждую постороннюю layout-правку в hash. Volatile wall-clock не включается как случайный salt; переход cutoff/past policy отражается в семантическом результате/source manifest.

Точный internal preview manifest v1: `{version:1,actorUserId,workspaceId,projectId,permissionEpoch,desiredRows,targets:[{id,revision,startDate,dueDate,meetingId,archivedAt}],dependencies:TaskDependencyDto[],endpoints:[{id,revision,startDate,dueDate,meetingId,context:DependencyTaskContextDto}],policies:ProjectDependencyPolicyDto[],locks:PlanningLock[],periods:[{id,revision,state,cutoffAt}],census:RecurrenceCensusAssessment[]}`. Complete census assessment сохраняется для релевантного planning period; incomplete assessment сохраняется для affected project periods независимо от принадлежности выбранному package. Arrays canonical sorted, IDs/versions/values берутся из одного consistent read. Include только источники, относящиеся к текущему typed footprint; labels/context для review входят своими revisions/значениями, если показаны как изменяемый source. В canonical hash нет isCutoffDue и текущего времени: cutoffAt/revision/state релевантного периода остаются источниками. Preview отдельно сообщает recoveryPeriodIds по текущему clock. Пока источники неизменны, повторный preview имеет тот же hash. Изменение readiness/locks/state меняет manifest.

Malformed/duplicate/out-of-range dates →400, foreign/denied →404/403 без раскрытия, stale expectedRevision →409 до preview. Authorized meeting/archived rows возвращаются как closed protected reasons `meeting_task|archived_task`; preview200 честно показывает невозможность apply. `recoveryPeriodIds` включает относящиеся к write-footprint pending/blocked census **и уже complete, но ещё unfrozen overdue cutoff**. UI разрешает Apply лишь когда protectedTargets/recoveryPeriodIds пусты, предлагает существующий explicit readiness/materialize recovery, затем новый preview; preview сам не materialize и не freeze. Apply всё равно заново проверяет всё: если cutoff наступил после чистого preview, может закоммитить **только existing tagged pre-handler prerequisite outcome** и вернуть PREVIEW_STALE после commit; ни одна proposed date при таком исходе не сохраняется. Любой иной поздний отказ — полный rollback, не произвольный committed rejection.

Apply принимает тот же normalized desired batch + previewHash, Idempotency-Key. Под единственным workspace barrier повторяет current ACL, current-source manifest, expected revisions и domain guards. До **любых proposed date writes** валидирует весь batch и complete source state. Нельзя вызывать public updateTask в цикле, открывать nested UOW или catch-and-commit после частично выполненного handler.

Общие `assertTaskDateRange`/`assertOrdinaryTaskDates` используются TaskApplication и новым batch application, чтобы range/meeting/current policy нельзя было обойти другим transport. Existing `createPlanningMutationGuard` получает exhaustive schedule intent/footprint; same-TX cutoff/recurrence materialization/rejection protocol сохраняется. При preview race с автоматической фиксацией — existing tagged **pre-handler** committed PREVIEW_STALE, затем throw после commit; unexpected failure откатывает всё. Для task.schedule.apply pre-handler явно сравнивает relevant manifest после собственной due-freeze и, если она его изменила, сохраняет tagged PREVIEW_STALE до запуска date handler; обычный throw не должен откатывать эту prerequisite и создавать вечный stale-loop. Общий status-transition policy P4a остаётся обязательным для любого status write; date apply status не меняет.

Один stale/foreign/archived/meeting/invalid-range target отклоняет весь proposed batch. Нет частичного success/невидимой части range. True date no-op в НОВОМ schedule.apply не поднимает task revision/не добавляет task audit/outbox; generic TaskApplication PATCH сохраняет прежнее поведение revision/audit даже для одинакового присланного значения; key receipt всё ещё может сохранить исходный успешный результат. Реальная правка увеличивает task revision и пишет task audit/outbox в той же transaction; package/participant revisions не меняются. Proposed mutation target hash включает projectId и полный normalized row payload. Старые task.create/update command names/hashes остаются прежними.

## 5. Dependency даты: предупреждения без скрытого enforcement

P4a finish-to-start здесь даёт date comparison только для двух обычных задач при известном predecessor.dueDate и successor.startDate. Если **любой endpoint — meeting task** по server-owned meetingId, comparison всегда `state:unknown,reason:meeting_calendar`: generic dueDate может отражать лишь день начала, а не конец встречи с UTC/IANA и переходом через полночь. Не выводить compatibility/conflict из этой date-only проекции; P3 calendar остаётся authority, ссылка открывает guarded MeetingDrawer. Это не меняет authoritative status blocking P4a. Due inclusive: successor.startDate<=predecessor.dueDate — conflict; обе даты есть и successor.startDate>predecessor.dueDate — compatible; отсутствует нужная сторона обычной задачи — `state:unknown,reason:missing_date`, а не «конфликтов нет». Для compatible/conflict reason отсутствует; closed enum unknown reason — ровно `meeting_calendar|missing_date`, meeting_calendar имеет приоритет при обоих условиях. Archived/cancelled unresolved predecessor не исчезает из источников. Status-only enforce P4a **не превращается в date enforcement** этим срезом.

Для edge с двумя targets batch сравнивает обе desired даты одновременно; с внешним endpoint использует current authorized date/context того endpoint. Никакого каскадного сдвига другой задачи. Сведения о cross-project endpoint возвращаются с тем же project/status context P4a. Preview явно помечает current dependency и не утверждает historical topology.

Предложенный bound: максимум1000 incident dependency comparisons на один preview/context. Если набор больше,422 «сузьте набор», без silent truncation или ограничения global cycle/status checks. Это ограничение нового review read, не переписывание старых TaskApplication hash/duedate contracts. Source footprint включает target project и участвующие endpoint projects, не угадывается по viewport и не расширяется на весь workspace без причины.

## 6. Новый read projection вместо второго task filter engine

Список/фильтры/пагинация задач остаются существующим GET tasks. Gantt использует эти current rows. Для видимых task IDs добавляется одна batch projection **<=100 IDs**, отдельные wire CSV и normalized-array domain schemas. Больше100 загруженных rows — несколько явно scoped batches; repeated rows merge по task ID и numeric asOfChangeSeq, не суммируются. Между batches нет обещания единого глобального snapshot; финальный preview/applied batch всегда consistent и целиком проверен.

Предложенный `TaskScheduleContextDto={projectId,asOfChangeSeq,baseline:null|BaselineScheduleContextDto,rows:TaskScheduleContextRowDto[],comparisons:ScheduleDependencyComparisonDto[]}`. Row содержит taskId, обязательный положительный `taskRevision=currentTask.revision`, current `{startDate,dueDate}`, meetingId|null, editableDates:boolean, authoritative P4a blocking summary и baselineDates. У fresh projection current startDate известен; это не backfill в старый stored TaskDto. Root IDs проверяются по path project, source/capability проверяются текущие. Graph bounds не подменяют этот read.

`ScheduleDependencyComparisonDto={dependencyId,predecessorTaskId,successorTaskId,state:'conflict'|'compatible'|'unknown',reason?:'meeting_calendar'|'missing_date',predecessorDueDate:date|null,successorStartDate:date|null,predecessorContext:DependencyTaskContextDto,successorContext:DependencyTaskContextDto}`. Shared comparison schema — discriminated union: unknown требует один closed reason, conflict/compatible запрещают reason. Это текущие разрешённые данные, не приватный neutral-count контракт. P4b, как P4a, workspace-visible; private ACL/Auth не заявляются.

## 7. Baseline overlay с явным происхождением

BaselineId выбирается пользователем, никогда не скрыто «последний baseline». `BaselineScheduleContextDto={baselineId,periodId,scope:'self'|'project',membershipId:null|UUID,frozenAt,sourcePersonalBaselineIds}`. Reader применяет текущую authorization политику существующего baseline read и проверяет project/workspace. Исторические даты берёт **только из сохранённого snapshot.tasks**, без current-date joins. Этот DTO не обещает historical row labels: обычный current task title можно показывать лишь как текущий, без приписывания его baseline. Выбранные baseline scope/period/membership/frozenAt/sourcePersonalBaselineIds читаются именно из сохранённого документа, не подменяются текущими project/person labels; current labels могут отображаться отдельно с явным отличием. Current task доступ всё равно обязателен; отозванный доступ скрывает cached overlay.

Row `baselineDates` — discriminated union:

- `{state:'not_selected'}` — baseline не выбран;
- `{state:'not_in_baseline'}` — выбран, но task в этом snapshot отсутствует;
- `{state:'captured',startDate:BaselineDateValueDto,dueDate:BaselineDateValueDto}` — обе стороны читаются из snapshot.

`BaselineDateValueDto={state:'not_captured'}|{state:'not_set'}|{state:'set',value:date}`. Property отсутствует в старом snapshot → not_captured; explicit null → not_set; конкретная дата → set. Никаких current-date fallback, переписывания JSON или приписывания старому baseline нового startDate:null. Task outside baseline не считается незапланированным по одному отсутствию даты.

P2a snapshot содержит cohort реальных commitments и связанных tasks, не весь проект. Overlay показывает scope/period/frozenAt и подпись покрытия; не заявляет полный проектный план. Существующее earliest numeric changeSeq правило personal→project sources сохраняется. Current edges отображаются отдельно как текущие. Historical topology требует новой explicit snapshot section в другом срезе.

Все пути под `/api/v1/workspaces/:workspaceId`. Public names ниже зафиксированы в `packages/contracts/src/schedule.ts`; `TaskScheduleApplication` в domain содержит ровно три метода.

## 9. UI lifecycle и честный календарь

Новая view `?view=gantt` переиспользует task filters/selection. Набор — загруженные доступные задачи с явной подписью, не весь проект без загрузки. Rows без дат остаются явной группой «Без дат». Только start или due → помеченный endpoint, не выдуманная полоса. Полоса с обеими датами включает due day. Не считать глобальные totals/completion/accuracy из viewport.

Ось всегда ограничена явным date-only окном `{windowStart,windowDays}`: default **28 дней**, переключение на84 дня для обзора; абсолютный максимум **366 дней** при любом zoom/ручном выборе. UI показывает обе включительные границы. Первое окно начинается с явно показанной текущей календарной даты `WorkspaceDto.timezone` (у ProjectDto нет timezone); пользователь может выбрать другую начальную дату. Состояние окна сохраняется при refetch/фильтрах/view switch; оно не вычисляется как min..max дат всех задач или baseline. Previous/next сдвигает начало ровно на текущий windowDays календарных дней; zoom меняет только windowDays в пределах1..366, не даты задач. На границах0001-01-01/9999-12-31 операции ограничиваются допустимым конечным окном или отключаются, без переполнения года.

Все вычисления оси — календарная date-only арифметика с явными годом/месяцем/днём, без миллисекундного шага86400000, локальных midnight или Date.UTC remap. Переход DST не добавляет/удаляет день; выбор browser timezone не сдвигает windowStart. Рендерится не более366 дневных ячеек/делений на ось и только загруженные строки. Диапазон0001..9999 не создаёт цикл по миллионам дней, огромную CSS width или координату за пределами окна: прежде геометрии берётся пересечение task/baseline range с окном. Длинные полосы обрезаются по краям с явными маркерами продолжения и текстовыми **исходными** start/due endpoint labels; полностью внешний диапазон имеет подпись «вне окна» и действие открыть ограниченное окно у выбранного endpoint. Один endpoint также отображается только в окне либо явно помечается вне окна. Baseline использует то же окно/clip, без расширения оси по historical dates. Ни navigation, ни clip, ни zoom не вызывают preview/apply и не меняют task dates.

Реализованный bounded UI использует текстовые date inputs и кнопки сдвига на день через тот же preview путь. Pointer drag/resize в текущий срез не вошёл и остаётся будущим дополнительным вводом, который также не должен писать немедленно. Preview показывает все original/desired dates и предупреждения; пользователь явно применяет. Рисование/zoom/scroll не меняет данные. Personal graph layout P4a и Gantt dates — разные writes.

Page-owned batch draft/command живёт выше drawer/filter/view и сохраняет original project/target IDs/revisions. Поздний preview применяется только к совпавшему normalized input/source scope. Refetch не перезатирает unsent dates. Pending/uncertain держит immutable original payload/key; новая форма не стирает held command. Stale409 → refresh sources и явный rebase expectedRevision из current context.taskRevision с сохранёнными typed dates, затем **новый preview**; неизвестный результат → exact explicit retry, без автоматической новой команды. Refresh/rebase никогда не меняет expectedRevision/input/key уже held uncertain command; это отдельный подтверждённый lifecycle после известного отказа. Actor/workspace boundary очищает cache/mutation scope по существующей политике. На390px доступен список+date editor без необходимости точного drag.

## 10. Gates до отдельного P4b acceptance

1. Real SQL/domain: date-only null/one endpoint/same-day/reversed range, leap/year edge и timezone/DST независимость; partial update final-range check. SQL invalid range rejected, old-column upgrade projection и старые input/hash/replay/pinned JSON byte equality.
2. Meeting generic startDate/dueDate и batch attempts отклоняются до proposed writes; planned UTC/IANA/roster/attendance/fact/recurrence baseline сохраняются. Ordinary task dates не меняют effort/participants/package/commitment/worklogs.
3. Preview→task revision/edge/status/policy/ACL/lock/readiness race → controlled409/review; один invalid/protected target не оставляет других dates/audit/outbox успеха. Unexpected late failure rollback; permitted committed prerequisite outcome сохраняет только разрешённые freeze effects.
4. Both batch endpoints используют desired values; outside cross-project/archived current predecessor не исчезает. ## 11. ADR P4b-01: clock crossing и prerequisite freshness

Согласовано координатором при source freeze: `isCutoffDue` удалён из canonical preview hash намеренно. Сам переход clock через cutoff не должен запрещать shared guard сохранить обязательную фиксацию. Apply сначала проверяет прежние semantic sources, затем mandatory guard выполняет due-freeze/census, затем ДО любых proposed date writes сравнивает тот же manifest. Изменившая релевантные period/locks/readiness prerequisite сохраняет только baseline/audit/outbox и typed durable PREVIEW_STALE; date writes отсутствуют. Unrelated completed-period freeze и personal layout не входят в target semantic source manifest и сами не делают preview stale. Уже изменившиеся до prerequisite sources дают обычный PREVIEW_STALE без новых эффектов. Unexpected failure всегда rollback.

Период релевантен date source, когда его commitments содержат выбранный task/package; locks фильтруются по выбранным task/package identities. Неполный recurrence census affected endpoint projects включается отдельно и виден как recovery. Hash не использует whole TaskDto, global changeSeq или wall-clock salt.

Guard-only schedule target включает `affectedProjectIds`, полученные из того же текущего authorized endpoint projection под barrier (target project и все incident endpoint projects). Canonical persisted command target/hash остаётся `{projectId}` плюс normalized public input; derived footprint не меняет пользовательский hash. Preview recovery и apply census используют один footprint, поэтому cross-project pending census не обходится прямым apply.
