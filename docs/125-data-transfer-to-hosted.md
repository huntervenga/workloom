# Перенос данных из локальной базы на хостинг (dump и restore)

Статус: инструкция + **репетиция на локальной копии** (23 октября 2026). На Railway ничего не выполнялось. Читать вместе с [124](124-railway-cloudflare-deploy.md): сначала поднимается пустой хостинг, потом переносятся данные.

## Что проверено репетицией

Дамп локальной `workloom_dev` (PostgreSQL 17.5) был восстановлен в отдельную пустую базу тестового кластера. Результат: `pg_restore` без ошибок; число строк совпало в `tasks` (3265), `task_field_values`, `task_project_placements`, `projects`, `memberships`, `users`, `shared_auth_identities`, `generic_report_definitions`, `audit_events`; в журнале миграций 34 записи; собранное приложение на этой копии ответило `/healthz/ready` = 200 (`database: ok`, `schema: ok`). Затем копия удалена. **Не проверено:** сам Railway (версия PostgreSQL, TLS публичного прокси, права роли), вход реальных пользователей на хостинге, команда `hosted-migrate` после восстановления.

## Что именно переносится и что нет

- Переносится **вся база целиком** (7 workspace: Balancy, личные и демонстрационные, synthetic). Выборочного экспорта одного workspace в проекте нет: связей между 107 таблицами слишком много. Если нужны только Balancy и ваши личные workspace, это отдельная работа; пока решайте, согласны ли вы на лишние демо-данные в проде.
- **Не переносятся:** очередь воркера (схема `workloom_queue`, воркер на хостинге выключен), активные веб-сессии и попытки входа (`shared_auth_sessions`, `shared_auth_login_attempts`: там зашифрованные токены под локальным `AUTH_SESSION_KEY`, на хостинге они бесполезны и небезопасны).
- **Переносятся, но отзываются:** записи персональных токенов (`api_tokens`) и локальных MCP-учёток. Строки нужны, потому что на них ссылается аудит; секреты хранятся только как хэши, поэтому после восстановления токены надо отозвать, иначе локально выданный токен заработает на проде.
- Пользователи входят через общий Auth (`auth.pavelignatov.com`): привязка идёт по паре «issuer + subject» (таблица `shared_auth_identities`, сейчас 2 записи). Поэтому после переноса тот же Google-аккаунт попадёт в свой прежний профиль и свои workspace. Если у вас в проде другой `AUTH_ISSUER`, привязки не совпадут.

## Правила безопасности

1. Восстанавливайте **только в пустую базу** (свежая база Railway до первого входа и до миграций). Восстановление поверх базы с данными пользователей перезапишет или сломает их; для непустой базы этой инструкции нет.
2. Дамп содержит все данные команды (имена, почты, задачи). Не храните его в репозитории и в публичных каналах; после переноса удалите копии.
3. Версия `pg_dump` должна быть не ниже версии сервера-источника (17), а сервер Railway не старше 17. Проверьте до начала: `SHOW server_version;` на Railway.
4. Перед восстановлением сделайте бэкап Railway (даже пустой базы) и заморозьте работу в локальном приложении: всё, что вы измените после снятия дампа, на прод не попадёт.

## Порядок действий

### 1. Подготовка

- По [124](124-railway-cloudflare-deploy.md) создана новая пустая база Railway. **Приложение пока не запускайте и не деплойте**: Pre-deploy и старт API теперь автоматически применяют миграции. Сначала восстановите дамп в пустую базу; схема и журнал миграций приедут вместе с ним. Если приложение уже создало схему, эта база больше не подходит для восстановления по данной инструкции.
- Локальный код и база на одной версии: в журнале 34 миграции, как в сборке, которую вы деплоите. Проверка: `psql "$DATABASE_URL" -Atc "select count(*) from drizzle.__drizzle_migrations"` → `34`.

### 2. Снять дамп (локально)

```sh
export PATH="/opt/homebrew/opt/postgresql@17/bin:$PATH"
set -a; . ./.env; set +a          # даёт DATABASE_URL локальной workloom_dev
pg_dump --format=custom --no-owner --no-acl \
  -N workloom_queue \
  --exclude-table-data=public.shared_auth_sessions \
  --exclude-table-data=public.shared_auth_login_attempts \
  --file="$HOME/workloom_for_hosted.dump" "$DATABASE_URL"
```

`--no-owner --no-acl` нужны, чтобы имена ролей локальной базы не просочились на хостинг.

### 3. Восстановить в Railway

Возьмите **публичный** адрес базы из переменной `DATABASE_PUBLIC_URL` сервиса PostgreSQL (она нужна, потому что приватный `*.railway.internal` недоступен с вашей машины). Не вставляйте её в чат и в историю команд на общем компьютере.

```sh
export TARGET='<DATABASE_PUBLIC_URL из Railway>'
psql "$TARGET" -Atc "select version(), count(*) from information_schema.tables where table_schema='public'"   # должно быть 0 таблиц
pg_restore --no-owner --no-acl --exit-on-error -d "$TARGET" "$HOME/workloom_for_hosted.dump"
```

`--exit-on-error` остановит процесс на первой ошибке, чтобы не получить полу-базу. При ошибке удалите всю схему (`DROP SCHEMA public CASCADE; DROP SCHEMA drizzle CASCADE; CREATE SCHEMA public;`) или пересоздайте базу и начните заново. Если соединение рвётся по TLS, добавьте в адрес `?sslmode=require`.

### 4. Отозвать токены и проверить

```sh
psql "$TARGET" -c "update api_tokens set revoked_at = now() where revoked_at is null"
psql "$TARGET" -Atc "select 'ledger', count(*) from drizzle.__drizzle_migrations"        # 34
psql "$TARGET" -Atc "select 'tasks', count(*) from tasks"                                # как локально
psql "$TARGET" -Atc "select 'sessions', count(*) from shared_auth_sessions"              # 0
```

Сравните числа с локальными (`tasks`, `projects`, `memberships`, `task_field_values`). Затем сверка манифеста миграций командой `hosted-migrate` из §5 документа 124 (с тем же `--expect-count 34` и SHA): после восстановления она должна сообщить «ничего применять». ПРОВЕРИТЬ: поведение на восстановленном журнале я не прогонял.

### 5. Проверка приложения

1. `https://workloom.pavelignatov.com/healthz/ready` → 200.
2. Войти своим Google-аккаунтом: вы должны попасть в прежний профиль и увидеть Balancy, недельные проекты, отчёты. Если вам открылся новый пустой workspace, значит привязка Auth не совпала (другой `AUTH_ISSUER` или `sub`): остановитесь и не продолжайте работу.
3. Откройте неделю 42 и страницу Reports, сверьте несколько задач с локальной копией.
4. Выдайте новый персональный токен на странице Integrations (старые отозваны) и проверьте `GET /api/public/v1/me`.

### 6. После переноса

- Удалите дамп с диска (`rm "$HOME/workloom_for_hosted.dump"`) и очистите переменную `TARGET`.
- С этого момента **прод становится источником правды**: повторный дамп поверх него не накатывайте. Для дальнейших обновлений недель используйте импорт Asana на хостинге (страница Projects → Import) либо синхронизацию, но не restore.

## Обновление недели из свежей выгрузки Asana (то, что мы сделали с неделей 42)

Для локальной базы я синхронизировал неделю 42 из `42_week.csv` + `42.json` без пересоздания проекта (скрипт был одноразовым, лежит вне репозитория). Принцип: задачи сопоставляются по Asana GID; для общих задач обновляются завершение, часы оценки/факта, теги и названия; новые задачи создаются; задачи, которых нет в выгрузке, **не удаляются** (их решение остаётся за человеком). Удалять проект и импортировать заново нельзя: у недель общие канонические задачи, а импортёр отказывается пересоздавать тот же источник в другом журнале ([108](108-reusable-asana-import.md)). Оформление этого скрипта как штатной команды — отдельная работа; до тех пор такое обновление выполняется вручную по запросу.
