# Выкладка Workloom на Railway + Cloudflare

Статус: **инструкция, ничего не выложено**. Написана 23 октября 2026 по состоянию кода `codex/bootstrap-plan` после ревью ([123](123-security-and-correctness-review.md)). Построена по схеме других сервисов Павла (LiveLoop, Round Table, Balancy Analytics): Railway для бэкенда и базы, Cloudflare для домена, общий Auth на `auth.pavelignatov.com`. Исходные требования к хостингу и все ограничения — в [85](85-hosted-runtime-preparation.md).

Чего я **не** проверял и что нельзя считать подтверждённым: сборку Docker-образа (демон Docker на этой машине не запускается), поведение Railway и Cloudflare (команды и названия экранов могут отличаться, сверяйтесь с их документацией), настоящий вход через Google на HTTPS, восстановление из бэкапа Railway. Эти пункты помечены «ПРОВЕРИТЬ» ниже.

## Как это устроено (и чем отличается от LiveLoop)

```
Браузер ──HTTPS──> Cloudflare (DNS, прокси) ──> Railway: сервис workloom ──приватная сеть──> Railway: PostgreSQL
                                                  │  один Node-процесс отдаёт:
                                                  │  /app (веб), /api, /api/public/v1, /mcp, /docs, /healthz/ready
                                                  └─ вход через https://auth.pavelignatov.com (уже существует)
```

- **Cloudflare Pages не нужен.** У LiveLoop фронтенд лежит на Pages, а API на Railway. У Workloom веб собирается в образ и отдаётся тем же процессом (так нужно для Secure-кук, CSP и одного origin). Cloudflare используется только для DNS и (по желанию) прокси.
- **Воркер выключен.** В контейнере нет фонового воркера, поэтому заморозки и материализация встреч делаются вручную (как и сейчас локально). Это ограничение пилота.
- **Одна реплика.** Лимиты запросов считаются в памяти процесса. Держите ровно один экземпляр сервиса.
- Имя сайта: `https://workloom.pavelignatov.com` (задано в [85](85-hosted-runtime-preparation.md)). Если выберете другое, везде ниже подставьте его.

## 0. Перед началом (на вашей машине)

1. Влейте ветку `codex/bootstrap-plan` в `main` (или решите, с какой ветки выкладывать). Проверьте, что дерево чистое: `git status`.
2. Локально должно быть зелёным: `npm run check`, `npm run build`, юнит-тесты (2464). Известно красными остаются два теста исторических миграций (0024 и 0029): они проверяют уже применённые миграции и не влияют на выкладку.
3. Установите Railway CLI (`npm i -g @railway/cli`) и войдите: `railway login`. Для Cloudflare достаточно веб-кабинета.

## 1. Railway: проект, база, сервис

1. В Railway создайте **новый проект** `workloom` (отдельный от LiveLoop и Auth).
2. Добавьте базу: **New → Database → PostgreSQL**. Другой сервис с базой не используйте: `DATABASE_URL` должен вести на отдельную базу этого проекта.
3. Добавьте сервис приложения: **New → Empty Service**, назовите `workloom`. Подключение GitHub-репозитория для автодеплоя **не включайте** (как у LiveLoop: выкладка только осознанная, чтобы пуш в `main` не перезапускал прод).
4. В настройках сервиса: Builder = Dockerfile (подхватится из `railway.json`: `Dockerfile`, healthcheck `/healthz/ready`, таймаут 120 секунд, перезапуск при ошибке до 3 раз). Replicas = 1. Cron и pre-deploy команды **не задавать**.
5. Привяжите CLI к проекту: из корня репозитория `railway link` (проект `workloom`, сервис `workloom`).

## 2. Переменные сервиса `workloom`

Задайте в **Variables** сервиса. Значения секретов не коммитьте и не вставляйте в чат.

| Переменная | Значение | Комментарий |
| --- | --- | --- |
| `APP_ENV` | `production` | для пробной выкладки сначала можно `staging` |
| `NODE_ENV` | `production` | включает раздачу веба из образа |
| `AUTH_MODE` | `shared` | `dev` на хостинге запрещён |
| `HOST` | `0.0.0.0` | |
| `PORT` | задаёт Railway сам | в Dockerfile `EXPOSE 8080`; при привязке домена укажите порт, который показывает Railway |
| `DATABASE_URL` | ссылка на переменную базы: `${{Postgres.DATABASE_URL}}` | приватный адрес `*.railway.internal`, sslmode не нужен. Публичный адрес без `sslmode=verify-full` сервер отклонит |
| `AUTH_BASE_URL` | `https://auth.pavelignatov.com` | |
| `AUTH_ISSUER` | `https://auth.pavelignatov.com` | точно как выдаёт Auth |
| `AUTH_AUDIENCE` | `pet-projects` | |
| `AUTH_APP_ORIGIN` | `https://workloom.pavelignatov.com` | без пути и слэша |
| `APP_ORIGIN` | `https://workloom.pavelignatov.com` | можно не задавать; если задан, только этот origin |
| `AUTH_SESSION_KEY` | 32 случайных байта в base64url (43 символа) | сгенерируйте: `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`. Сохраните в менеджере паролей. **Один и тот же ключ между выкладками**: смена разлогинит всех |
| `TRUST_PROXY_HOPS` | `2` | см. ниже |
| `LOG_LEVEL` | `info` | |

Не задавайте: `DEV_ACTOR_ID`, `PG*`, `NODE_TLS_REJECT_UNAUTHORIZED`, `AUTH_JWKS_URL`.

**`TRUST_PROXY_HOPS` важен.** Лимиты запросов и защита от перебора токенов определяют клиента по адресу из `X-Forwarded-For`. С нулём все пользователи выглядят как один адрес прокси и делят один лимит. Перед сервером стоят Railway и (если включён оранжевый прокси) Cloudflare, поэтому начните с `2` (с серым облачком Cloudflare, то есть только DNS, ставьте `1`). ПРОВЕРИТЬ после запуска: с двух разных адресов сделайте частые запросы и убедитесь, что лимит одного не блокирует другого. Я не проверял, сколько ровно прокси добавляют Railway и Cloudflare.

## 3. Домен: Railway + Cloudflare

1. Railway → сервис `workloom` → **Settings → Networking → Custom Domain** → `workloom.pavelignatov.com`. Railway покажет CNAME-цель (вида `xxxx.up.railway.app`) и, возможно, TXT-запись для подтверждения.
2. Cloudflare → зона `pavelignatov.com` → **DNS → Add record**: `CNAME`, имя `workloom`, цель из Railway. Если Railway дал TXT, добавьте его тоже.
3. **SSL/TLS → Overview**: режим **Full (strict)**. Прокси (оранжевое облако) можно включить после того, как Railway выдаст сертификат и домен станет «active». Если сертификат не выпускается за прокси, на время переведите запись в «DNS only».
4. **Caching → Cache Rules** (по желанию): не кэшировать пути `/api/*`, `/mcp*`, `/auth/*`, `/healthz/*`. Файлы веба с хэшем в имени (`/app/assets/*`) можно кэшировать на долгий срок.
5. Не включайте в Cloudflare «Under Attack», переписывание HTML и «Rocket Loader»: они ломают CSP и скрипты приложения. Для HSTS приложение само отдаёт заголовок.

## 4. Auth: разрешить новый origin

Единый вход живёт в сервисе `auth` (Railway, репозиторий `/Volumes/PavelData/ai/auth`). Он принимает только origin из списка `ALLOWED_REDIRECT_URIS`.

1. В Railway откройте сервис **auth** → Variables → `ALLOWED_REDIRECT_URIS` и добавьте через запятую `https://workloom.pavelignatov.com`.
2. Перезапустите сервис auth. Это изменение чужого сервиса и боевых настроек входа: делайте его сами или дайте явное разрешение.
3. Необязательно, для аналитики: зарегистрируйте сервис командой из репозитория auth `npm run register-service workloom "Workloom" https://workloom.pavelignatov.com` (ключи покажутся один раз).
4. В Google OAuth ничего менять не нужно: callback у Auth общий (`auth.pavelignatov.com/auth/google/callback`).

## 5. Бэкап и миграция базы

База пустая, поэтому сначала миграции. Сервер сам **не** мигрирует базу при старте.

1. Включите бэкапы Railway для PostgreSQL (Database → Backups) и сделайте первый вручную. ПРОВЕРИТЬ, что восстановление в отдельную базу работает, до реальных данных.
2. Сверьте манифест миграций на вашей машине (на 23 октября 2026: **34 миграции**, SHA `27cbf97dcd0b74ef9ef1607a5d2286bbd7ba1b19270e1965538d087003731cfb`):

   ```sh
   npm run build:libs
   node -e 'import("@workloom/db").then(m=>{const e=m.readExpectedMigrations();console.log(e.length,require("node:crypto").createHash("sha256").update(JSON.stringify(e),"utf8").digest("hex"))})'
   ```
3. Деплой образа (шаг 6) выполните **до** миграции: скрипт лежит в образе. Приложение сначала ответит 503 на `/healthz/ready` (схема отсутствует), это нормально.
4. Запустите миграцию внутри Railway, где доступен приватный адрес базы (число и SHA подставьте из шага 2):

   ```sh
   railway ssh --service workloom -- node scripts/hosted-migrate.mjs --apply --expect-count 34 --expect-manifest-sha 27cbf97dcd0b74ef9ef1607a5d2286bbd7ba1b19270e1965538d087003731cfb
   ```
   ПРОВЕРИТЬ: доступность `railway ssh` на вашем тарифе и версии CLI. Альтернатива: запустить ту же команду локально с `DATABASE_URL`, указывающим на **публичный** адрес базы с `?sslmode=verify-full`. Сертификат TCP-прокси Railway может не пройти `verify-full`; тогда используйте путь через `railway ssh`.
5. После успеха `/healthz/ready` должен вернуть 200 (`database: ok`, `schema: ok`).

## 6. Выкладка образа

Из чистой закоммиченной копии (как у LiveLoop, никаких автодеплоев):

```sh
git status            # должно быть чисто
railway up --service workloom --ci
```

Сборка идёт по `Dockerfile` (Node 24, `npm ci`, сборка библиотек, API и веба, `npm prune`), старт `node apps/api/dist/main.js`. На этой машине я прогнал те же шаги в чистой копии без Docker: `npm ci` 9 секунд, сборка и `prune` прошли, а собранное урезанное дерево стартует и отдаёт `/`, `/app`, `/docs`. Сам образ не собирался. Прежние попытки собрать образ упирались в 20-минутный таймаут сети внутри Docker, а не в код. Если сборка на Railway зависнет на `npm ci` или `npm prune`, повторите деплой.

## 7. Проверка после выкладки

1. `https://workloom.pavelignatov.com/healthz/ready` → 200 с `database: ok`, `schema: ok`.
2. `/` (лендинг), `/app` (приложение), `/docs` (публичная документация API) открываются, в консоли браузера нет ошибок CSP.
3. Войдите двумя разными Google-аккаунтами. Каждый должен получить **свой** пустой workspace. Проверьте, что один не видит данные другого.
4. Создайте проект, задачу, комментарий с @упоминанием; создайте и отзовите персональный токен на странице Integrations; вызовите `curl -H "Authorization: Bearer wlm_pat_…" https://workloom.pavelignatov.com/api/public/v1/me`.
5. Подключите MCP: `claude mcp add --transport http workloom https://workloom.pavelignatov.com/mcp --header "Authorization: Bearer wlm_pat_…"`.
6. Обновите страницу, которая была открыта до выкладки: должно появиться «Workloom has been updated» с кнопкой обновления. Образ не хранит старые хэшированные файлы, поэтому старые вкладки после каждой выкладки будут просить обновиться.
7. Проверьте восстановление: бэкап → отдельная база → `readiness`.

## 8. Перенос ваших локальных данных

Локальная база `workloom_dev` (Balancy, недельные проекты, отчёты) сама на хостинг не попадает: первый вход создаст пустой workspace. Пошаговая инструкция с репетицией на локальной копии: [125](125-data-transfer-to-hosted.md) (дамп, восстановление **только в пустую** базу, отзыв токенов, проверка). Это операция над боевой базой, поэтому выполняйте её сами или дайте явное разрешение. Важно: миграции из §5 в этом случае не запускаются, схема и журнал приезжают вместе с дампом.

## 9. Откат и эксплуатация

- **Откат кода:** Railway → Deployments → предыдущий деплой → Redeploy. Миграции вперёд-только: если миграция уже применена, старый образ увидит схему «из будущего» и ответит 503. Перед миграцией делайте бэкап.
- **Секреты:** `AUTH_SESSION_KEY` не менять без необходимости; при утечке сменить, все сессии сбросятся.
- **Лимиты:** лимиты запросов действуют внутри одного процесса, поэтому реплика одна. Токены без ограничения по workspace (`workspaceIds = null`) дают доступ ко всем workspace владельца: на хостинге выдавайте токены с явным списком.
- **Мониторинг:** Railway healthcheck проверяет только запуск. Подключите внешний пинг `/healthz/ready` (например, Better Stack/UptimeRobot).
- **Не сделано:** подтверждённая сборка образа, реальный HTTPS-вход, два реальных пользователя, управляемое восстановление, проверка старой вкладки на проде. Пока они не пройдены, выкладку лучше считать пилотом для 1–2 человек.
