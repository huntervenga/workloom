# Completion focus after a task moves

Completing a Board task moves its card between status lanes. The lane owns the card subtree, so even the stable native completion button is unmounted and replaced. A real [AppRoutes/ProjectPage regression](../apps/web/src/routes/ProjectCompletionFocus.test.tsx) first reproduced the failure: native Enter sent one confirmed status command, the old control became disconnected, Reopen appeared, and focus remained on the document body. The private RED log is `/private/tmp/workloom-completion-focus-red.log`. This source result supplements the separate compiled browser RED recorded in docs25; it is not compiled browser acceptance.

[useTaskCompletion](../apps/web/src/features/tasks/useTaskCompletion.ts) now keeps a focus lease for one explicit completion or reopen intent. The lease is separate from the existing command and retained-draft ledgers. [TaskCompletionAction](../apps/web/src/features/tasks/TaskCompletionAction.tsx) supplies the actual native trigger at direct activation or explicit menu selection, and registers its enabled rendered control in a layout effect. Both confirmed-receipt arrival and target readiness attempt the same one-time restoration, so either ordering works without delays, animation frames or polling. Old registration cleanup cannot remove a newly registered target for the same task.

Focus may return only to a connected, enabled completion control for the same task and exact confirmed task revision/status, with current edit permission, eligible task metadata and no replacement edit session. A matching current list head must exist; a missing, newer or ineligible head ends the lease. An older list waits for its authoritative refetch. This never expands a hidden table group, restores a filtered card, changes selection, opens a drawer or assumes an optimistic result.

An explicit pointer outside the action or its own menu, including a click on the document body, cancels the lease. Focus elsewhere, window blur, another accepted intent, owner unmount, permission loss, a new inline edit or replacement session also cancel it. ProjectPage supplies the presentation identity from actor/workspace/project, router location key, table grouping and all raw filter values; any change cancels restoration even if the user later returns before the old acknowledgement. The Page bridge is implemented by the ProjectPage owner. Natural focus loss caused solely by the old card unmount does not grant a new intent or cancel the existing one.

A lost response clears the original focus lease but preserves the exact existing unknown command. Clicking **Retry original status change** grants a fresh focus intent for that same held session. The existing exact request body and Idempotency-Key, retry/access guards, confirmation reconciliation, status policy and independent retained drafts remain unchanged. Confirmation through another recovery surface does not invent a focus claim.

The [hook focus tests](../apps/web/src/features/tasks/useTaskCompletion.focus.test.tsx) cover both handshake orders, late old-target cleanup, one-time consumption, presentation/permission/edit/session replacement, missing/newer/ineligible task heads and owner unmount. The real-page tests cover native Enter/Space across Board lanes, multiple done choices, reopen menu selection, outside pointer/focus/blur, changing presentation before a late acknowledgement and explicit lost-response retry with unchanged command bytes/key. Existing completion command, policy, Table control-identity and recovery tests remain the regression gates.
