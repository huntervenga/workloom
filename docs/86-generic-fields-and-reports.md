# Обычные поля и настраиваемые отчёты

**Подтверждённое направление продукта,18 октября2026. Не реализовано.**
Последнее уточнение пользователя имеет приоритет над прежними обязательными weekly/period сценариями.
План и факт должны быть обычными пользовательскими колонками; отчёт — сохранённой настройкой над выбранными полями.
Недельное планирование остаётся возможным шаблоном, а не условием существования проекта и его оценок.
Этот документ задаёт следующий продуктовый контракт, не объявляет новый API, migration или browser PASS.

## Что исправляем

Сейчас Workloom предлагает отдельный native period engine для personal plans, worklogs, freezes и pinned reports.
Подпись `Weekly plan · HunterVenga` сейчас обозначает недельный план выбранного участника, а не обычное пользовательское поле и не generic report builder.
Он сохраняет полезные гарантии истории, но не соответствует запрошенному простому повседневному сценарию.
Пользователю не нужно сначала создавать неделю, выбирать автора факта и изучать специальную модель, чтобы записать два числа.
Обычный проект должен работать с задачами, своими колонками и произвольно настроенным отчётом.
Текущие weekly views и данные считаются отдельным legacy/optional сценарием до явной миграции.
Их существование и прежняя техническая приёмка не означают, что generic report builder уже выполнен.
Ранее принятые runtime и evidence остаются исторически верными; меняется продуктовый приоритет.

## Пустой проект и колонки

Новый пустой проект не требует Plan, Fact, периода или запуска специального учёта времени.
Автор создаёт нужные ему поля через обычное управление колонками.
Для времени нужен тип duration: значение хранится в одной точной единице, интерфейс показывает понятные часы/минуты.
Правила округления и допустимый диапазон задаются типом, одинаковы для ввода, API и расчёта.
Пустое значение, явный0 и удалённая запись различаются.
Названия Budget, Spent, A/B или План/Факт не имеют специального смысла для сервера.
Колонку можно переименовать, скрыть, удалить/архивировать и создать заново обычным способом.
Новое поле с тем же названием получает новый ID; отчёт не перепривязывается к нему по имени.
Изменение типа существующего поля не должно молча переинтерпретировать старые значения.
Существующая оценка work package не становится обязательным источником generic duration-колонки.
Оценка задачи и обычный duration не зависят от наличия периода.

Шаблон «План и факт» создаёт две обычные duration-колонки и начальную настройку сравнения.
Он не создаёт скрытые глобальные native Plan/Fact fields и не захватывает одноимённые поля проекта.
Пользователь видит создаваемые колонки до подтверждения, может затем менять их как любые другие.
Применение шаблона не записывает часы, не фиксирует baseline и не создаёт период без отдельного выбора.
Удаление шаблонных колонок требует обычного подтверждения последствий для использующих их отчётов.

## Отчёт как сохранённая настройка

В Reports пользователь создаёт определение отчёта, выбирает проект и доступный набор задач.
Редактор показывает выбранные поля, расчёт, фильтры, группировки и необязательные даты на одном понятном экране.
Настройка хранит стабильные project/field/option IDs и собственную версию, а не только отображаемые названия.
Переименование поля меняет подпись, но сохраняет связь; недоступное или удалённое поле показывает явную проблему.
Фильтры и группировки выбираются из поддержанного каталога и проверяются сервером.
Первая ограниченная версия поддерживает sum, count и avg для совместимых типов.
Count обязан явно показывать, считает он задачи или заполненные значения; avg — какой набор заполненных значений делит.
Пользователь не передаёт SQL, произвольный код или неограниченное выражение.
Неподдержанное сочетание нельзя сохранять под видом успешно рассчитанного отчёта.

«План против факта» — конфигурация сравнения двух выбранных duration-полей.
Она показывает обе суммы, разницу и при допустимом знаменателе отношение.
Пустой/неизвестный план не превращается в0; отношение при0 или неизвестном плане не выдумывается.
Отсутствующий факт не означает завершённую работу за0 часов.
Частично заполненный набор сопровождается количеством/составом пропусков, а не ложным полным итогом.
Завершённость для оценки качества плана задаётся явным фильтром/правилом отчёта.
Незавершённая задача без факта не маркируется автоматически как переоценённая.

## Даты и произвольные интервалы

Фильтр дат необязателен: отчёт может считать все подходящие задачи без периода.
При включении пользователь выбирает конкретное поддержанное date-поле и правило попадания задачи в диапазон.
Это могут быть due date или обычная date-колонка; нельзя молча подменять их датой записи числа.
Редактор показывает выбранное поле и включённые границы, чтобы правило можно было проверить по строкам.
Доступны неделя, месяц и произвольный диапазон; week/month — только удобные presets одного фильтра.
Отчёт с диапазоном не создаёт native weekly period и не меняет длительности задач.
Date-only значения не сдвигаются через timezone; для timestamp-фильтра timezone и границы должны быть явными.
Запись task-level duration без даты работы нельзя распределить по дням недели автоматически.
Если нужна ежедневная детализация, это отдельный источник данных и последующий scope.

## Серверный расчёт и распределение

Итоги считает сервер по всему разрешённому scope, включая строки вне загруженной страницы.
Пагинация, сортировка, collapse и видимая часть таблицы не меняют итог отчёта.
Detail rows и totals относятся к одной проверяемой версии расчёта; UI не суммирует загруженные страницы как полный итог.
Сервер повторно проверяет доступ к проекту, задачам и полям; сохранённое определение не даёт вечных прав.
Недоступный источник не должен утекать через значения, счётчики или подписи групп.
Одна canonical task с несколькими placements учитывается один раз в заявленном scope.
Parent и child не должны дублировать один общий источник; правило включения показывается явно.

Phase1 выбирает простое распределение по одному основному исполнителю задачи, с отдельной Unassigned-группой.
Участники задачи не получают автоматически по полной копии её duration.
Несколько исполнителей требуют заранее выбранного правила: один ответственный, доли или явно перекрывающиеся группы.
Пока такое правило не реализовано, неподдержанный вариант блокируется, а не молча удваивает итог.
Для долей категории выбирается одно single-select поле; Uncategorized входит в тот же знаменатель.
Множественные tags могут пересекаться: режим либо явно показывает overlapping groups, либо требует эксклюзивного правила.
Сумма таких tag-групп не объявляется100% и не используется как общий total повторно.

## История, ограничения и исходный план

Используются обычные права и generic field history, deadline, per-actor lifetime quota и owner exceptions.
Те же проверки обязательны для inline, pane, bulk, import и других поддержанных writers.
Обычный owner подчиняется правилам; exception требует явного reason и фиксируется в разрешённой истории.
Manual field lock и уже защищённый baseline остаются абсолютными; generic report не открывает обход записи.
Добавление/переименование/изменение определения отчёта само по себе не редактирует значения и не сбрасывает quota.

Чтобы сравнить с начальным планом, пользователь явно сохраняет исходную версию выбранных полей и состава scope.
Нужно хранить field IDs/types, версии значений, правило группировки/атрибуции, filters и включённые task identities.
Позднее изменение числа остаётся текущей версией, исходное значение не переписывается.
Новые задачи, удаление/архивирование и изменения состава scope показываются отдельно от исходного набора.
Если значение тогда отсутствовало, original остаётся unknown; позднее число не становится первоначальным задним числом.
Снимок не может опираться только на загруженные строки или текущие подписи колонок.
Существующие freezes/pinned reports не пересчитываются под новую модель автоматически.

## Два ограниченных этапа

Phase1: обычные duration/date/существующие типизированные поля, сохранённое report definition и его editor.
Серверный query выполняет ограниченный каталог measures/filters/groupings и показывает totals+detail.
Простая assignee attribution, проверяемые unknown/zero, versioned initial-plan comparison входят в основной контракт.
Opt-in недельный template использует этот же путь, без обязательного native периода.
Первые примеры — произвольные Budget/Spent, A/B, категории и диапазон дат на обычном проекте.
Это план реализации: схемы/API/editor/запросы ещё предстоит спроектировать и проверить.

Phase2 при подтверждённой потребности: recurring templates, несколько участников и отдельные subject scopes.
Здесь уточняется личный план каждого человека, датированный worklog и распределение общего duration.
Существующие требования shared/recurring meetings, roster/attendance, приватности и исходных наблюдений сохраняются.
Упрощение generic отчётов не даёт права выкинуть эти требования или перенести их сложность в скрытые допущения.
До выбора модели legacy meeting/personal accounting продолжает жить отдельно.

## Переход без потери истории

Новая модель добавляется отдельно; старые worklogs, personal plans, freezes и отчёты сохраняются.
Owner сначала видит предлагаемый mapping источников и проверяемый preview, затем подтверждает его.
Legacy period/member значения нельзя слепо складывать в одно task-level поле.
Нужны явные правила task/package identity, attribution, units и выбранного временного scope.
Агрегат за период не получает выдуманную дату/дневной breakdown; суммы не превращаются в авторские worklogs.
Два одинаково названных поля не считаются одним источником.
Миграция должна показывать переносимые и непереносимые записи, исходные IDs и контрольные итоги.
Применение отдельно разрешает owner; exact retry не создаёт дубликаты и повторные initial snapshots.
Автоматических DB writes/reseed/drop или отключения legacy engine в этом документационном шаге нет.
Старые URL/report snapshots остаются читаемыми с явным обозначением их модели.

## Критерии принятия

Owner открывает пустой проект, создаёт duration-поля Budget/Spent или A/B и вводит значения без периода.
Он строит сравнение по выбранным IDs, переименовывает колонки и получает тот же верный результат.
Удалённое и созданное заново поле не подхватывается старым report definition автоматически.
Произвольный диапазон и preset одной недели используют выбранное date-поле и дают независимый ожидаемый результат.
Снятие фильтра дат не требует weekly period; оценки и ввод duration остаются доступны.
Null/unknown,0 и missing различимы в строках, totals и coverage; нет бесконечного/выдуманного ratio.
Server totals совпадают до/после pagination; tag/assignee/placement/parent правила не удваивают часы.
История, deadline/quota и owner exception работают одинаково через все writers, manual/frozen locks не обходятся.
Initial snapshot сохраняет старые значения и scope; новые задачи и поздние изменения объяснены отдельно.
Старые worklogs/baselines/reports читаются без изменений; mapping preview не пишет данные до подтверждения.
Отдельно проверяются API/PG, editor/browser, сохранённая настройка/reload и миграционные conservation oracles.
Ни один из этих acceptance пунктов данным документом не объявляется выполненным.
