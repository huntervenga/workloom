# Local recurrence worker

Use Node.js 24 and the repository's synthetic loopback PostgreSQL database. Root `.env` is loaded when present; existing process environment wins. `APP_ENV=local` and `AUTH_MODE=dev` are required independently of `NODE_ENV`. Hosted/Railway configuration and non-loopback database URLs fail before startup. This worker is not a production deployment or authentication integration.

Explicitly run the root `npm run db:migrate` and `npm run db:queue:migrate` commands before starting. The latter owns pg-boss schema 46 and both approved queue registrations. Run `npm run build`, then `npm run start --workspace @workloom/worker` from the root. Runtime startup verifies application readiness, exact queue schema and every approved main/DLQ option; it never creates or repairs schemas or queues.

The relay subscribes only to `recurrence.materialization_requested` version 1. Its enqueue and dispatch receipt share one database transaction. Unsupported versions of that exact type remain pending and visible; unrelated historical outbox rows are untouched. Each queue job calls one domain facade under the workspace write barrier. Pending chunks and stale-source replacement requests are committed by domain code, not a second worker transaction. A replayed delivery returns the durable original command result, including its original `createdCount`; it does not mean those rows were created again on this attempt. Process outcome counters count deliveries and are never accounting totals. The default two handlers are a **per-process** limit; the workspace barrier serializes protected writes across processes.

Default `LOG_LEVEL=info` emits JSON lines to stdout. After startup, `worker.health` and `worker.health_queue` appear immediately and every 30 seconds after the previous observation settles. Inspect these logs for status/reasons, relay heartbeat age, exact subscribed backlog/oldest age, unsupported subscribed rows, queue failure counts and retained dead-letter jobs. Queue counts are pg-boss reported/cached operational metrics, not accounting totals. Missing reads remain unavailable rather than becoming zero. No task titles, meeting URLs, payloads or database credentials are logged. `silent` intentionally suppresses logs.

SQL reads use finite PostgreSQL statement/lock timeouts. SIGTERM/SIGINT stops health/relay timers and new job intake, settles startup calls and in-flight observations/relay work, drains handlers, then closes owned pools exactly once. A signal during queue start or consumer registration cannot leave a late-created worker running. Queue graceful drain has the configured finite budget; jobs still active at expiry return through pg-boss retry semantics. P3b has no automatic DLQ replay or admin repair action.

`createMaterializationHandler(...).handle(jobs)` is the natural acknowledgement boundary for isolated real-queue tests: await the committed domain result, then a test-owned queue callback may throw once before pg-boss acknowledgement. Production has no crash-injection environment flag.
