# Local recurrence and cutoff worker

Use Node.js 24 and the repository's synthetic loopback PostgreSQL database. Root `.env` is loaded when present; existing process environment wins. `APP_ENV=local` and `AUTH_MODE=dev` are required independently of `NODE_ENV`. Hosted/Railway configuration and non-loopback database URLs fail before startup. This worker remains local synthetic infrastructure.

Explicitly run root `npm run db:migrate` and `npm run db:queue:migrate` before starting. The latter owns pg-boss schema 46 and four approved registrations, in this order:

- `workloom.recurrence.dead_letter.v1`
- `workloom.recurrence.materialize.v1`
- `workloom.planning.cutoff.dead_letter.v1`
- `workloom.planning.cutoff.v1`

Run `npm run build`, then `npm run start --workspace @workloom/worker` from the root only after the separate runtime upgrade/start gate is authorized. Startup verifies application readiness, the queue schema and every approved main/DLQ option before registering either consumer. Runtime never creates or repairs schemas or queues. Explicit queue installation adds missing registrations and refuses drift in an existing queue.

Separate relays subscribe only to `recurrence.materialization_requested` v1 and `planning.cutoff_requested` v1. Queue insertion and the outbox dispatch receipt share one database transaction. Unsupported versions or malformed rows of each exact subscribed type remain pending and visible while supported rows progress; unrelated outbox rows remain untouched. Cutoff sends carry the request's stored UTC `cutoffAt` as pg-boss `startAfter`. The queue persists that absolute instant, so restart cannot cause delivery before the requested deadline. A moved cutoff is revalidated by the domain under the workspace barrier; old queued jobs cannot freeze from old inputs.

Each job calls one authoritative facade under the workspace write barrier. Cutoff jobs contain IDs, revisions, a stored cutoff and source hash. Current stored cutoff and generation authorizers are revalidated by domain code; the worker supplies no actor and never substitutes another administrator. Pending, stale, not-due and blocked outcomes acknowledge the delivery. Their transaction owns any fresh request or bounded continuation; the handler has no continuation send, sleep or job loop. Only malformed jobs and unexpected failures use the finite queue retry budget. A lost acknowledgement can redeliver; durable receipts retain the original outcome and counts.

Cutoff discovery runs one bounded batch (default 50, maximum 100 targets) per completed poll. Its database adapter persists fresh requests and its seek checkpoint before advancing; it catches up after inactivity without depending on a surviving process timer. Polls never overlap. Relay/discovery failures use bounded exponential backoff to 30 seconds; blocked authority needs explicit domain recovery. The existing mandatory write guards still protect overdue periods while the worker is stopped or delayed. Automatic report creation remains deferred.

`JOB_CONCURRENCY` defaults to 2 and is at most 2. A single FIFO admission limit is shared by recurrence and cutoff handlers, so the combined number of executing domain jobs never exceeds that process setting. Each consumer can prefetch at most that many jobs; waiting jobs hold no application transaction. This is a per-process limit. The workspace database barrier serializes protected writes across processes.

Default `LOG_LEVEL=info` emits JSON lines to stdout. `worker.health`, `worker.health_cutoff`, `worker.health_discovery`, `worker.health_cutoff_outcome` and one `worker.health_queue` per registration appear immediately and every 30 seconds after the previous observation settles. Inspect status/reasons, both relay heartbeats and backlogs, exact-event unsupported rows, discovery failures, cutoff outcome counts, queue failures and retained dead-letter jobs. `runtime.health()` also exposes the shared active/waiting concurrency counts and the last bounded discovery result. Queue counts are pg-boss reported/cached signals; process counters count deliveries, including replay. They are not accounting totals. Missing reads remain unavailable. Logs contain no task titles, URLs, payloads or database credentials; queue failure outputs contain only safe error classifications. `silent` suppresses logs.

SQL reads and domain transactions use finite PostgreSQL statement/lock bounds. SIGTERM/SIGINT stops health, both relay timers and discovery, stops both consumers' new intake, settles startup calls and in-flight observations/discovery/relay batches, drains handlers, then closes owned pools once. A signal during startup or consumer registration cannot leave a late worker running. Queue graceful drain has the configured finite budget; still-active jobs return through pg-boss retry semantics. There is no automatic DLQ replay or queue repair action.

`createMaterializationHandler(...).handle(jobs)` and `createCutoffHandler(...).handle(jobs)` are natural acknowledgement boundaries for isolated queue tests. A test-owned callback can throw once after a committed domain result to exercise lost acknowledgements. Production has no crash-injection flag. Real queue tests use the standard disposable database helper and never the running application's database.
