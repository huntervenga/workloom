## Стек и границы

React + TypeScript + Vite для клиента, Node.js + TypeScript + Fastify для сервера, PostgreSQL + Drizzle для хранения. Клиент и сервер находятся в одной npm workspaces монорепе. Планируемая площадка — Railway; ресурсы ещё не созданы.

Первый локальный прототип работает без входа пользователя на синтетических участниках. Пользователи, пространства, роли и политики уже есть в модели; общий Auth подключается перед командным пилотом с реальными данными. Для этой первой недели достаточно таблицы, план/факта, встреч и минимального импорта; полный Gantt, builder и MCP можно завершить следом.

## Что реализовано в P1a

- Проекты с четырьмя статусами по умолчанию, секции и теги workspace со стабильными ID: создание и переименование в интерфейсе; архивирование этих сущностей без удаления строк — возможность API.
- Обычные задачи, видимые всему workspace: таблица и боковая панель для создания и редактирования; несколько участников и ответственный, статус, срок, приоритет, теги и текущая оценка; подзадачи-детализация и явный `added_scope`; архив и восстановление.
- Серверные поиск, фильтры и постраничная загрузка; итоги в таблице видимо относятся только к уже загруженным строкам.

Важное поведение:

- «Оценка задачи» — текущий общий бюджет WorkPackage на всю команду, а не baseline и не личные часы; персональный недельный план и его распределения задаются отдельно в P2a. Подзадача-детализация разделяет пакет родителя, поэтому итоги считаются один раз на `workPackageId`; `added_scope` создаёт новый пакет.
- Ревизии задачи, пакета и набора участников проверяются независимо; конфликт отклоняется, а не перезаписывается.
- Каждая команда атомарно записывает состояние, audit и outbox. Повтор с тем же `Idempotency-Key` и тем же содержимым возвращает сохранённый результат; другое содержимое с тем же ключом отклоняется.

## Что реализовано в P1b

- Колонки проекта девяти типов: текст, число, длительность в минутах, дата, одиночный и множественный выбор, участники, логическое значение и URL. Значения редактируются в панели задачи и показываются в таблице; тип колонки после создания неизменяем.
- Менеджер колонок для owner/admin: определения и варианты выбора со стабильными ID, порядок и видимость. Ширина поддерживается API и сохраняется интерфейсом; отдельного UI изменения ширины пока нет. Настройки менеджера общие для проекта; отдельные [личные предпочтения](docs/32-personal-table-columns.md) сохраняют порядок и видимость встроенных и пользовательских колонок без изменения общих настроек. Именованные сохранённые виды пока отсутствуют. Архивные варианты сохраняются в прежних значениях и истории, но не назначаются заново.
- История значений с постраничной загрузкой и неизменяемым снимком определения, названий вариантов и участника изменения. Переключатель записи действует на будущие изменения: включение не восстанавливает прошлое, выключение не удаляет уже записанное. Audit/outbox сохраняют метаданные операции, а полные старое и новое значения — только включённая история.
- Простая блокировка значений отдельной пользовательской колонки, действующая через общие domain-команды. Это не блокировка встроенной оценки и не недельный baseline. Ревизии определения, значения и расположения колонок проверяются независимо; `null`, `0`, `false` и отсутствие записи различаются.

## Что реализовано в P2a

В проекте открывается страница «Неделя»: периоды с семью календарными днями и timezone, персональные планы в минутах отдельно от общей оценки задачи, распределения по исполняемым задачам и нераспределённый остаток. Участник меняет свой план и факт; owner/admin — также чужие. Один commitment сохраняет ID для одной тройки period/package/member.

- Личная и проектная фиксация показывают серверный preview. Его hash проверяет все источники под общим барьером записи; устаревший preview требует повторного просмотра. Неизменяемые снимки хранят значения и подписи, включая неизвестные оценки.
- Наступивший cutoff проверяется и существующими командами задач/колонок. Сначала фиксируется старый план; запрещённая правка возвращает 409 с уже сохранённым baseline, повтор не создаёт второй снимок. Удаление участника или перенос задачи не снимают защиту выбранного значения и пакета, даже если оно отсутствовало или было null.
- После фиксации можно добавлять новую работу и записывать факт. Сервер отличает исходный план, добавленный объём и незапланированную работу. Detail child сохраняет package; родитель, дети, участники и теги не размножают часы.
- Ручной факт относится к человеку, задаче и целому периоду, без выдуманной дневной разбивки. Первая обычная запись не требует причины; коррекция или void создают новую неизменяемую ревизию с причиной. Явный ноль отличается от отсутствия/void.
- План/факт сохраняется как отдельный report run с исходным baseline, точными ревизиями факта, серверными итогами и графиком по людям; детализация загружается страницами. Правка факта не меняет прежний run. Неизвестные планы и пропуски факта видны через полноту/охват; точное отклонение при неполноте остаётся null. Недельные 360 минут сравниваются с недельным фактом, а не с полной оценкой пакета 1200.

Это ограниченный P2a: фактические проверки и оставшиеся ограничения описаны в [контракте 13](docs/13-p2a-contract.md) и [журнале 11](docs/11-implementation-progress.md). Наличие реализации не заменяет запись о завершённом browser/полном gate в журнале.

## Что реализовано в P2b

- Проект выбирает одно своё поле одиночного выбора как тип работы. Первая запись факта сохраняет стабильные ID и исторические подписи категории. Обычная коррекция часов переносит этот снимок; явная переклассификация требует причины и актуальных ревизий. Старый факт остаётся «Без категории», пока пользователь явно его не переклассифицирует.
- Отчёт по типам работает до фиксации baseline и сохраняется отдельным неизменяемым run: серверные доли по категориям и людям, общий знаменатель со всеми минутами «Без категории», постраничная детализация источников. Переименование варианта или коррекция факта не переписывают прежний отчёт. Подтверждённый ноль и void различаются; число записанных источников не выдаётся за полноту учёта времени.
- В таблице задач явно выбирается неделя для личного плана и собственного ручного факта. Сервер возвращает личные и командные минуты и полный итог пакета, включая незагруженные detail tasks; эти суммы не складываются повторно по участникам, тегам или дочерним строкам. Полный итог периода берётся из отчёта, а не из видимых строк.
- Миграция сохраняет прежние проекции колонок и pinned JSON. Прежний raw `work.set` с тем же ключом возвращает точный сохранённый ответ, включая старый ответ без поля category; новые чтения показывают legacy как «Без категории».

Контракт и ограничения — в [документе 14](docs/14-p2b-contract.md); фактические прогоны и отдельно проверенные browser-сценарии — в [журнале 11](docs/11-implementation-progress.md). P2b не вводит обязательный факт при Done, дневной учёт, встречи или универсальный конструктор отчётов.

## Что реализовано в P3a: разовые встречи и присутствие

Ограниченный P3a принят координатором после отдельных core/API/PostgreSQL, browser и визуальных проверок. Их точный охват и последовательность фиксирует [журнал 11](docs/11-implementation-progress.md).

- Одна датированная встреча — одна задача и один пакет с общим номинальным бюджетом duration × attendees. Создание даёт только предложения личного плана: часы плана или факта не начисляются автоматически. План применяется отдельной командой после серверного preview с текущими правами всех выбранных людей.
- Организатор и приглашённые задаются явно. Присутствие подтверждается атомарным набором: present, partial, отсутствовал с записанным нулём либо неизвестно без факта. Void исключает прежний источник; коррекция/восстановление используют тот же ID и причину. Изменение реальной длительности или ссылки само не переписывает записанные часы.
- Подтверждённый факт сохраняет точный occurrence snapshot. Независимая переклассификация поднимает worklog head; последующая attendance-команда проверяет этот текущий head и сохраняет категорию. Для отменённой/непроведённой встречи предусмотрен явный ноль по запланированному occurrence без выдуманного actual start.
- Неделя выбирается явно; перенос между периодами пока отклоняется. UI разрешает локальное время в выбранной IANA zone, отвергает DST gap и спрашивает offset при overlap; API принимает точный UTC instant. Персональные/проектные snapshots и когда-либо записанное attendance защищают исходное planned расписание/состав; generic task/manual команды не обходят meeting guards.
- Общие чтения и новые отчёты учитывают manual и attendance sources один раз. Старые manual endpoints, parsed inputs/hashes, точные cached outcomes и pinned JSON сохранены; это не сертификация старого browser bundle.

Встречи workspace-visible, без private ACL и внешней рассылки приглашений.

### Ограниченный P3b: серии встреч и worker

- Daily/weekday серии с конечной датой или числом встреч и явно выбранными периодами. Серверный preview показывает nominal wall time, разрешённый instant и DST warnings; устойчивый occurrence key не меняется при переносе.
- Экземпляры сначала имеют reserved header; явная подготовка периода или отдельный worker создаёт одну shared meeting/task/package. Подготовка не подтверждает личный план или факт автоматически.
- Изменение с даты, pause, skip/move/restore/reset используют ревизии и preview; зафиксированное расписание и когда-либо записанное присутствие защищены. Reset/restore отдельно показывают плановый состав/длительность до и после.
- Перед freeze выполняется полный календарный census, включая отменённые header-only экземпляры. Большой backlog подготавливается ограниченными chunks; worker retry не дублирует сущности. Current stored authorizer проверяется при каждом выполнении.

Локальный worker использует явную миграцию очереди, точную подписку outbox и отдельный процесс. Это bounded реализация по [16](docs/16-p3b-contract.md), а не общий планировщик произвольных jobs.

### Ограниченный P4a: зависимости и личный граф

- Finish-to-start связи между задачами разных проектов одного workspace; cycles проверяются по полному графу. Снятие/восстановление сохраняет identity и историю ревизий.
- Предшественник разрешён только в Done. Warn показывает блокировку; Enforce запрещает новый переход в работу/Done, включая изменение шаблона повторяющейся встречи. Фильтр/архив не скрывает blocker от проверки.
- Граф выбранных задач имеет явные границы и читаемый список; Canvas загружается отдельно. Своя раскладка сохраняется только явной командой, включает скрытые позиции и не меняет задачи, даты, план или факт. Доступны клавиатурные формы связей и перемещения.

Это current dependency projection и personal view preference. Historical topology не восстанавливается из текущего графа.

### Ограниченный P4b: даты и простой Gantt

- У обычной задачи есть nullable дата начала и срок без времени. Представление «Сроки» показывает загруженные задачи в явно выбранном окне28/84/366 календарных дней; одна дата остаётся точкой, дальние даты обрезаются по окну. Часы не превращаются в календарную длительность.
- Даты одной или до100 задач меняются вводом полей или сдвигом на день, затем серверным review и атомарным apply. Устаревшие версии/источники требуют нового review, потерянный ответ повторяется с исходным ключом и содержимым. Pointer drag пока не реализован; автоматического каскада дат нет.
- Текущие зависимости показывают inclusive date conflicts, missing dates и отдельный meeting-calendar unknown. Даты встреч меняются через их календарь. Date edit не меняет оценку, личный план или факт.
- Явно выбранный immutable personal/project baseline даёт отдельную исходную полосу и происхождение. Старое отсутствие startDate показывается как «не сохранялась», а не подменяется текущей датой; not-set и not-in-baseline различаются. Cutoff сначала сохраняет исходный план, затем требует нового review до proposed date writes.

Точный bounded scope — [18](docs/18-p4b-contract.md), фактическая приёмка — [11](docs/11-implementation-progress.md).

### Ограниченный P5a: импорт CSV

- Локальный UTF-8 CSV до50 строк задач,100 колонок и1MiB: сохранение исходного файла, явное сопоставление, предварительная проверка и атомарное применение в одном проекте. Внешние ID остаются строками; повтор неизменённого источника не создаёт копии, конфликты не перезаписываются.
- Переносятся обычные задачи, родительские связи и пять скалярных типов существующих дополнительных полей. Смысл исходных часов и единицы сохраняются в сверке. Импортированная текущая оценка не становится исходной оценкой пакета, недельным планом или фактом.
- Явно приватные строки блокируются; для остальных требуется подтверждение доступности выбранного пилота. Исходник и сверка доступны owner/admin. Это не перенос приватных ACL и не полный импорт Asana, OAuth, вложений или зависимостей.

Точный scope — [19](docs/19-p5-import-contract.md), проверки — [11](docs/11-implementation-progress.md).

### Ограниченный P5b: локальный MCP

Workspace → «Интеграции» позволяет выпустить свой ограниченный ключ, выбрать scopes/срок и отозвать его. Браузер показывает секрет один раз в памяти; API хранит только hash и метаданные. Потерянный секрет не восстанавливается: отзовите запись и выпустите новую.

Compiled stdio adapter предоставляет семь чтений и keyed `create_task`/`update_task` через обычные domain commands. Каждые list/call проверяют текущую membership, scopes, expiry/revoke; task write повторно проверяет credential внутри workspace barrier до cached outcome. Неизвестный результат требует точно исходного call и operationKey. Это loopback-only локальный пилот, без remote MCP/OAuth/private ACL.

MCP запускается отдельным клиентом непосредственно через Node, без npm banner и без DATABASE_URL. `npm run dev` его не запускает; конфигурация клиента автоматически не изменяется. Пример безопасной конфигурации — [apps/mcp/README](apps/mcp/README.md), точный контракт — [20](docs/20-p5b-mcp-contract.md), текущий handoff — [21](docs/21-local-pilot-handoff.md).

Ещё не реализовано: приватные ACL, общий Auth, сохранённые представления, массовые операции и полная история встроенных полей (полный P1); закрытие факта и исправления закрытых периодов, полная точность завершённого пакета, принятие поздней неизвестной оценки, полноценные split/replace/transfer/carryover и дневной факт (полный P2); полный P3/My Tasks, Gantt date pointer resize и остальной P4, полный импорт, остальные MCP tools и remote MCP, календарные connectors и deployment. Текущий интерфейс не является завершённым MVP.

### Неопределённый результат записи

Автоматического повтора записи и офлайн-очереди нет. Пока запрос выполняется или его исход неизвестен, форма показывает отправленные данные без возможности их менять. Явный повтор отправляет то же содержимое с тем же ключом; если закрыть диалог, состояние остаётся на странице. При уходе со страницы или смене actor, а также при перезагрузке или закрытии вкладки интерфейс предупреждает; осознанный уход сбрасывает этот ключ из памяти. Долговременной очереди команд нет, поэтому прежде чем создавать что-то заново, проверьте, что сервер уже сохранил.

## Локальный запуск

Нужен Node.js 24.19.0 (закреплён в `.node-version` и `.nvmrc`). Все команды выполняются из корня репозитория. Зависимости ставятся строго по lockfile: `npm ci`.

### Текущий рабочий checkout

В этом checkout игнорируемый `.env` (права 0600) уже указывает на сохранённый синтетический кластер PostgreSQL 17.5 в игнорируемой `.local/postgres/data` (только `127.0.0.1:55432`, база `workloom_dev`). Это кластер конкретной задачи, а не production и не стандартная настройка. Пока он работает, достаточно:

```sh
npm ci
npm run dev              # API на 127.0.0.1:4310, клиент на http://127.0.0.1:4311
```

Не заменяйте этот `.env` значениями из `.env.example`: порт Docker 54329 к этому кластеру не относится. Учётные данные в документацию не выносятся. История кластера — в [журнале 11](docs/11-implementation-progress.md); текущие схема, сохранность и runtime-проверки — в [журнале 25](docs/25-ux-verification.md).

### Новая копия с Docker

Стандартный путь для свежей копии: PostgreSQL 17 из Docker Compose на `127.0.0.1:54329`, значения из `.env.example`. На хосте разработки Docker отсутствовал, поэтому этот путь там не исполнялся; проверки базы выполнены на нативном PostgreSQL (см. журнал 11).

```sh
cp -n .env.example .env  # не перезаписывает существующий .env; синтетические значения без секретов
npm ci
npm run db:up            # PostgreSQL 17 в Docker на 127.0.0.1:54329
npm run build
npm run db:migrate
npm run db:seed:demo     # синтетические участники и пространства
npm run dev              # API на 127.0.0.1:4310, клиент на http://127.0.0.1:4311
```

Режим без входа (`AUTH_MODE=dev`) предназначен только для локальной разработки на синтетических данных. Скрипты `dev:api`, `start` и `db:*` читают корневой `.env`; переменные, уже заданные в окружении, имеют приоритет.

Курсоры списков задач, истории значений и недельного планирования подписываются локальным секретом процесса API. После перезапуска API выданные курсоры отклоняются с 400; автоматического восстановления в клиенте нет, поэтому список или страницу нужно перезагрузить вручную. Долговременной публичной конфигурации ключа нет до P6.

### Автоматическая подготовка встреч

`npm run dev` запускает только API и web. Для автоматической подготовки серий нужен отдельный процесс из корня репозитория:

```sh
npm run build
npm run db:migrate
npm run db:queue:migrate        # явная установка/проверка pg-boss schema и четырёх approved queues
npm run start --workspace @workloom/worker
```

Worker при старте только проверяет application/queue readiness и настройки; сам DDL не создаёт и drift не исправляет. Health — JSON logs `worker.health`/`worker.health_queue`; SIGTERM завершает работу с drain. Подробности и ограничения — [apps/worker/README](apps/worker/README.md). В текущем checkout после реального cutoff gate worker штатно остановлен и OFF; API/web и синтетические данные сохранены. Отдельный managed worker-only lifecycle также принят; [43](docs/43-managed-local-worker.md) описывает `start --worker`, `worker-start`, `worker-stop`, свежий doctor health и ещё не проверенные общий lifecycle с активным worker и OS reboot. Plain `start` сохраняет уже запущенный owned worker, но не запускает новый.

### Проверка production-сборки

```sh
npm run build
NODE_ENV=production npm start   # собранный API и SPA на http://127.0.0.1:4310
```

Это локальная оптимизированная сборка, а не deployment.

### Тесты

- `npm run test:unit` — unit-тесты contracts, domain, db, API и worker, затем jsdom-тесты `@workloom/web`. У `@workloom/ui` отдельного набора тестов нет.
- `npm run test:integration` сначала выполняет полную сборку (`npm run build`), потому что набор включает smoke собранного API и ассетов SPA. `.env` не читается: экспортируйте отдельный `TEST_DATABASE_URL=postgres://<user>:<password>@127.0.0.1:<port>/workloom_test`. Имя базы должно начинаться с `workloom_test` или заканчиваться на `_test` и не совпадать с `DATABASE_URL`.
- Браузерные тесты: один раз `npm run test:e2e:install`, затем `npm run test:e2e`. Playwright сам запускает `npm run dev` (или использует уже запущенный) и открывает `http://127.0.0.1:4311`. PostgreSQL он не поднимает: база должна быть запущена, мигрирована и заполнена демо-данными.

## Добавление языка

1. Скопируйте нужные JSON-файлы пространств имён из `apps/web/src/i18n/locales/en/` в каталог с корректным языковым тегом, например `apps/web/src/i18n/locales/de/` или `apps/web/src/i18n/locales/fr-CA/`.
2. Переведите значения, сохранив английские ключи, имена `{{parameter}}` и форму сообщений. Для множественного числа сохраните объект с обязательной формой `other`; остальные формы выбираются по правилам языка. HTML не добавляйте. Перевод может быть частичным: пропущенные сообщения берутся из English-каталога.
3. Из корня репозитория на Node.js 24 проверьте каталоги, обнаружение файлов и типы:

```sh
npm run check:localization
npm run test --workspace @workloom/web -- src/i18n/LocalizationManager.test.tsx src/i18n/catalog-discovery.test.ts src/i18n/audit.test.ts
npm run typecheck --workspace @workloom/web
```

Реестр языков и импорты менять не требуется: язык обнаруживается по JSON-файлам. Чтобы добавить его в собранное приложение, выполните отдельную `npm run build` и перезагрузите вкладку. При двух и более включённых в сборку языках переключатель появится в верхней панели автоматически. English остаётся языком по умолчанию до явного выбора пользователя.

Подробности о fallback, параметрах и проверке переключения — в [руководстве по локализации](docs/23-localization-and-ux.md#add-a-language).
