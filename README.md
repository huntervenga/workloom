# Workloom

Рабочее название собственного командного трекера: привычная таблица задач, история оценок, недельные планы, общие созвоны, зависимости и автоматические отчёты.

Создано 16 октября 2026 года. Сейчас здесь P0 и ограниченные P1a/P1b/P2a. P0 — цепочка React → Fastify → реальный PostgreSQL с синтетической локальной identity. P1a — проекты, секции, задачи и теги; P1b — типизированные колонки проекта, их значения и история; P2a — недельный план, фиксация, ручной факт и воспроизводимый план/факт в браузере, API, domain и PostgreSQL (подробнее ниже). Полный P1, MVP и командный пилот не завершены. Что, когда и кем реально проверено — в [журнале доказательств](docs/11-implementation-progress.md); этот README результатов прогонов не фиксирует.

## Стек и границы

React + TypeScript + Vite для клиента, Node.js + TypeScript + Fastify для сервера, PostgreSQL + Drizzle для хранения. Клиент и сервер находятся в одной npm workspaces монорепе. Планируемая площадка — Railway; ресурсы ещё не созданы.

Первый локальный прототип работает без входа пользователя на синтетических участниках. Пользователи, пространства, роли и политики уже есть в модели; общий Auth подключается перед командным пилотом с реальными данными. Для этой первой недели достаточно таблицы, план/факта, встреч и минимального импорта; полный Gantt, builder и MCP можно завершить следом.

## Что реализовано в P1a

- Проекты с четырьмя статусами по умолчанию, секции и теги workspace со стабильными ID: создание и переименование в интерфейсе; архивирование этих сущностей без удаления строк — возможность API.
- Обычные задачи, видимые всему workspace: таблица и боковая панель для создания и редактирования; несколько участников и ответственный, статус, срок, приоритет, теги и текущая оценка; подзадачи-детализация и явный `added_scope`; архив и восстановление.
- Серверные поиск, фильтры и постраничная загрузка; итоги в таблице видимо относятся только к уже загруженным строкам.

Важное поведение:

- «Оценка задачи» — текущий общий бюджет WorkPackage на всю команду, а не baseline и не личные часы; персональный недельный план и его распределения задаются отдельно в P2a. Подзадача-детализация разделяет пакет родителя, поэтому итоги считаются один раз на `workPackageId`; `added_scope` создаёт новый пакет.
- Ревизии задачи, пакета и набора участников проверяются независимо; конфликт отклоняется, а не перезаписывается.
- Каждая команда атомарно записывает состояние, audit и outbox. Повтор с тем же `Idempotency-Key` и тем же содержимым возвращает сохранённый результат; другое содержимое с тем же ключом отклоняется.

## Что реализовано в P1b

- Колонки проекта девяти типов: текст, число, длительность в минутах, дата, одиночный и множественный выбор, участники, логическое значение и URL. Значения редактируются в панели задачи и показываются в таблице; тип колонки после создания неизменяем.
- Менеджер колонок для owner/admin: определения и варианты выбора со стабильными ID, порядок и видимость. Ширина поддерживается API и сохраняется интерфейсом; отдельного UI изменения ширины пока нет. Настройки общие для проекта; личные представления пока отсутствуют. Архивные варианты сохраняются в прежних значениях и истории, но не назначаются заново.
- История значений с постраничной загрузкой и неизменяемым снимком определения, названий вариантов и участника изменения. Переключатель записи действует на будущие изменения: включение не восстанавливает прошлое, выключение не удаляет уже записанное. Audit/outbox сохраняют метаданные операции, а полные старое и новое значения — только включённая история.
- Простая блокировка значений отдельной пользовательской колонки, действующая через общие domain-команды. Это не блокировка встроенной оценки и не недельный baseline. Ревизии определения, значения и расположения колонок проверяются независимо; `null`, `0`, `false` и отсутствие записи различаются.

## Что реализовано в P2a

В проекте открывается страница «Неделя»: периоды с семью календарными днями и timezone, персональные планы в минутах отдельно от общей оценки задачи, распределения по исполняемым задачам и нераспределённый остаток. Участник меняет свой план и факт; owner/admin — также чужие. Один commitment сохраняет ID для одной тройки period/package/member.

- Личная и проектная фиксация показывают серверный preview. Его hash проверяет все источники под общим барьером записи; устаревший preview требует повторного просмотра. Неизменяемые снимки хранят значения и подписи, включая неизвестные оценки.
- Наступивший cutoff проверяется и существующими командами задач/колонок. Сначала фиксируется старый план; запрещённая правка возвращает 409 с уже сохранённым baseline, повтор не создаёт второй снимок. Удаление участника или перенос задачи не снимают защиту выбранного значения и пакета, даже если оно отсутствовало или было null.
- После фиксации можно добавлять новую работу и записывать факт. Сервер отличает исходный план, добавленный объём и незапланированную работу. Detail child сохраняет package; родитель, дети, участники и теги не размножают часы.
- Ручной факт относится к человеку, задаче и целому периоду, без выдуманной дневной разбивки. Первая обычная запись не требует причины; коррекция или void создают новую неизменяемую ревизию с причиной. Явный ноль отличается от отсутствия/void.
- План/факт сохраняется как отдельный report run с исходным baseline, точными ревизиями факта, серверными итогами и графиком по людям; детализация загружается страницами. Правка факта не меняет прежний run. Неизвестные планы и пропуски факта видны через полноту/охват; точное отклонение при неполноте остаётся null. Недельные 360 минут сравниваются с недельным фактом, а не с полной оценкой пакета 1200.

Это ограниченный P2a: фактические проверки и оставшиеся ограничения описаны в [контракте 13](docs/13-p2a-contract.md) и [журнале 11](docs/11-implementation-progress.md). Наличие реализации не заменяет запись о завершённом browser/полном gate в журнале.

Ещё не реализовано: приватные ACL, общий Auth, сохранённые представления, массовые операции и полная история встроенных полей (полный P1); закрытие факта и исправления закрытых периодов, полная точность завершённого пакета, принятие поздней неизвестной оценки, полноценные split/replace/transfer/carryover и дневной факт (полный P2); встречи (P3); worker, календарные connectors, внешние MCP-адаптеры и deployment. Текущий интерфейс не является завершённым MVP.

### Неопределённый результат записи

Автоматического повтора записи и офлайн-очереди нет. Пока запрос выполняется или его исход неизвестен, форма показывает отправленные данные без возможности их менять. Явный повтор отправляет то же содержимое с тем же ключом; если закрыть диалог, состояние остаётся на странице. При уходе со страницы или смене actor, а также при перезагрузке или закрытии вкладки интерфейс предупреждает; осознанный уход сбрасывает этот ключ из памяти. Долговременной очереди команд нет, поэтому прежде чем создавать что-то заново, проверьте, что сервер уже сохранил.

## Локальный запуск

Нужен Node.js 24.19.0 (закреплён в `.node-version` и `.nvmrc`). Все команды выполняются из корня репозитория. Зависимости ставятся строго по lockfile: `npm ci`.

### Текущий рабочий checkout

В этом checkout игнорируемый `.env` (права 0600) уже указывает на временный синтетический кластер PostgreSQL 17.5, запущенный отдельно от репозитория (только `127.0.0.1:55432`, база `workloom_dev`). Это кластер конкретной задачи, а не production и не стандартная настройка. Пока он работает, достаточно:

```sh
npm ci
npm run dev              # API на 127.0.0.1:4310, клиент на http://127.0.0.1:4311
```

Не заменяйте этот `.env` значениями из `.env.example`: порт Docker 54329 к этому кластеру не относится. Учётные данные в документацию не выносятся. Состояние кластера, его схемы и проверок — в [журнале 11](docs/11-implementation-progress.md).

### Новая копия с Docker

Стандартный путь для свежей копии: PostgreSQL 17 из Docker Compose на `127.0.0.1:54329`, значения из `.env.example`. На хосте разработки Docker отсутствовал, поэтому этот путь там не исполнялся; проверки базы выполнены на нативном PostgreSQL (см. журнал 11).

```sh
cp -n .env.example .env  # не перезаписывает существующий .env; синтетические значения без секретов
npm ci
npm run db:up            # PostgreSQL 17 в Docker на 127.0.0.1:54329
npm run db:migrate
npm run db:seed:demo     # синтетические участники и пространства
npm run dev              # API на 127.0.0.1:4310, клиент на http://127.0.0.1:4311
```

Режим без входа (`AUTH_MODE=dev`) предназначен только для локальной разработки на синтетических данных. Скрипты `dev:api`, `start` и `db:*` читают корневой `.env`; переменные, уже заданные в окружении, имеют приоритет.

Курсоры списков задач, истории значений и недельного планирования подписываются локальным секретом процесса API. После перезапуска API выданные курсоры отклоняются с 400; автоматического восстановления в клиенте нет, поэтому список или страницу нужно перезагрузить вручную. Долговременной публичной конфигурации ключа нет до P6.

### Проверка production-сборки

```sh
npm run build
NODE_ENV=production npm start   # собранный API и SPA на http://127.0.0.1:4310
```

Это локальная оптимизированная сборка, а не deployment.

### Тесты

- `npm run test:unit` — unit-тесты contracts, domain, db и API, затем jsdom-тесты `@workloom/web`. У `@workloom/ui` отдельного набора тестов нет.
- `npm run test:integration` сначала выполняет полную сборку (`npm run build`), потому что набор включает smoke собранного API и ассетов SPA. `.env` не читается: экспортируйте отдельный `TEST_DATABASE_URL=postgres://<user>:<password>@127.0.0.1:<port>/workloom_test`. Имя базы должно начинаться с `workloom_test` или заканчиваться на `_test` и не совпадать с `DATABASE_URL`.
- Браузерные тесты: один раз `npm run test:e2e:install`, затем `npm run test:e2e`. Playwright сам запускает `npm run dev` (или использует уже запущенный) и открывает `http://127.0.0.1:4311`. PostgreSQL он не поднимает: база должна быть запущена, мигрирована и заполнена демо-данными.

## Команды

Все команды ниже — реальные скрипты корневого `package.json`. Какие из них и на каком состоянии дерева прошли, записано в [журнале 11](docs/11-implementation-progress.md).

| Команда | Что делает |
| --- | --- |
| `npm run dev` | Собирает библиотеки и запускает API и Vite dev server |
| `npm run build` | Собирает пакеты и приложения по порядку: contracts → domain → db → ui → api → web |
| `npm start` | Запускает собранный API (`apps/api/dist/main.js`) |
| `npm run lint` | ESLint без предупреждений и проверка границ браузерного кода |
| `npm run typecheck` | Проверка типов во всех пакетах, корневых конфигурациях и `tests/` |
| `npm run check` | `lint` и `typecheck` |
| `npm run test:unit` | Unit-тесты contracts, domain, db и API, затем jsdom-тесты `@workloom/web` |
| `npm run test:integration` | Полная сборка, затем интеграционные тесты на PostgreSQL и smoke собранного API/SPA (нужен `TEST_DATABASE_URL`) |
| `npm run test:e2e` | Браузерные тесты Playwright в Chromium |
| `npm run db:up` / `npm run db:down` | Запуск и остановка PostgreSQL в Docker; `db:down` сохраняет данные |
| `npm run db:generate` / `db:migrate` / `db:seed:demo` | Генерация миграций, применение миграций, синтетический демо-набор |

## Структура

```text
apps/web/          React SPA
apps/api/          HTTP API и выдача собранного SPA
apps/worker/       Повторения, отчёты, импорт и outbox
packages/contracts/ Общие DTO и схемы валидации
packages/domain/   Прикладные команды и правила
packages/db/       PostgreSQL, Drizzle и миграции
packages/ui/       Базовые компоненты и токены
packages/config/   Общие конфигурации TypeScript и lint
infra/             Docker Compose для локального PostgreSQL; позже Railway
scripts/           Порядок сборки workspaces, проверка границ, загрузка .env
tests/integration/ Интеграционные тесты на отдельной тестовой базе
tests/e2e/         Браузерные тесты Playwright
tests/fixtures/    Контрольные примеры без личных данных
docs/              Спецификация, планы и журнал доказательств
```

Пустые каталоги обозначают согласованные границы будущего кода; они не означают наличие реализации. Рабочее название Workloom не является утверждённым публичным брендом.
