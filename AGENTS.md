# Workloom

Workloom is the provisional name for a team task tracker. This monorepo holds a React/TypeScript client and Node.js/TypeScript backend. The repository contains application code: P0 (React → Fastify → PostgreSQL with a synthetic development identity), bounded P1a (projects, sections, statuses, tags, workspace-visible tasks with shared work-package estimates), bounded P1b (nine typed project-scoped custom fields, stable option IDs, shared project-column settings, value history and custom-field locks), bounded P2a (weekly periods, personal commitments/allocations, source-fresh personal/project freezes, period work revisions and pinned weekly plan/fact reports), and bounded P2b (project work-category binding, immutable category snapshots and explicit recategorization, pinned work-type reports, explicit-week personal plan/fact entry from the task table). Accepted bounded P3a adds one-off meetings, explicit personal-plan preview/apply, atomic attendance and immutable occurrence work revisions; exact functional, browser and visual evidence is recorded separately in the journal. Full P1 (private ACLs, shared Auth, saved views, bulk edits and complete built-in-field history), full P2 (close/corrections, full-package completion accuracy, late estimate acceptance, split/replace/transfer/carryover commands and daily work logs), recurrence/materialization workers (P3b), dependency graph/Gantt (P4), external MCP adapters and deployment are not done. The exact P2a/P2b/P3a catalogs and limits live in `docs/13-p2a-contract.md`, `docs/14-p2b-contract.md` and `docs/15-p3a-contract.md`; acceptance evidence stays in the journal, not in the implementation status paragraph. Use `README.md` for setup and `docs/11-implementation-progress.md` for what was actually verified, when and by whom.

## Working boundaries

- Keep client code in `apps/web`, server adapters in `apps/api`, jobs in `apps/worker`, shared contracts in `packages/contracts`, domain commands in `packages/domain`, persistence in `packages/db`, and shared UI in `packages/ui`.
- Run all commands with this repository as the explicit working directory. Commands described in planning documents are intended future interfaces until implemented; do not claim they already run.
- Preserve other contributors' uncommitted changes and stay within assigned files.
- Early local versions may use a development identity adapter without login. Keep workspace/actor context and permission checks in domain commands. The no-login mode is for local development with synthetic data, not a deployable public authentication bypass.
- UI, HTTP, MCP, imports and background jobs use the same domain commands and access rules. Baselines and confirmed history are corrected by revision, not silently overwritten.
- Entity IDs are UUIDs; the shared `idSchema` in `packages/contracts` canonicalizes them to lowercase, and domain code compares IDs case-insensitively.
- Custom-field types are immutable. Null, zero, false and an absent value row are distinct. Keep definition, value and project-column-setting revisions independent. Disabling value history never deletes existing immutable snapshots; audit/outbox for value writes contain metadata, not hidden old/new values. The P1b manual custom-field lock is distinct from P2a baseline locks on selected task/field and work-package identities, including absent/null values.
- Every new task/field/planning mutation must declare an exhaustive typed intent and run the mandatory planning guard after current authorization/idempotent replay and before its handler. Overdue freeze saves old sources under the shared workspace barrier. A protected edit commits only the freeze and tagged idempotent rejection; unwrap FIELD_LOCKED after the transaction commits. Unexpected errors roll back everything; never catch a late handler error and commit partial writes.
- Preserve immutable personal/project snapshots and first package-freeze observations. An unknown first whole-package estimate stays original-unknown even if protectEstimate was false and a current estimate is filled later; explicit late acceptance is future work. New post-freeze work is server-classified added/unplanned, never client-claimed original.
- Weekly reports use pinned baseline/worklog revisions and authoritative server summaries/by-person groups. Do not replace missing/void with zero, multiply work logs through tags/participants/children, or derive full totals from loaded row pages. Manual-period facts have no invented daily precision.
- Work categories use stable project field/option IDs and immutable first-fact snapshots. Hours-only corrections copy the existing category; explicit recategorization requires a reason and current worklog/binding revisions. Include uncategorized minutes in work-type denominators. Preserve old `work.set` parsed input/hash and exact stored outcomes; optional output additions must not inject defaults into old replay JSON.
- Task-table time writes require an explicitly selected period. Server task/package projections include unloaded detail sources; deduplicate packages across pages and never sum loaded projections into an authoritative period total. Active zero, missing and void sources remain distinct.
- Meeting creation proposes personal plans but does not write plans or attendance automatically. Keep the current meeting locator canonical before the first fact. Generic task/manual commands must not bypass meeting roster/schedule/package guards. Meeting occurrence attribution and attendance source identity remain immutable across metadata changes and category recategorization; current attendance reads join the latest worklog head. Old manual commands and cached outcomes stay unchanged when recorded-work output unions expand.
- Recurrence and P4 contracts in docs16/docs17 remain planned until explicit milestone GO. Future materialization must reuse an in-transaction meeting primitive without nesting public write runners or skipping source census before freeze.
- Do not deploy, publish, provision paid services, send invitations or external messages, change secrets, or perform destructive data operations without the user's authorization.
- Before reading or editing a sibling product, announce the target, inspect its Git state and read local instructions. Do not import sibling product source at runtime.
- Verify only the affected scope. Documentation changes require link and consistency checks; implementation requires the milestone's meaningful tests. No website build is needed for documentation-only changes.
- If Claude CLI is used, pass `--model opus` unless Pavel requests a different model; preserve actual review provenance.
